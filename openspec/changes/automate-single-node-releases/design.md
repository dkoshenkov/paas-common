# Design

## Context

Подтверждены read-only удалённые теги common `v1.0.0` (`44986cc…`) и `v1.1.0` (`7b22045…`); manifest на main содержит `1.1.0`, CHANGELOG относится к SDK. В ctl и daemon удалённых тегов нет. Локальный manifest common `0.3.2` и локальные теги отстают от origin и не являются основанием для отката. 7 ноября пользователь определил: «мультинод делаем в версии v2, так что давай пока повышать минорные». Рабочие AGENTS, backlog и delta specs согласованы с этой границей. В опубликованном main прежняя редакция AGENTS пока связывает 1.0 с мультинодом.

8 ноября повторно сверены доступные по SSH удалённые refs всех трёх репозиториев. Границы main — common `7b22045ec8240932024a263c742f46a7529afcb6`, ctl `a7a50ca6a8a6808e1c2bc5dbf194eed3daf8ea80`, daemon `d34d5610735250d5c5f8fe01812a654b418f1058`. У common тег и опубликованный GitHub Release `v1.1.0` соответствуют версии в `configs/.release-please-manifest.json`. У ctl и daemon команда ls-remote не вернула тегов. Через авторизованный коннектор GitHub коллекции releases у ctl и daemon вернули пустые массивы. В полных деревьях обеих main (truncated=false) из release-файлов присутствует только .github/workflows/release-reusable.yml, release manifest отсутствует. В common граница v1.1.0 совпала с merge commit [релизного PR №23](https://github.com/dkoshenkov/paas-common/pull/23).

В опубликованном common workflow `.github/workflows/release.yml` запускается по push в main, задаёт concurrency group release и передаёт RELEASE_PLEASE_TOKEN в googleapis/release-please-action@v5. Для commit релиза 1.1.0 GitHub вернул success в [существующем запуске](https://github.com/dkoshenkov/paas-common/actions/runs/42376950719). В main ctl и daemon из релизных workflow имеется только вызываемый release-reusable.yml. Эти данные описывают действующую конфигурацию; приёмка нового вычислителя в GitHub и проверка прав его токена остаются открытыми.

## Goals / Non-Goals

**Goals:** продолжить 1.x common, согласовать bootstrap приложений и обеспечить проверяемый выпуск.

**Non-Goals:** откат опубликованного SDK, выпуск v2, изменение API продукта, ограничение ручных действий людей, реализация в рамках planning.

## Decisions

8 ноября владелец одобрил локальную реализацию расчёта и bootstrap. Подключение workflow, изменения в GitHub и публикация требуют отдельных разрешений.

1. Для `1.x` однодового продукта предлагается minor по умолчанию, patch для обычного `fix`, breaking — minor; максимальный bump побеждает. Это сохраняет ранее явно заданное исключение fix из общего пожелания повышать minor; если пользователь имел в виду minor даже для fix, политику нужно изменить до реализации. Для `0.x` действует прежнее правило только в 0.x. Версия `1.x` не является ошибкой; `1.1.0` common → `1.2.0` для обычного изменения или `1.1.1` для fix. Breaking в 1.x может нарушить совместимость потребителей SDK, поэтому требует отдельного анализа совместимости и одобрения, даже если предлагаемый bump minor. Автоматика не выпускает 2.x, а политика 2.x определяется отдельно.
2. Предлагается минимальный проверяемый вычислитель по полному диапазону пользовательских коммитов от проверенной границы до точного SHA main; служебный release-коммит определяется по подтверждённому release PR, а не только тексту. Неизвестный тип — minor; `fix!` и `BREAKING CHANGE:` — minor. `Release-As` и другие overrides от пользовательских коммитов не должны обходить проверку авторасчёта. Неполная история или конфликт — остановка.
3. Первоначальный вариант, проверенный в задаче 2.3, использовал документированный CLI Release Please `release-pr --release-as <версия>` в manifest-режиме и отдельно `github-release`. [CLI](https://github.com/googleapis/release-please/blob/main/docs/cli.md) документирует override, [стратегии](https://github.com/googleapis/release-please/blob/main/docs/customizing.md) показывают, что стандартный default не даёт minor для всех типов, а always-minor не сохраняет patch для fix. Для action есть [сообщение о проблеме override в manifest](https://github.com/googleapis/release-please-action/issues/1220); не предполагать поддержку. До внедрения проверить на конкретной закреплённой версии CLI override и создание PR в том числе при только `chore`; при неуспехе остановиться и пересогласовать архитектуру. Синтетические коммиты и форк не предлагаются.
4. Common продолжает с `1.1.0` и соответствующей проверенной границы release; перед включением синхронизировать read-only факты о main, теге и release PR, не перезаписывая историю. Для ctl и daemon первый тег — `v1.0.0`. Каждый расчёт охватывает всю достижимую историю до выбранного SHA main включительно. Перед bootstrap требуется заново проверить отсутствие опубликованной границы. [Документация bootstrap](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md) описывает manifest и `bootstrap-sha`.
5. Проверка release PR без секрета сверяет рассчитанную версию с точным SHA актуальной базы и manifest; доверенный workflow перед публикацией сверяет выпуск, SHA и состояние тега. Секрет с минимальными необходимыми правами недоступен коду недоверенных PR. Существующие настройки CI и защиты исследуются; не предполагается обязательное изменение branch settings. Если нельзя обеспечить достоверную проверку, автоматический выпуск не включается. Это ограничение автоматики, а не запрет действий людей.
6. Сериализация и проверка состояния дают повторяемость: тот же SHA — та же версия, существующий PR обновляется, совпадающий тег/релиз распознаётся; конфликты требуют восстановления. Произвольный коммит не исключается только по похожему тексту.

### Результат проверки Release Please и решение для рассмотрения

На реальном CLI release-please 17.11.2 с `release-type: go`, manifest под `configs/` и локальной имитацией GitHub проверены fix, bootstrap, разные формы сообщений и повторный запуск. CLI построил ожидаемые версии 1.1.1 и 1.0.0. При повторном запуске для неизменного fix в тестовом API остался один PR. Обычный chore дал ноль PR со стандартными секциями и один после явного включения секции chore. Незнакомый conventional type учитывается при явном включении этого типа. Для сообщения `update dependency metadata` CLI вернул ноль PR даже с `--release-as 1.2.0`. Вычислитель по утверждённой политике корректно выдаёт minor для этого диапазона. Неполную границу следует отклонять до вызова CLI. [Воспроизводимая локальная проверка](../../../tests/release-please-cli/probe.py).

Состав release PR берётся из проверенного диапазона Git. Локальный генератор использует результат расчёта и историю на том же SHA, формирует manifest и записи CHANGELOG, проверяет повторный запуск и конфликт предыдущего состояния. Обновление PR и выпуск через GitHub потребуют отдельного подключения с проверкой SHA, тега и полномочий. 8 ноября владелец одобрил локальное формирование содержимого release PR.

### Проверка release PR в трёх репозиториях

8 ноября владелец одобрил локальную подготовку workflow для 3.1. Проверка получает актуальные base и head PR, пересчитывает кандидат из полной истории проверенного main и сравнивает Git-объекты двух файлов. Изменение другого пути или режима файла и устаревшая база требуют обновления кандидата. Недоверенный head используется только как набор Git-объектов для чтения. Проверка выполняет код из доверенного источника с минимальными правами чтения.

В common исходник проверяющего инструмента находится в доверенной базе. Для ctl и daemon используется тот же исходник из фиксированного репозитория common. При подключении задаётся отдельная переменная `PAAS_RELEASE_TOOLS_SHA` с полным SHA проверенного коммита, содержащего инструмент. До публикации этого коммита и установки переменной проверка кандидата в этих репозиториях должна завершаться ошибкой. Существующий release workflow common на push продолжает работать независимо. 8 ноября GitHub API вернул для ветки main во всех трёх репозиториях `protected=false` и пустой список required status check contexts. Фактическую привязку результата к PR и повторную проверку перед публикацией предстоит проверить в GitHub.

Для последующих выпусков доверенная переменная `PAAS_RELEASE_BASE` имеет вид `version@commit-sha`. Она задаёт независимо подтверждённую границу. Проверка читает версию из manifest базы и сравнивает тег с этим SHA. Иначе перемещённый с прежней границы на более поздний feature-коммит тег мог бы исключить этот feature из расчёта и ошибочно дать patch. Для уже подтверждённой границы common `1.1.0` SHA закреплён в проверяющем инструменте. Для bootstrap ctl и daemon без manifest и релизных тегов используются подтверждённые корневые коммиты; переменная границы при этом должна отсутствовать.

`pull_request_target` запускает workflow в контексте default branch. Shell отдельно фиксирует и проверяет head PR. Установку обязательной проверки на нужный SHA и поведение реального runner требуется подтвердить при подключении. [Документация GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target).

### Локальная приёмка проверки PR

В двух временных полных копиях опубликованного main для ctl и daemon из подготовленных manifest и CHANGELOG составили тестовые кандидаты с одним коммитом. Каждый дважды получил `verified`. Добавление файла `unexpected.txt` вызвало отказ. Для common отдельным тестом воспроизведена подмена тега после feature-коммита. Проверка отклонила неверную границу, которая иначе позволяла бы получить patch вместо minor. Набор тестов проверяет также подмену содержимого, симлинки и исполняемые файлы, лишних родителей, устаревшие SHA и повтор запуска.

Для всех трёх workflow проверен синтаксис с actionlint. В [локальном сквозном сценарии](../../../tests/release-workflow/real-git-probe.py) shell из YAML получил PR как Git-объекты, восстановил локальный ref main в detached checkout, вызвал проверяющий инструмент на Go и повторно сверил SHA. В этом сценарии настоящие Git и Go работают с временными репозиториями; ответы GitHub API моделируются. [Проверка отказов](../../../tests/release-workflow/probe.py) отдельно моделирует расхождение head, ошибку fetch/diff, отсутствие доверенного pin и смену базы. Запуск в GitHub и проверка действительных полномочий токена относятся к 3.2–3.3.

### Состояние GitHub до подключения

Для 3.2 на рабочем месте выполнен `release-please --version` из закреплённой
установки: `17.11.2`. В [журнале опубликованного job common](https://github.com/dkoshenkov/paas-common/actions/runs/42376950719/job/128416386549)
runner указал фактические права своего `GITHUB_TOKEN`: запись contents, issues
и pull requests, чтение metadata. Сам шаг release-please получает отдельный
секрет `RELEASE_PLEASE_TOKEN`. Его полномочия и запуск новой проверки release PR
на выбранном SHA по-прежнему требуют подтверждения.

8 ноября API содержимого вернул 404 для `.github/workflows/release-pr-check.yml` на main каждого из трёх репозиториев. Новая проверка существует в рабочих копиях. Список repository rulesets для common пуст. Для приватных ctl и daemon этот endpoint вернул 403 с сообщением GitHub об ограничении тарифа. Ранее чтение самих веток показало `protected=false`. Через доступный коннектор endpoint настроек прав Actions workflow недоступен. Область прав действующего RELEASE_PLEASE_TOKEN и результат новой проверки на конкретном head PR остаются неподтверждёнными; успешный старый release-run common этого не устанавливает.

## Risks / Trade-offs

- [Позднее решение о v2 противоречит локальной документации] → согласовать актуализацию границ до реализации, без переписывания опубликованных релизов.
- [Возможна несовместимость SDK при breaking minor] → явно согласовать совместимость и потребителей до такого выпуска.
- [Разные границы истории Release Please и вычислителя] → интеграционные проверки pinned версии и fail closed при расхождении.
- [Нет доступа к GitHub, секретам или CI] → зафиксировать непроверенное и не включать автоматику; локальный тест не доказывает работу GitHub Actions.

## Migration Plan

### Локальная проверка на опубликованной истории 8 ноября

Для каждого репозитория взята отдельная полная bare-копия origin. Расчёт использовал SHA ветки main и содержимое manifest из Git-объекта. Рабочие ветки с изменениями PaaS в этот расчёт не вошли.

| Репозиторий | Проверенный main | Начало диапазона | Результат |
| --- | --- | --- | --- |
| paas-common | `7b22045ec8240932024a263c742f46a7529afcb6` | тег `v1.1.0` на том же SHA | `no_release`, новых пользовательских коммитов 0 |
| paas-ctl | `a7a50ca6a8a6808e1c2bc5dbf194eed3daf8ea80` | корень `0344eb7fe3b6dad5ab47bf637352c79c8a2e7b8d`, включительно | первый кандидат `1.0.0`, 12 коммитов |
| paas-daemon | `d34d5610735250d5c5f8fe01812a654b418f1058` | корень `9f5bdc37f04f660dd0726c08166489db48e3fd6c`, включительно | первый кандидат `1.0.0`, 15 коммитов |

Команда запускается из модуля paas-common. Пример для подтверждённой границы common на этом снимке:

```sh
go run ./scripts/release-version --repo /path/to/full/paas-common.git \
  --head 7b22045ec8240932024a263c742f46a7529afcb6 \
  --base-tag v1.1.0 --base-sha 7b22045ec8240932024a263c742f46a7529afcb6 \
  --manifest configs/.release-please-manifest.json
```

Для первого выпуска ctl или daemon передаются `--repo`, `--head` и `--bootstrap-root` для каждого подтверждённого корня. JSON с `status=no_release` означает отсутствие релиза. При конфликте команда возвращает ненулевой exit code. Для формирования двух файлов к тем же параметрам добавляется `--output-dir` с абсолютным путём вне исходного репозитория. Повтор в тот же каталог проверяет содержимое. Для no_release выбранный путь остаётся свободным. Проверка локального калькулятора и файлов — `go test -race ./scripts/release-version`. В локальных результатах проверены 12 SHA для ctl и 15 для daemon: порядок и состав совпали с `git rev-list --reverse refs/heads/main` в соответствующих полных копиях.

При подсчёте достижимого диапазона учитываются и merge-коммиты. Если ветка содержит один `fix: ...`, а в main появился отдельный `Merge pull request ...`, этот диапазон даёт minor. Для одного squash-коммита с заголовком `fix: ...` результат — patch. Исключение служебного релизного коммита требует подтверждённого SHA его PR.

После проверки вычислителя и интеграции CLI отдельно согласовать подключение workflows. Проверить реальные права и CI с внешним доступом. При сбое отключить автоматический caller, сохраняя имеющиеся PR, теги и релизы; восстановление после сверки. Коммиты, push, PR и публикация требуют отдельных разрешений.
