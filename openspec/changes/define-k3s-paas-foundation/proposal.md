# Proposal

Согласовано дополнительно: сетевые связи разных приложений закрыты по умолчанию
и разрешаются явно через PaaS; компоненты одного приложения могут общаться свободно.
Для каждого компонента выбирается внешний доступ none/allowlist/all; по умолчанию
none. Allowlist содержит точные домены без портов и разрешает все порты домена.
Поддомены задаются отдельно; маски и автоматическое разрешение поддоменов исключены.
Связи между приложениями задаются у источника, без встречного разрешения получателя.
Мигратор имеет только DNS и целевую PostgreSQL. Механизм исполнения доменных
ограничений, включая изменения DNS и обход через IP, отложен в PAAS-012;
список пока не считается гарантией сетевого запрета. Точная схема конфигурации открыта.

## Why

Нужна PaaS для быстрой раскатки бизнесовых приложений, переиспользования инфраструктуры
и общего мониторинга. Начальный сценарий изменился с Docker Compose на k3s;
существующие API-черновики нужно привести к новым требованиям.

## What Changes

- Статус: фиксация обсуждения; реализация и весь design целиком ещё не одобрены.
- Локальное переименование в `paas-common`, смена Go module path и перенос
  OpenSpec/backlog согласованы как отдельный этап. Разработка PaaS ещё не одобрена.
- Начальный формат деплоя — обычные Kubernetes-манифесты; точный способ их подачи
  и PaaS-метаданные для БД, секретов и разрешённых связей ещё требуют согласования.
- Начальный набор пользовательских ресурсов: Deployment, Service типа ClusterIP,
  ConfigMap и Ingress. Остальные типы отклоняются до применения пакета;
  служебные ресурсы и постоянные тома инфраструктуры создаёт PaaS.
- Namespace определяется приложением операции деплоя; имена ресурсов задаёт
  пользователь. Принадлежность учитывается PaaS, конфликты и чужой Namespace
  отклоняются; смена имени не удаляет старый ресурс автоматически.
- Пакет деплоя относится к одному явно выбранному компоненту и содержит один
  Deployment с его Service, ConfigMap и Ingress по необходимости. Каждый ресурс
  имеет одного владельца-компонента; общие пользовательские ConfigMap между
  компонентами в первой версии не поддерживаются.
- PaaS управляет стандартными метками приложения, компонента и экземпляра Deployment
  и точными selectors по ним. Стабильные ID и владение сохраняются до изменений
  Kubernetes и переиспользуются после сбоя; мигратор не получает ID Deployment.
- Штатное управление ресурсами выполняется через PaaS. Документация рекомендует
  не обращаться к Kubernetes API в обход PaaS: прямые изменения могут нарушить
  согласованность состояния платформы и кластера.
- PaaS управляет служебными объектами и защищёнными полями через CLI/TUI;
  некритичные расхождения сопровождаются WARN с сохранением значения PaaS,
  нарушения изоляции отклоняются. Мигратор выполняется с недоступными обычным
  workloads credentials и полномочиями в Namespace приложения; daemon проверяет
  пользовательские манифесты и создаёт миграционный Job отдельной операцией.
  Обычные workloads не получают Kubernetes-права для обхода этих проверок.
- Доступ к секретам явно привязывается через PaaS к конкретным контейнерам,
  включая отдельные разрешения init-контейнеров. Имя Secret в YAML не выдаёт доступ;
  разрешённые контейнеры используют общую роль PostgreSQL приложения.
- Разрешены secretKeyRef, envFrom.secretRef, Secret volumes и Secret projections
  с проверкой привязок. ServiceAccount приложения и мигратора управляет PaaS;
  прикладные Pods и мигратор не получают API-токены и права управления Kubernetes.
- Для приватных образов используется GHCR; собственный registry в первой версии
  не разворачивается. Оператор настраивает credentials скачивания через CLI.
  GHCR-токен скрыт от daemon: для первой версии выбран доступ container runtime
  через конфигурацию registry на узле, без Kubernetes imagePullSecret с токеном.
  Первая версия передаёт токен из CLI через SSH напрямую доверенной операции узла
  и хранит в root-only файле без прикладного шифрования. Daemon работает внутри k3s
  с отдельным ServiceAccount и ограниченными правами в подготовленных Namespace;
  административная подготовка выполняется из CLI через SSH. Будущий переход на imagePullSecrets вынесен в PAAS-010,
  усиление хранения и обработки в памяти — в PAAS-011 с проверкой пересечения задач.
- Namespace и начальные права готовит доверенный этап CLI. В доступных daemon
  Namespace кластер независимо применяет Restricted в режиме enforce; daemon
  не может ослабить защиту, управлять системными workloads или получить root узла.
- Для GHCR пользователь paas получает ограниченный NOPASSWD на точные действия
  root-owned helper: сохранение, применение и статус. Сохранение не перезапускает
  k3s; применение выполняется явно. Остальные registry-настройки сохраняются.
- Приложения и общие сервисы размещаются в отдельных Namespace; межсервисный доступ
  ограничивается NetworkPolicy по явно выбранным потребителям.
- Первая среда — k3s; установщик PaaS устанавливает его, если он отсутствует
  на выбранном сервере. Обязательный PostgreSQL хранит состояние control plane PaaS.
- Внешний HTTP/HTTPS-вход первой версии — встроенный Traefik k3s в одном экземпляре
  с автоматическим получением и продлением сертификатов через ACME. Состояние ACME
  хранится на постоянном томе; Caddy и отдельный сервис продления не требуются.
- Домены регистрируются через CLI/TUI за приложением: один домен — одно приложение,
  несколько доменов на приложение допустимы. Компоненты используют их в Ingress;
  чужие/незарегистрированные домены, wildcard и правила без host отклоняются.
  Смена и удаление регистрации — отдельные операции PaaS.
- По делегированному архитектурному ревью согласован профиль маршрутов: один
  host/path на Ingress, Prefix/Exact, управляемый priority и строгий Prefix Traefik,
  проверка конфликтов всего приложения и результирующих Service/портов.
- Во втором круге согласованы единая ASCII-канонизация доменов, проверка IDNA A-label,
  служебные class/TLS Ingress и четыре управляемых annotations; backend первого
  профиля использует обычный HTTP без пользовательских Service annotations.
- В третьем круге согласованы HTTP-01, HTTP→HTTPS без fallback на HTTP backend,
  внешний наблюдаемый TLS-статус, раздельные staging/production ACME state,
  единственный writer и защищённое восстановление state. Live-проверок пока нет.
- Текущий этап продукта — `0.x.x`, только одна нода. Для `1.0.0`/`1.x.x`
  обязательна поддержка мультинода; это отдельная будущая работа.
- Первоначальная установка выполняется с компьютера оператора через SSH.
- На сервере используется отдельный Linux-пользователь `paas`.
- Основной интерфейс `paas-ctl` — интерактивный TUI в терминале.
- Вспомогательный скрипт подготавливает отдельный ключ PaaS и позволяет отозвать
  его SSH-доступ, сохраняя основной ключ оператора.
- Один общий PostgreSQL обслуживает приложения через отдельные БД и пользователей.
- БД и роли приложения создаются только при наличии мигратора в его конфигурации;
  служебная БД самой PaaS обязательна всегда. Первая миграция автоматически
  предшествует запуску компонентов; последующие выбираются через TUI/флаги CLI.
- Пользователь приложения получает SELECT/INSERT/UPDATE/DELETE без TRUNCATE и DDL;
  отдельный мигратор меняет структуру и преобразует данные в своей схеме.
  Удаление мигратора из конфигурации прекращает его последующие запуски, сохраняя
  существующие БД, роли, credentials и доступ приложения. Удаление БД и отзыв доступа
  выполняются отдельными явными операциями через PaaS.
- Отдельная учётная запись приложения нужна также для атрибуции обращений к БД.
- Пароли генерируются, сохраняются в Kubernetes Secrets и доступны оператору через CLI.
- Дополнительная инфраструктура создаётся автоматически по потребности;
  версии задаются в конфигурации платформы. Kafka пока не входит в реализацию.
- Компоненты приложения — например, API, frontend, worker, processor или scraper —
  и общие сервисы уровня платформы обновляются независимо. Сервис объявляется один
  раз, а доступ к нему выдаётся только выбранным приложениям.
- После первоначальной подготовки мигратор запускается по явному выбору оператора;
  образ собирается по SQL-шаблону.
- Flux генерирует контракты; packages-go переиспользуется и обновляется в SDK.
- **BREAKING**: планируется замена Compose-зависимых полей API описанием для новой модели;
  входом для деплоя на первом этапе будут Kubernetes-манифесты. Адаптеры Compose и
  Swarm в будущем потребуют собственных входных форматов или адаптеров.
- Окружения, квоты БД и следующие среды исполнения вынесены в backlog.

## Capabilities

### New Capabilities

- `shared-infrastructure`: обязательная основа и подключение общих сервисов по потребности.
- `application-database-access`: отдельные БД, пользователи, права и идентичность для метрик.
- `application-secrets`: генерация, хранение и явное получение credentials.
- `independent-deployments`: независимые обновления компонентов и запуск мигратора.
- `operator-tui`: интерактивное управление установкой, приложениями и операциями в терминале.

### Modified Capabilities

- Нет: основные спецификации пока отсутствуют.

## Impact

- `paas-common`: исходные API в `docs/api`, обновление packages-go с текущей `v0.2.0`,
  регенерация HTTP/gRPC/OpenAPI. Версию генератора и совместимость нужно проверить.
- `paas-daemon`: будущие управление состоянием, подготовка ресурсов, деплои и миграции.
- `paas-ctl`: TUI, вспомогательный SSH-скрипт и первоначальная установка
  с подготовкой пользователя `paas` и отсутствующего k3s; операции деплоя,
  миграций, просмотра статуса и получения credentials.
- Flux и packages-go: пока только отдельные backlog-файлы в этом workspace;
  исходники соседних проектов этим change не изменяются.
- `docs/backlog/`: задачи PaaS, Flux и packages-go, связанные с этим change.
- `AGENTS.md`: граница `0.x.x`/`1.x.x` и целевая политика автоматического
  версионирования только для `0.x.x`: minor по умолчанию, patch для fix, minor для
  breaking changes; переход на `1.0.0` согласуется отдельно после готовности мультинода.
  В `1.x.x` API проектировать с обратной совместимостью.
- Release-автоматизация проверена по локальным файлам; обнаруженные пробелы
  сохранены в backlog, workflow в текущем этапе не изменяются.
- Граница текущего этапа: документы; код, зависимости и инфраструктура не изменяются.
