## 1. Уточнение контрактов и согласование архитектуры

- Согласовано: штатное управление ресурсами через PaaS; документация рекомендует
  избегать прямых обращений к Kubernetes API в обход платформы ради согласованности
  состояния. Мигратор остаётся в Namespace приложения; daemon проверяет манифесты
  и создаёт Job отдельной авторизованной операцией. Точный реестр проверок и матрица
  Kubernetes-прав ещё требуют уточнения; это не закрывает пункты 1.1–1.4.
- Согласовано: один встроенный Traefik k3s с автоматическим получением и продлением
  сертификатов через ACME, постоянное хранилище его состояния, без Caddy и отдельного
  сервиса продления. HTTP-01, правила Ingress и жизненный цикл ACME уточнены
  в делегированных кругах ниже; конкретные версии, параметры профиля, backend
  хранилища и механизм backup/restore остаются для инфраструктурного этапа.
  Пользовательские PVC пока не согласованы.
- Согласован начальный набор пользовательских манифестов: Deployment, Service
  типа ClusterIP, ConfigMap и Ingress. Служебные ресурсы создаёт PaaS;
  неподдерживаемые виды/версии и другие типы Service отклоняются до применения
  пакета. Точные правила защищённых полей остаются частью открытого пункта 1.1.
- Согласованы Namespace и идентичность ресурсов: Namespace берётся из приложения
  операции деплоя; пропуск заполняется, чужое значение отклоняется. Явные имена
  сохраняются, принадлежность учитывается в состоянии PaaS, конфликты и дубликаты
  отклоняются, смена имени не удаляет старый ресурс. Остальные защищённые поля
  ещё требуют уточнения в пункте 1.1.
- Согласована привязка компонентов: приложение и компонент выбираются в операции;
  один пакет содержит один Deployment и его необязательные Service, ConfigMap и Ingress.
  Каждый ресурс имеет одного владельца-компонента; пользовательские ConfigMap
  между компонентами не разделяются. Деплой меняет только выбранный компонент,
  пропуск прежнего ресурса в пакете не удаляет его автоматически.
- Согласованы метки и selectors с уточнениями архитектурной проверки: три стабильных
  ID приложения/компонента/Deployment, точные selectors и привязка Services к Deployment
  текущего пакета; мигратор не получает instance ID Deployment. Намерение и владение
  сохраняются до Kubernetes, повтор использует те же ID; параллельные операции
  компонента сериализуются или отклоняются. Противоречия отклоняются, только
  managed-by исправляется с WARN после проверки владения. Формат ID и границы
  свободных меток определены в specs; реализация и пункт 1.1 в целом ещё открыты.
- Согласована явная выдача секретов конкретным контейнерам, включая отдельные
  разрешения init-контейнеров. Daemon проверяет привязки в env и томах для каждого
  потребителя; неразрешённая ссылка отклоняет пакет. Общая роль PostgreSQL приложения
  сохраняется.
- Согласованы способы подключения Secret: secretKeyRef, envFrom.secretRef, Secret
  volumes и Secret projections с проверкой всех потребителей; optional не отменяет
  разрешение. Один ServiceAccount приложения и отдельный мигратора управляются PaaS;
  без прав чтения Secrets через API, создания workloads и изменения RBAC. API-токены
  не выдаются, automount=false, явные проекции и Secrets с SA-токенами отклоняются.
  Пользовательские imagePullSecrets в первой версии не принимаются.
- Выбран GHCR с поддержкой приватных образов и настройкой credentials скачивания
  через CLI; собственный registry не нужен. Открытый GHCR-токен должен быть скрыт
  от daemon, включая косвенное извлечение через workload. Для первой версии выбрана
  registry-конфигурация узла для container runtime, без Kubernetes Secret с токеном.
  Передача — напрямую из CLI через SSH; хранение — root-only файл root:root 0600
  без прикладного шифрования. Сохранение и явное применение с перезапуском k3s
  уточнены в контракте registry-helper ниже; восстановление выполняется явным
  restore-registry с отдельным apply-registry.
  Будущий переход на независимый механизм imagePullSecrets вынесен в PAAS-010;
  реализация платформы и криптографического механизма не разрешена.
- Усиление хранения и обработки в памяти вынесено в PAAS-011 с проверкой пересечения
  с PAAS-010. runtime/secret выбран для применимых Go-операций на поддерживаемых
  Linux-целях после проверки toolchain/экспериментальной сборки; это не шифрование
  файлов, на macOS его дополнительная защита не заявляется.
- Согласована граница полномочий: CLI через SSH выполняет доверенную подготовку
  узла, Namespace и начальных прав; daemon внутри k3s с отдельным ServiceAccount
  управляет только приложениями в подготовленных Namespace. Нет SSH/sudo/admin
  kubeconfig, изменения Namespace/RBAC/admission, системных workloads, собственного
  развёртывания, произвольных PV, nodes/proxy и повышения собственных полномочий.
  Restricted enforce обеспечивается кластером независимо от daemon.
  GHCR настраивается узкой операцией с фиксированным файлом и вводом credentials
  через stdin.
- Согласован registry-helper: set-ghcr/restore-registry/apply-registry/status, root-owned бинарник
  и каталог, ограниченный NOPASSWD на точные вызовы без wildcard. Сохранение атомарное,
  с сохранением других registry-настроек и одной root-only предыдущей версии;
  применение и рестарт k3s выбираются явно. Ошибки без автоматического цикла рестартов/
  откатов; готовность k3s не подменяет проверку скачивания без влияния cache.
  Границы sudo установки/подготовки Namespace и двухшаговое восстановление
  согласованы ниже; точные команды установки/sudoers определяются до реализации.
- Согласована принадлежность доменов: регистрация через CLI/TUI за одним приложением,
  несколько доменов приложения и использование компонентами с разными путями.
  Чужие/незарегистрированные host, wildcard и правила без host отклоняются;
  смена/удаление регистрации — отдельные операции. Регистрация не заменяет DNS/ACME-проверку.
- Делегированный круг 1/3 — согласован архитектором с исправлениями: один host/path
  на Ingress, Prefix/Exact, строгий Prefix и вычисленный priority Traefik, конфликты
  и резервы всего приложения, проверка результирующих Service и сохранённых Ingress.

  Ingress, отсутствие входных Service annotations. Backend — HTTP с исключением

- Делегированный круг 3/3 — согласован архитектором с исправлениями: HTTP-01,

  компоненты по умолчанию общаются свободно. Внешний доступ каждого компонента:
  none/allowlist/all, по умолчанию none; точные домены без портов открывают все порты.
