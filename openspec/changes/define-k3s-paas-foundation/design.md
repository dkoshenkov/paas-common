# Design

## Context

- Статус: архитектура платформы согласована частично; этап переименования выполнен,
  штатное управление через PaaS и мигратор в Namespace приложения согласованы.
  Итоговая архитектура и реализация PaaS ещё не одобрены.
- Мотивация и границы репозиториев: [proposal.md](proposal.md).
- `paas-ctl` и `paas-daemon` пока шаблоны; `paas-common` содержит исходные API.
- Текущий API использует `compose_yaml` и `compose_sha256`; Makefile генерирует
  только общие контракты из `docs/api/common`.
- SDK зависит от packages-go `v0.2.0`, локальный Flux — от `v0.3.0`.
- Документ Flux относит path-параметры к отложенным возможностям;
  API PaaS уже содержит `/apps/{name}`. Нужна проверка на минимальном контракте.
- Существующий `common/migration.yaml` описывает Up/Down API;
  это не реализация отдельного контейнера мигратора.

## Goals / Non-Goals

**Goals:**

- Зафиксировать подтверждённые требования и проверяемые границы первой версии.
- Переиспользовать один PostgreSQL, сохраняя разные БД и пользователей приложений.
- Независимо управлять версиями компонентов и запусками миграций.
- Использовать Flux и packages-go по их назначению.

**Non-Goals:**

- Реализация кода в текущем документальном этапе.
- Окружения, квоты БД, Kafka, Compose и Swarm в первой реализации.
- Обязательный Vault, общий релиз frontend/backend и автоматические миграции при каждом последующем деплое.
- Мультинод в `0.x.x`; он относится к будущему этапу продукта `1.0.0`/`1.x.x`.

## Decisions

### Подтверждено пользователем

- Репозиторий называется `paas-common`: контракты, сгенерированные SDK-артефакты
  и общие определения PaaS. Локальный каталог и module path переименованы;
  OpenSpec и backlog находятся внутри него. GitHub-репозиторий переименован в
  `dkoshenkov/paas-common`; origin указывает на `git@github.com:dkoshenkov/paas-common.git`.
- Начинаем с k3s вместо Docker Compose.
- В первой версии внешний HTTP/HTTPS-трафик обслуживает один экземпляр встроенного
  Traefik k3s. Он получает и продлевает управляемые сертификаты через ACME;
  Caddy и отдельный сервис продления не нужны. Состояние ACME (`acme.json`, включая
  ключи и сертификаты) сохраняется на постоянном томе и защищается от доступа
  обычных workloads. Пересоздание Pod не должно терять это состояние.
  Настройка встроенного Traefik выполняется через `HelmChartConfig`.
- Домены явно регистрируются за приложением через CLI/TUI. Один домен принадлежит
  одному приложению; приложение может иметь несколько доменов. Host в YAML не
  регистрирует домен и не подтверждает право на него. Компоненты приложения могут
  использовать его домены с разными путями по согласованному ниже профилю маршрутов.
  Ingress принимает только явные доменные имена своего приложения;
  чужой/незарегистрированный host, wildcard и правило без host отклоняются до
  применения пакета. Смена и удаление регистрации домена — отдельные операции PaaS;
  отсутствие Ingress в пакете не удаляет регистрацию. Регистрация внутри PaaS
  не заменяет настройку DNS и подтверждение домена центром сертификации.
- Входной формат начального деплоя — обычные Kubernetes-манифесты. Это нативный
  формат k3s/Kubernetes; будущие адаптеры Compose или Swarm потребуют отдельного
  способа описания или преобразования.
- В первой версии пользовательский пакет содержит только `apps/v1 Deployment`,
  `v1 Service` типа `ClusterIP`, `v1 ConfigMap` и `networking.k8s.io/v1 Ingress`.
  Deployment описывает компоненты, Service — их внутренние адреса и порты,
  ConfigMap — несекретные настройки, Ingress — домены, пути и целевые Services.
  PaaS проверяет принадлежность домена и backend приложения и управляет выбором
  Traefik и ACME resolver; правила Ingress уточнены в трёх делегированных кругах
  ниже. Остальные защищённые поля остаются частью открытого пункта 1.1.
  Неподдерживаемый тип отклоняется до начала применения всего пакета.
  Namespace, служебные Secrets, ServiceAccount/RBAC, NetworkPolicy, Job мигратора
  и постоянные тома инфраструктуры создаёт PaaS. Пользовательские Job, CronJob,
  StatefulSet, PVC и другие типы пока не поддерживаются.
- Namespace определяется приложением, выбранным в операции деплоя. Отсутствующий
  `metadata.namespace` заполняется PaaS, совпадающий принимается; любое другое
  значение, включая `default`, отклоняется до применения пакета с указанием поля
  и ожидаемого Namespace. WARN и замена явно чужого Namespace не применяются.
- Пользователь задаёт стабильное `metadata.name`; отсутствие имени и `generateName`
  не поддерживаются. Идентичность ресурса — API group, тип ресурса, Namespace и имя;
  версия API не входит в идентичность. PaaS учитывает принадлежность ресурса
  приложению в своём состоянии; метка в пользовательском YAML её не подтверждает.
  Повторный деплой обновляет тот же ресурс в пределах разрешённых полей.
  Конфликт со служебным ресурсом, другим владельцем или объектом вне учёта PaaS
  отклоняется без автоматического присвоения. Дубликаты идентичности в одном
  пакете отклоняются до применения. Новое имя означает новый ресурс и не удаляет
  прежний; переименование и удаление требуют явной операции.
- Оператор выбирает приложение и компонент в операции деплоя; один пакет относится
  к одному компоненту и содержит ровно один Deployment. Несколько контейнеров этого
  Deployment выпускаются вместе; независимо выпускаемые части — отдельные компоненты.
  Service, ConfigMap и Ingress включаются по необходимости. Каждый пользовательский
  ресурс принадлежит одному компоненту; daemon сохраняет привязку в состоянии PaaS,
  а пользовательская метка не переносит ресурс к другому владельцу.
  Service выбирает Pods Deployment своего компонента, Ingress указывает его Service,
  пользовательские ConfigMap используются только его контейнерами. Общие пользовательские
  ConfigMap между компонентами не поддерживаются; служебные подключения к БД и общим
  сервисам выдаёт PaaS отдельно. Деплой меняет только ресурсы выбранного компонента;
  отсутствие прежнего ресурса в новом пакете не удаляет его автоматически.
- Метки идентичности: `app.kubernetes.io/part-of` — стабильный ID приложения,
  `app.kubernetes.io/component` — стабильный ID компонента,
  `app.kubernetes.io/instance` — стабильный ID экземпляра компонента, представленного
  конкретным Deployment. На Deployment и его Pod template ставятся все три;
  на Service, ConfigMap и Ingress — ID приложения и компонента. Все эти ресурсы
  и Pod template получают информационную метку `app.kubernetes.io/managed-by=paas`.
  Deployment selector и selector каждого Service текущего пакета — ровно три
  метки идентичности Deployment этого пакета, без дополнительных условий.
  Пропущенные ключи меток заполняются, заданные проверяются; отсутствующий или пустой
  selector генерируется, непустой должен совпасть целиком, включая отсутствие
  непустого `matchExpressions`. Конфликты отклоняются до применения пакета;
  только неверный `managed-by` исправляется с WARN после проверки владения.
  Описательные метки свободны, кроме служебных ключей и системных меток контроллеров;
  они не подтверждают владение и не выдают полномочия. Все ID непустые, стабильные,
  соответствуют формату Kubernetes labels и не зависят от отображаемых имён/релиза.
- Намерение создания, идентичность, владелец и стабильный ID ресурса сохраняются
  до изменений Kubernetes. Повтор операции после сбоя использует те же записи и ID;
  это не разрешает присвоить произвольный неизвестный объект. Параллельные операции
  одного компонента сериализуются либо явно отклоняются как конфликтующие.
  Старый Service вне пакета сохраняет прежнюю привязку; для переключения его включают
  в новый пакет. Мигратор не получает `app.kubernetes.io/instance` Deployment.
  Проверка пакета до применения не означает транзакционного применения Kubernetes;
  частичный результат требует повтора с сохранёнными ID.
- Способ доставки манифестов и PaaS-метаданные для БД, Secrets и разрешённых связей
  ещё не выбраны.
- Штатное управление ресурсами выполняется через PaaS; пользовательские манифесты
  проходят через daemon. Документация рекомендует не обращаться к Kubernetes API
  в обход PaaS, чтобы состояние платформы и кластера оставалось согласованным.
  Прямые административные изменения находятся вне штатного сценария; механизм
  восстановления согласованности после них пока не определён.
- Служебные объекты (созданные PaaS NetworkPolicy, Secrets и полномочия мигратора)
  управляются PaaS целиком. В пользовательских workloads защищаются Namespace,
  идентификаторы, служебные метки принадлежности/доступа и ссылки на credentials.
  Эти настройки изменяются через CLI/TUI. Остальные пользовательские метки свободны.
- Для некритичного расхождения защищённого поля выводится WARN с путём поля,
  ожидаемым значением, допустимыми вариантами и способом корректного изменения;
  применяется значение PaaS. Изменения, нарушающие изоляцию, отклоняются.
- Мигратор выполняется защищённо: обычный workload не может получить его credentials
  или использовать его полномочия, включая ссылки на Secret и ServiceAccount.
  В первой версии миграционный Job и отдельный Secret мигратора находятся в Namespace
  приложения; дополнительный Namespace мигратора не требуется. Daemon проверяет
  пользовательские манифесты и создаёт Job по своему шаблону в рамках авторизованной
  операции миграции. Обычным workloads не выдаются Kubernetes-права на чтение Secret
  мигратора, создание или изменение workloads и полномочий, позволяющих обойти
  проверки daemon. Администратор кластера и daemon — доверенные стороны;
  рекомендация оператору сама по себе не заменяет этих ограничений доступа.
- Секреты выдаются по явным привязкам PaaS к конкретным контейнерам Deployment.
  Разрешение основному контейнеру не распространяется автоматически на sidecar
  или init-контейнер; init-контейнер требует отдельного разрешения. Ссылка на имя
  Secret сама по себе не даёт доступа. Daemon сверяет все ссылки с привязками
  в состоянии PaaS до применения пакета, включая env и тома; для Secret volume
  проверяется каждый монтирующий его контейнер. Ссылка без разрешения или попытка
  получить Secret мигратора обычным контейнером отклоняет пакет.
  Контейнеры с разрешённым доступом к БД используют общую роль приложения;
  отдельные роли по компонентам этим решением не вводятся.
- Разрешены `env[].valueFrom.secretKeyRef`, `envFrom[].secretRef`, `volumes[].secret`
  и `volumes[].projected.sources[].secret` с проверкой привязок. `envFrom` требует
  разрешения на весь Secret; каждый потребитель составного тома должен иметь доступ
  ко всем его Secrets. `optional: true` не отменяет проверку разрешения. Другие
  механизмы получения секретов, включая CSI-провайдеры, пока не поддерживаются.
  Контейнеру, которому выдан секрет, доверяем: эта привязка не создаёт отдельную
  границу безопасности между контейнерами одного Pod.
- PaaS создаёт один ServiceAccount приложения для обычных компонентов и отдельный
  ServiceAccount мигратора. Они не получают прав чтения Secrets через API, создания
  workloads и изменения RBAC. Пропущенный `serviceAccountName` заполняется ожидаемым,
  совпадающий принимается, другой отклоняет пакет. На ServiceAccount и Pod template
  задаётся `automountServiceAccountToken: false`; пропуск заполняется, явный `true`
  отклоняется. В пользовательских workloads запрещены явные проекции
  `serviceAccountToken` и подключение Secrets типа `kubernetes.io/service-account-token`.
  Мигратор также работает без API-токена; права изменения схемы даёт его роль БД.
  Registry credentials рассматриваются отдельно от выдачи credentials контейнерам;
  пользовательские `imagePullSecrets` в первой версии не используются.
- Выбран GHCR (`ghcr.io`), включая приватные образы; собственный registry не нужен.
  Credentials скачивания задаются через CLI и не включаются в Git или манифесты
  значениями. Требование пользователя — сквозное шифрование credentials.
  Пользователь выбрал скрыть открытый GHCR-токен от daemon. Для этих credentials
  прежнее доверие daemon как обработчику открытых Secrets не применяется.
  Для первой версии выбран доступ container runtime к GHCR через конфигурацию
  registry на узле (`/etc/rancher/k3s/registries.yaml`), без Kubernetes Secret с токеном.
  Получатель credentials — доверенная часть узла, недоступная daemon. Для первой
  версии CLI передаёт токен непосредственно через SSH с проверкой ключа сервера,
  скрытым вводом/stdin, без значения в аргументах команд и логах. На узле credentials
  хранятся в конфигурации `root:root`, режим `0600`, в каталоге, недоступном daemon
  для записи, без прикладного шифрования файла. Это согласованное упрощение;
  root узла остаётся доверенной стороной, защита от чтения диска не заявляется.
  CLI выполняет доверенную подготовку узла и Namespace через SSH; daemon работает
  внутри k3s с отдельным ServiceAccount и управляет только необходимыми ресурсами
  в подготовленных Namespace приложений. Он не получает SSH-ключ, sudo,
  административный kubeconfig, права изменения Namespace, RBAC/admission-защиты,
  системных workloads и собственного развёртывания, создания произвольных PV,
  доступа nodes/proxy, impersonation или выдачи себе дополнительных полномочий.
  Во всех Namespace, где daemon создаёт workloads, кластер независимо применяет
  Pod Security Restricted в режиме enforce; daemon не может изменить настройки
  или получить исключение. Проверка daemon дополняет эту защиту ранней диагностикой.
  Создание Namespace и начальных прав выполняется доверенным этапом CLI до
  передачи управления daemon. Общий root/SSH-доступ daemon не выдаётся.
  Узкая операция настройки GHCR принимает username и токен через stdin, меняет
  только ghcr.io в фиксированном файле, сохраняет root:root 0600, не возвращает
  credentials и не принимает произвольные команды/пути.
  Для registry выбран один root-owned helper с фиксированными действиями
  `set-ghcr`, `apply-registry`, `status`. Пользователь paas получает ограниченный
  NOPASSWD только на эти точные вызовы без wildcard; helper и каталог установки
  недоступны ему для записи. Отдельные права на shell, редактор, tee или произвольный
  systemctl не выдаются. Права первоначальной установки определяются отдельно.
  `set-ghcr` проверяет вход и существующий YAML; некорректный файл не заменяется.
  Меняется только auth ghcr.io с сохранением остальных registry/mirrors/TLS-настроек.
  Запись атомарная, root:root 0600; хранится одна предыдущая версия с такой же защитой.
  Параллельные изменения сериализуются, повтор тех же настроек сам по себе не требует
  нового перезапуска. Сохранение даёт статус «требуется применение» без рестарта.
  `apply-registry` по явному выбору оператора перезапускает только службу k3s
  и проверяет готовность. При ошибке нет циклов автоматических рестартов/откатов;
  показывается фактическое состояние и сохраняется предыдущая конфигурация.
  `status` не раскрывает credentials. Готовность k3s и проверка скачивания выбранного
  приватного образа учитываются отдельно; cache не подтверждает доступ к registry.
  Явное восстановление предыдущей конфигурации ещё требует уточнения своего вызова.
  Этот доступ не обеспечивает автоматического разграничения
  скачивания образов по приложениям. Шифрование только передачи не закрывает доступ
  через чтение Kubernetes Secret или создание workload, монтирующего его;
  такой путь не считается выполнением требования. TLS и шифрование Secrets
  в хранилище сами по себе не считаются согласованным механизмом этой защиты.
- Будущий переход на `imagePullSecrets` с отдельным доверенным получателем,
  независимыми ограничениями чтения/монтирования и защитой от обхода daemon
  обязателен как дальнейшая задача PAAS-010 в `docs/backlog/paas.md`.
  В первой версии этот механизм не реализуется; архитектура будущего этапа
  требует отдельного согласования. Абстракции для двух механизмов заранее не вводятся.
- Усиление хранения вынесено в PAAS-011: шифрование сохранённых credentials и копий,
  управление ключами и минимизация открытых копий в памяти. PAAS-010 может закрыть
  эту задачу только при выполнении её критериев; второй механизм не дублируется.
  Для временной обработки секретов в Go выбран `runtime/secret` там, где применим;
  перед реализацией проверяются выбранный toolchain и экспериментальная сборка
  `GOEXPERIMENT=runtimesecret`. Пакет очищает временную память, не шифрует файлы;
  поддерживает Linux amd64/arm64, на macOS дополнительная защита не заявляется.
  Он не заменяет защиту канала, прав доступа и хранения и не требует новой зависимости.
- Продукт `0.x.x` поддерживает одну ноду; `1.0.0`/`1.x.x` требует мультинод.
- Автоматическое версионирование нужно в каждом репозитории. Только для `0.x.x`: minor
  по умолчанию, patch по `fix:`, minor по `!` или `BREAKING CHANGE:`. Переход на
  `1.0.0` согласуется отдельно после готовности мультинода. В `1.x.x` API проектировать
  с обратной совместимостью; правило bump для `0.x.x` на него не распространяется.
  Политика записана в AGENTS.md.
- Установка PaaS включает установку k3s на выбранном сервере, если его ещё нет.
- Первоначальная установка выполняется через SSH с компьютера оператора.
- SSH-подключения PaaS выполняются отдельным Linux-пользователем `paas`.
- Основной пользовательский интерфейс `paas-ctl` — интерактивный TUI.
- Нужен вспомогательный скрипт для отдельного ключа PaaS с возможностью отзыва
  без отключения основного ключа оператора.
- PostgreSQL нужен сразу для состояния control plane; этот же экземпляр
  переиспользуется через отдельные логические БД приложений.
- БД приложения, роли приложения/мигратора и credentials создаются только при
  наличии мигратора в конфигурации этого приложения. Служебная БД самой PaaS
  обязательна независимо от конфигураций приложений. При первом деплое мигратор
  запускается автоматически до старта компонентов; при ошибке они не запускаются.
  При последующих деплоях запуск миграции выбирается явно через TUI/флаги CLI.
- Для приложения создаётся отдельный пользователь PostgreSQL с именем приложения;
  общий пользователь всех приложений не подходит для изоляции и учёта обращений.
- Мигратор получает отдельного пользователя с правами изменения структуры своей
  выделенной схемы и SELECT/INSERT/UPDATE/DELETE для преобразования данных.
- Приложение получает SELECT/INSERT/UPDATE/DELETE без TRUNCATE, владения объектами,
  изменения постоянной структуры, SUPERUSER, CREATEDB и CREATEROLE.
- Удаление мигратора из конфигурации прекращает его последующие запуски, но сохраняет
  существующие БД, роли, credentials и доступ приложения. Удаление БД и отзыв доступа
  выполняются отдельными явными операциями PaaS; их подробный контракт ещё открыт.
- Credentials автоматически генерируются, хранятся в Kubernetes Secrets
  и могут быть явно получены оператором через CLI.
- Дополнительная инфраструктура поднимается при первом запросе, версия задаётся
  в конфигурации платформы. Kafka пока не нужна.
- Общий сервис объявляется один раз на уровне платформы; владелец явно выбирает,
  каким приложениям разрешено подключаться. По умолчанию доступ закрыт. Сервис
  обновляется независимо от приложений-потребителей. Примеры назначения сервиса:
  аутентификация, медиа или аналитика; конкретный набор не фиксируется.
- Каждое приложение и каждый общий сервис получают отдельный Kubernetes Namespace.
  PaaS задаёт NetworkPolicy так, чтобы разрешённые связи работали, а невыбранные
  приложения не могли подключиться.
- Приложение — группа независимо выпускаемых компонентов: API, frontend, worker,
  processor, scraper и другие роли. После первоначальной подготовки мигратор
  может запускаться отдельно.
- На старте компоненты, которым нужна БД, используют общую БД и пользователя
  приложения без прав создания, изменения или удаления таблиц/полей. Будущая задача — выдавать компонентам отдельные роли с минимальными
  правами только на требуемые таблицы.
- Основа мигратора — папка SQL и шаблон образа; собственный Go-мигратор не выбран.
- Окружения отложены; квоты рассматриваются в будущем.

### Сетевая модель — согласована пользователем, детали открыты

- Между разными приложениями сетевой доступ закрыт по умолчанию;
  необходимые связи разрешаются явно через PaaS у компонента-источника
  к Service целевого приложения. Встречное разрешение получателя не требуется;
  обратное инициирование соединения требует своего разрешения. Ответный трафик
  разрешённого соединения не является обратным инициированием.
- Компоненты одного приложения могут свободно обращаться друг к другу по сети.
  Точная схема переключателя внутриприкладной связи ещё уточняется.
- Внешний доступ задаётся отдельно для каждого компонента: none (по умолчанию),
  allowlist или all. Allowlist содержит точные домены без портов; разрешены все
  порты указанного домена, включая подключения к почтовым сервисам.
  Имя совпадает точно: example.com не разрешает api.example.com; поддомены
  добавляются отдельными записями. Маски, включая *.example.com, не поддерживаются.
  All разрешает весь внешний интернет, но не даёт этим разрешением доступ
  к внутренним адресам платформы/узла и Kubernetes API.
  Механизм исполнения списка, DNS/IP-сопоставления и защита от прямого IP-обхода
  отложены пользователем в PAAS-012 и не блокируют дальнейшее обсуждение SDD.
  Список сохраняет целевые требования, но до исполнения/проверки не считается
  гарантией сетевого запрета. Временное поведение первой реализации требует
  отдельного согласования; молчаливая замена allowlist на all не разрешена.
  Служебные исключения открыты.
- Мигратор имеет только DNS и доступ к целевой PostgreSQL, без доступа
  к компонентам/другим приложениям и внешним API. Разрешения обычных компонентов
  и режим all он не наследует. Служебные соединения Traefik/ACME и общей
  инфраструктуры уточняются отдельно от профиля приложений.
- Эти решения не разрешают реализацию платформы и не закрывают пункт 1.1.

### Согласовано архитектором в рамках делегирования пользователя

Пользователь разрешил три последовательных круга SDD-ревью с продолжением после
согласования архитектором GPT-6 Astra low; это не разрешение реализации платформы.

- Круг 1/3: пользовательский Ingress содержит один host и один path; несколько
  Ingress в пакете допустимы без скрытого разбиения ресурсов. Разрешены явно заданные
  Prefix/Exact, регистрозависимые буквальные пути без rewrite/StripPrefix.
  DefaultBackend, backend.resource, regex-режимы, percent-encoded объявленные paths
  и обратная косая черта не поддерживаются; Kubernetes-валидация обязательна.
  Строгий Prefix Traefik включается и проверяется для закреплённой версии k3s/Traefik.
  Priority задаёт PaaS: 2*L+1 для Prefix, 2*L+2 для Exact, где L — байтовая UTF-8
  длина пути; у Prefix игнорируется завершающий slash, кроме корня. Проверяется
  переполнение и предел 2147482647. Иные пользовательские priority/matcher/rule syntax/
  middleware отклоняются. Более длинный подходящий путь выигрывает.
  Вложение разрешено, дубликаты и одинаковые host/path у Exact и Prefix запрещены;
  Prefix сравнивается без завершающего slash, Exact буквально. Проверяются текущие,
  сохранённые и незавершённые маршруты всего приложения; update исключает собственную
  прежнюю запись, а сбой не освобождает её до установления результата Kubernetes.
  Backend — TCP-порт Service своего компонента/Namespace из пакета или состояния;
  проверяется результирующий Service, включая сохранённые Ingress вне пакета.
  Атомарность переключения трафика не обещается; encoded request-target и штатная
  очистка пути Traefik требуют проверки выбранной версии, не собственного URL-decoding.
- Круг 2/3: домены канонизируются одинаково при регистрации, в rules.host и TLS hosts:
  ASCII lowercase и удаление одной завершающей DNS-точки, затем проверка DNS labels
  (не более 63 символов каждый, 253 всё имя, минимум два labels). Unicode, пробелы,
  URL/порт/путь/credentials, wildcard, IP, localhost и .localhost отклоняются.
  Punycode принимается только как корректный обратимый IDNA A-label; для реализации
  используется готовый строгий профиль golang.org/x/net/idna, без собственного кодека
  и без изменения зависимостей на этапе SDD. Канонизация не подтверждает DNS/владение.
  Ingress class берётся из профиля; TLS — одна запись с единственным каноническим
  host без непустого secretName. PaaS включает TLS через router.tls и задаёт HTTPS
  entrypoint/resolver. Разрешены только точные ожидаемые строковые annotations
  router.priority/entrypoints/tls/tls.certresolver; другие входные Ingress annotations
  и непустые Service annotations отклоняются. Живые annotations доверенных контроллеров
  этим правилом не удаляются и обратно в пользовательский пакет не копируются.
  Для используемого Ingress TCP-порта Service запрещены port 443 и имя https*;
  targetPort 443 не запрещён сам по себе. Backend обслуживает HTTP; внутренние
  HTTPS/h2c/ServersTransport вне первого профиля.
- Круг 3/3: один активный ACME resolver с явными HTTPS CA directory endpoint,
  email и приватным постоянным storage; только HTTP-01. Опубликованные DNS A/AAAA
  должны вести на ожидаемые публичные адреса узла; требуются входящие TCP80/443,
  DNS-разрешение и исходящий HTTPS к CA. HTTP redirect штатный, встроенный solver
  обслуживает HTTP-01 с allowACMEByPass=false. Объявление самого challenge path
  и путей внутри него запрещено, широкие Prefix / и /.well-known разрешены.
  Приоритет solver проверяется на закреплённой версии; нет HTTP fallback к backend.
  SNI strict не добавляется: до выпуска может предъявляться default certificate,
  который не считается готовым или доверенным.
  TLS PENDING/READY/ERROR отделён от Deployment/БД/backend readiness. Внешний paas-ctl
  проверяет DNS к ожидаемому узлу и TLS с правильным SNI, доверенной цепочкой,
  SAN/hostname и сроком; результат содержит checkedAt и срок сертификата. Старый
  результат показывается со временем, без обещания непрерывной доступности.
  Точную ACME-причину не выводим из одного неуспешного TLS probe или парсинга логов.
  Ошибка renewal не удаляет state/действующий сертификат и не откатывает Deployment/БД;
  показывается известная диагностика, срок и предупреждение об истечении. После
  неуспешной новой проверки прежний READY не сохраняется. Повторы первичного выпуска
  ограничены подтверждённым поведением версии; явная проверка/контролируемый restart
  Traefik со state описываются для неустранившейся ошибки.
  Staging проверяется первым, не считается production READY и не добавляет тестовые
  корни в системное доверие. Переход CA явный; state staging/production в отдельных
  файлах одного приватного PVC, один активный resolver. Один writer обеспечивается
  также при upgrade (Recreate или эквивалент); replicas=1/RWO сами этого не доказывают.
  Zero-downtime не обещается. Первое пустое state отличается от утраты существовавшего;
  при потере/повреждении/недоступности требуется восстановление или явный перевыпуск,
  а не молчаливый старт с пустым файлом. Backup/restore до эксплуатации проверяются
  при остановленном writer; место копии и механизм выбираются на инфраструктурном этапе.
  Удаление/перенос домена проверяет все сохранённые маршруты и резервы; занятый домен
  не освобождается. Удаление регистрации не обещает удаления/остановки renewal
  сертификата; работающий acme.json для очистки не редактируется.

### Предлагаемая техническая реализация — требует согласования

- `paas-common`: контракты и generated transport; `paas-ctl`: команды оператора;
  `paas-daemon`: состояние и выполнение операций.
- TUI в `paas-ctl` вызывает те же операции установки и API управления;
  бизнесовая логика daemon не дублируется в экранах.
- Предлагаемые экраны: серверы и установка, приложения/компоненты, деплой,
  миграции, статус и логи операций, явное получение credentials.
- Библиотека TUI и точная структура экранов ещё не выбраны; новый веб-интерфейс
  для первой версии не требуется.
- Предлагаемый скрипт `paas-ctl/scripts/ssh-key.sh` использует штатные OpenSSH
  `ssh-keygen` и `ssh`; собственная реализация SSH не требуется.
- Предлагается отдельная пара Ed25519 для каждого сервера в `~/.ssh/paas/`;
  существующий ключ не перезаписывается. Passphrase вводится средствами OpenSSH,
  для повторного использования допускается ssh-agent; значения не сохраняются в конфигурации PaaS.
- Первичное добавление публичного ключа выполняется через текущий административный
  доступ. Приватная часть остаётся у оператора; сохраняется только путь к ней.
- Тем же административным доступом скрипт создаёт пользователя `paas`, если его нет,
  и устанавливает ключ в его разрешённые ключи. Существующая учётная запись
  проверяется и переиспользуется без удаления данных и чужих ключей.
- Для registry права sudo пользователя `paas` ограничены согласованными действиями
  helper; права установки и подготовки Namespace ещё требуют согласования.
  Выбор отдельного пользователя не означает выдачу `NOPASSWD: ALL`.
- Подключение PaaS выбирает отдельную identity; проверка не использует другие
  identity, пароль или существующий multiplexed connection. Host key проверяется.
- Отзыв выполняется через независимый административный доступ: удалить точную
  запись ключа, определяемую по публичному материалу/fingerprint, а не только комментарию;
  остальные ключи и права файлов сохраняются.
- Сам отзыв ключа блокирует новые SSH-аутентификации. Закрытие уже открытых сессий
  и отзыв отдельно выданных API-токенов или kubeconfig — другие операции.
- Для k3s использовать Kubernetes API; обычный Kubernetes рассматривать
  как следующую целевую конфигурацию, а не заранее отдельную систему адаптеров.
- Установщик проверяет сервер и наличие k3s; при отсутствии устанавливает
  закреплённую версию, при наличии проверяет доступность и совместимость.
- Недоступность API или отсутствие kubeconfig не доказывают отсутствие k3s;
  существующий кластер не переустанавливается и не обновляется автоматически.
- Последовательность установки: готовый k3s → PostgreSQL → служебная БД и Secrets
  → daemon. PostgreSQL состояния PaaS не становится обязательным datastore самого k3s,
  чтобы не создавать циклическую зависимость запуска.
- Первоначальную установку PostgreSQL и служебных Secrets выполнять до запуска
  daemon, которому уже требуется собственная БД.
- Владельцем БД оставить служебную сторону; мигратору выдать владение выделенной
  схемой и её объектами. Бизнесовый пользователь не владеет этими объектами.
- Настроить доступ к новым таблицам/sequences через default privileges роли мигратора;
  закрыть лишние права PUBLIC и подключения к чужим/служебным БД.
- Отдельные Secrets приложения и мигратора; значения не дублируются в состоянии daemon.
- Включить шифрование Secrets в хранилище k3s и ограничить доступ через RBAC.
- Сборку образа мигратора выполнять локально или в CI.
- Привязку credentials определяет явная операция миграции приложения;
  произвольная метка контейнера не выдаёт повышенные права.
- Запуски миграций одной БД сериализуются; инструмент учитывает историю применений.
- Повторные операции сохраняют ресурсы и пароли; частично выполненная подготовка
  восстанавливается без выдачи приложению неполностью настроенного доступа.
- Обычный деплой не меняет версии общих сервисов; их обновление — отдельная операция.
- Удаление приложения по умолчанию сохраняет данные; удаление БД и смена пароля
  требуют отдельных явно выбранных операций.

### Граница следующего обсуждения

- Этот change фиксирует основу; формат API/описания приложения пока не утверждён.
- Принято использовать Kubernetes-манифесты как вход деплоя; способ доставки,
  правила формирования имени выделяемого Namespace и контракт PaaS-метаданных
  ещё открыты. Приложение и компонент выбираются в операции деплоя;
  Namespace ресурса определяется приложением
  операции деплоя. Изоляция строится на отдельных Namespace и
  NetworkPolicy для явного списка разрешённых потребителей.
- Требуется уточнить реестр защищённых объектов/полей, допустимые значения и
  диагностику WARN/отказа. Хранение ожидаемых значений и использование hash пока
  не определены; механизм не должен доверять копии или hash из пользовательского YAML.
- Мигратор и его Secret размещаются в Namespace приложения; штатные изменения идут
  через PaaS. Виды пользовательских манифестов выбраны; требуется уточнить все
  проверяемые пути ссылок на credentials/ServiceAccount и точную матрицу
  Kubernetes-прав обычных workloads.
- Traefik и встроенный ACME выбраны; принадлежность доменов приложению согласована.
  Профиль маршрутов согласован в круге 1; канонизация host и class/TLS/annotations —
  в круге 2; HTTP-01 и жизненный цикл HTTPS — в круге 3. Конкретные закреплённые
  версии, значения профиля CA/email/entrypoints, backend постоянного тома и место/
  механизм backup/restore выбираются и проверяются на инфраструктурном этапе.
  Постоянный том инфраструктуры не означает согласование пользовательских PVC.
  Несколько экземпляров Traefik и HA сертификатов относятся к будущему согласованию;
  текущее решение не предполагает совместный доступ реплик к одному `acme.json`.
- Мультинод и HA не отождествляются; требования будущей реализации отдельны.
- Release-аудит по локальным файлам: SDK содержит caller и release-конфиги;
  ctl/daemon содержат только reusable workflow и скрипт генерации callers.
  Политика minor по умолчанию в существующем SDK-конфиге не настроена.
- Для `0.x.x` breaking change повышает minor, а автоматический переход на `1.0.0`
  запрещён. Начиная с `1.0.0`, API проектировать с обратной совместимостью.
- Модель приложения, общая БД/роль его компонентов и доступ к общим сервисам только
  для явно выбранных приложений согласованы. Способ задания разрешённого списка
  (например, селектор или метка) и контракт подключения остаются открытыми.
- Перед соответствующими этапами нужно отдельно выбрать способ установки,
  аутентификацию оператора, SQL-инструмент и состав мониторинга.
- SSH-установка и отдельный пользователь `paas` согласованы;
  отдельно нужно определить sudo для установки и подготовки Namespace,
  а также вызов явного восстановления registry-конфигурации.
- TUI согласован; библиотека и компоновка экранов выбираются перед его реализацией.
- Профиль SELECT/INSERT/UPDATE/DELETE приложения без TRUNCATE и преобразование
  данных мигратором согласованы; точные SQL grants проверяются на этапе реализации.
- Удаление мигратора сохраняет уже созданные БД, роли, credentials и доступ;
  подробный контракт отдельных операций удаления БД и отзыва доступа ещё открыт.
- Требуется определить флаги последующих миграций, сохранение результата первой
  подготовки при сбоях daemon и добавление мигратора уже развёрнутому приложению.
- Получение секрета является требованием; произвольный доступ всех пользователей CLI
  к секретам не подразумевается.

## Risks / Trade-offs

- Прямые изменения управляемых ресурсов через Kubernetes API могут рассинхронизировать
  состояние daemon и кластера → штатные операции выполняются через PaaS;
  документация рекомендует избегать обхода. Автоматическое восстановление пока
  не определено и не считается гарантией этой модели.
- Общий PostgreSQL означает общий отказ и общие ресурсы → отдельные пользователи
  изолируют доступ, а резервное копирование, ограничения и мониторинг проектируются явно.
- Разные пользователи дают атрибуцию, но сами не собирают метрики и не вводят квоты
  → отдельные задачи PAAS-002 и PAAS-003.
- Утечка credentials мигратора позволяет менять его схему → отдельный Secret,
  выдача только задаче миграции, отсутствие credentials в образе и логах.
- Независимые миграции могут сломать старый backend → совместимые изменения схемы;
  автоматический откат образа не означает обратную миграцию БД.
- Потеря кластера может означать потерю Secrets → резервное копирование
  PostgreSQL, секретов и необходимых ключей восстановления.
- Обновление packages-go может потребовать регенерации → закрепить совместимые
  версии и проверить generated client/server без ручного исправления generated files.
- Прерванная установка k3s или недоступный кластер → отличать отсутствие установки
  от неисправного состояния, показывать причину и не выполнять разрушительную замену.
- Потеря доступа PaaS → основной административный доступ остаётся независимым;
  отзыв проверяется новой сессией с единственным ключом PaaS.

## Migration Plan

- Сейчас сохранить и проверить документы; не менять код или установленные сервисы.
- Согласовать недостающие контракты и архитектуру выбранного этапа.
- Подготовить обновление SDK и проверку Flux; затем двигаться по этапам tasks.md.
- При замене Compose-полей явно согласовать несовместимость API.
- Основные specs синхронизировать и change архивировать только после реализации
  согласованного объёма и проверок; статус документов не равен готовности платформы.
