# Design

## Context

- Статус: архитектура платформы согласована частично; этап переименования выполнен,
  штатное управление через PaaS и мигратор в Namespace приложения согласованы.
  Согласованные SDK-этапы и транспортное ядро завершены; итоговая архитектура
  платформы и следующие runtime-этапы отдельно согласуются.
- Мотивация и границы репозиториев: [proposal.md](proposal.md).
- `paas-ctl` и `paas-daemon` содержат исполняемое транспортное ядро с тестами;
  `paas-common` содержит исходные API, generated SDK и явные валидаторы.
- Makefile генерирует common и PaaS HTTP/OpenAPI preview/apply/get, каталог
  приложений/компонентов и список операций.
  Старые apps/logs с Compose-полями остаются неподключёнными черновиками.
- В pkg/http/paas/validation доступны явные context-free проверки согласованных
  DTO: envelope/Diagnostic, public Plan/preview, Operation/ErrorResponse,
  catalog query/summary/page и operation list query/page.
  Они не подключаются generated handlers автоматически и не реализуют runtime;
  границы и результаты следующего четырёхшагового цикла записаны в tasks.md.
- SDK-объём уточнён в delta spec independent-deployments отдельным требованием
  «SDK предоставляет явные проверки семантики DTO без runtime». Tasks разделяет
  2.3.1, 2.3.2 и открытый 2.3.3; соответствие коду/тестам проверяется по матрице
  в sdk-semantic-check-2026-10-20.md. Открытый каталог ошибок не закрывается
  context-free валидатором; семантика blocker ID для неизвестного code остаётся сервису.
- Этап 2.2 выполнен с packages-go `v0.3.0`; согласованный подэтап 2026-10-24
  обновляет runtime к merged commit PR #13, Flux к v0.4.0 и Go к 1.27.3.
  Common gRPC/proto сохраняются.
- Flux v0.4.0 поддерживает path-параметры. Активный PaaS entrypoint продолжает
  использовать static paths/query/body; `/apps/{name}` и `/apps/{app_name}/logs`
  относятся к неподключённым Compose-черновикам. Их миграция и подключение
  в подэтап 2026-10-24 не входят.
- Существующий `common/migration.yaml` описывает Up/Down API;
  это не реализация отдельного контейнера мигратора.

## Goals / Non-Goals

**Goals:**

- Зафиксировать подтверждённые требования и проверяемые границы первой версии.
- Переиспользовать один PostgreSQL, сохраняя разные БД и пользователей приложений.
- Независимо управлять версиями компонентов и запусками миграций.
- Использовать Flux и packages-go по их назначению.

**Non-Goals:**

- Реализация кода в текущем документальном этапе.
- Окружения, квоты БД, Kafka, Compose и Swarm в первой реализации.
- Обязательный Vault, общий релиз frontend/backend и автоматические миграции при каждом последующем деплое.
- Мультинод в `0.x.x`; он относится к будущему этапу продукта `1.0.0`/`1.x.x`.

## Decisions

### Подтверждено пользователем

- Профиль первого нового PaaS SDK согласован 2026-10-19: источник — Flux spec
  (YAML в DSL Flux), из него Flux генерирует Go HTTP client/server и OpenAPI.
  Собственный API использует статические пути, query-параметры для идентификаторов
  и фильтров, JSON-body для команд. Новый proto/gRPC-профиль отложен;
  существующие common gRPC-артефакты сохраняются. Generated-файлы вручную не
  редактируются. Path-поддержка Flux не требуется для этой формы собственного API;
  профиль GitHub-импорта остаётся отдельным решением. Согласование профиля не
  утверждает точные URL/DTO, обновление зависимостей или реализацию SDK.
- Репозиторий называется `paas-common`: контракты, сгенерированные SDK-артефакты
  и общие определения PaaS. Локальный каталог и module path переименованы;
  OpenSpec и backlog находятся внутри него. GitHub-репозиторий переименован в
  `dkoshenkov/paas-common`; origin указывает на `git@github.com:dkoshenkov/paas-common.git`.
- Начинаем с k3s вместо Docker Compose.
- В первой версии внешний HTTP/HTTPS-трафик обслуживает один экземпляр встроенного
  Traefik k3s. Он получает и продлевает управляемые сертификаты через ACME;
  Caddy и отдельный сервис продления не нужны. Состояние ACME (`acme.json`, включая
  ключи и сертификаты) сохраняется на постоянном томе и защищается от доступа
  обычных workloads. Пересоздание Pod не должно терять это состояние.
  Настройка встроенного Traefik выполняется через `HelmChartConfig`.
- Домены явно регистрируются за приложением через CLI/TUI. Один домен принадлежит
  одному приложению; приложение может иметь несколько доменов. Host в YAML не
  регистрирует домен и не подтверждает право на него. Компоненты приложения могут
  использовать его домены с разными путями по согласованному ниже профилю маршрутов.
  Ingress принимает только явные доменные имена своего приложения;
  чужой/незарегистрированный host, wildcard и правило без host отклоняются до
  применения пакета. Смена и удаление регистрации домена — отдельные операции PaaS;
  отсутствие Ingress в пакете не удаляет регистрацию. Регистрация внутри PaaS
  не заменяет настройку DNS и подтверждение домена центром сертификации.
- Входной формат начального деплоя — обычные Kubernetes-манифесты. Это нативный
  формат k3s/Kubernetes; будущие адаптеры Compose или Swarm потребуют отдельного
  способа описания или преобразования.
- В первой версии пользовательский пакет содержит только `apps/v1 Deployment`,
  `v1 Service` типа `ClusterIP`, `v1 ConfigMap` и `networking.k8s.io/v1 Ingress`.
  Deployment описывает компоненты, Service — их внутренние адреса и порты,
  ConfigMap — несекретные настройки, Ingress — домены, пути и целевые Services.
  PaaS проверяет принадлежность домена и backend приложения и управляет выбором
  Traefik и ACME resolver; правила Ingress уточнены в трёх делегированных кругах
  ниже. Остальные защищённые поля остаются частью открытого пункта 1.1.
  Неподдерживаемый тип отклоняется до начала применения всего пакета.
  Namespace, служебные Secrets, ServiceAccount/RBAC, NetworkPolicy, Job мигратора
  и постоянные тома инфраструктуры создаёт PaaS. Пользовательские Job, CronJob,
  StatefulSet, PVC и другие типы пока не поддерживаются.
- Namespace определяется приложением, выбранным в операции деплоя. Отсутствующий
  `metadata.namespace` заполняется PaaS, совпадающий принимается; любое другое
  значение, включая `default`, отклоняется до применения пакета с указанием поля
  и ожидаемого Namespace. WARN и замена явно чужого Namespace не применяются.
- Пользователь задаёт стабильное `metadata.name`; отсутствие имени и `generateName`
  не поддерживаются. Идентичность ресурса — API group, тип ресурса, Namespace и имя;
  версия API не входит в идентичность. PaaS учитывает принадлежность ресурса
  приложению в своём состоянии; метка в пользовательском YAML её не подтверждает.
  Повторный деплой обновляет тот же ресурс в пределах разрешённых полей.
  Конфликт со служебным ресурсом, другим владельцем или объектом вне учёта PaaS
  отклоняется без автоматического присвоения. Дубликаты идентичности в одном
  пакете отклоняются до применения. Новое имя означает новый ресурс и не удаляет
  прежний; переименование и удаление требуют явной операции.
- Оператор выбирает приложение и компонент в операции деплоя; один пакет относится
  к одному компоненту и содержит ровно один Deployment. Несколько контейнеров этого
  Deployment выпускаются вместе; независимо выпускаемые части — отдельные компоненты.
  Service, ConfigMap и Ingress включаются по необходимости. Каждый пользовательский
  ресурс принадлежит одному компоненту; daemon сохраняет привязку в состоянии PaaS,
  а пользовательская метка не переносит ресурс к другому владельцу.
  Service выбирает Pods Deployment своего компонента, Ingress указывает его Service,
  пользовательские ConfigMap используются только его контейнерами. Общие пользовательские
  ConfigMap между компонентами не поддерживаются; служебные подключения к БД и общим
  сервисам выдаёт PaaS отдельно. Деплой меняет только ресурсы выбранного компонента;
  отсутствие прежнего ресурса в новом пакете не удаляет его автоматически.
- Метки идентичности: `app.kubernetes.io/part-of` — стабильный ID приложения,
  `app.kubernetes.io/component` — стабильный ID компонента,
  `app.kubernetes.io/instance` — стабильный ID экземпляра компонента, представленного
  конкретным Deployment. На Deployment и его Pod template ставятся все три;
  на Service, ConfigMap и Ingress — ID приложения и компонента. Все эти ресурсы
  и Pod template получают информационную метку `app.kubernetes.io/managed-by=paas`.
  Deployment selector и selector каждого Service текущего пакета — ровно три
  метки идентичности Deployment этого пакета, без дополнительных условий.
  Пропущенные ключи меток заполняются, заданные проверяются; отсутствующий или пустой
  selector генерируется, непустой должен совпасть целиком, включая отсутствие
  непустого `matchExpressions`. Конфликты отклоняются до применения пакета;
  только неверный `managed-by` исправляется с WARN после проверки владения.
  Описательные метки свободны, кроме служебных ключей и системных меток контроллеров;
  они не подтверждают владение и не выдают полномочия. Все ID непустые, стабильные,
  соответствуют формату Kubernetes labels и не зависят от отображаемых имён/релиза.
- Намерение создания, идентичность, владелец и стабильный ID ресурса сохраняются
  до изменений Kubernetes. Повтор операции после сбоя использует те же записи и ID;
  это не разрешает присвоить произвольный неизвестный объект. Параллельные операции
  одного компонента сериализуются либо явно отклоняются как конфликтующие.
  Старый Service вне пакета сохраняет прежнюю привязку; для переключения его включают
  в новый пакет. Мигратор не получает `app.kubernetes.io/instance` Deployment.
  Проверка пакета до применения не означает транзакционного применения Kubernetes;
  частичный результат требует повтора с сохранёнными ID.
- Формат доставки манифестов одобрен GPT-6 Astra (reasoning low) 2026-10-19
  по запросу пользователя с условным разрешением продолжить после одобрения:
  JSON-body с `app_id`, `component_id` и непустым `files: [{name, content}]`.
  `content` — исходный YAML без интерполяции и клиентского преобразования объектов
  в JSON; файл может содержать несколько YAML-документов. Один непустой документ
  представляет один поддерживаемый объект; массивы и Kubernetes List отклоняются.
  Пустые документы пропускаются; весь пакет обязан содержать ровно один Deployment.
  Ошибка любого документа отклоняет пакет до начала применения.
  `name` — только диагностическая метка: daemon не выполняет по ней файловых
  операций, не загружает URL и не определяет идентичность/владельца ресурса.
  Имена непустые, уникальные, ограничены по длине, без управляющих символов;
  отображение в терминале безопасно. CLI передаёт basename одиночного файла или
  относительное имя файла каталога. Порядок файлов не задаёт порядок применения.
  Ошибки адресуются именем файла и номером YAML-документа с 1, с путём поля,
  когда применим; для синтаксической ошибки допустимы строка/столбец парсера.
  Daemon ограничивает JSON body на проводе с учётом escaping, число файлов и
  документов, длину имён и сложность разбора YAML (глубина/aliases); превышение
  отклоняется до применения. Числа лимитов согласованы ниже;
  DTO диагностики согласован ниже. Полный пакет не выводится в обычные логи.
  Проверка и подтверждение относятся к одному снимку: CLI не перечитывает файлы
  незаметно перед запуском. Изменение входа требует новой проверки/подтверждения;
  daemon перед применением повторно проверяет актуальные ограничения.
  Связь preview/apply согласована ниже; рекурсивность обхода каталога и symlink
  остаются для следующих контрактов. PaaS-метаданные для БД, Secrets и разрешённых
  связей пока не выбраны. Ревью формата не означает проверки generated DTO или
  одобрения реализации SDK/платформы.
- Строгое ревью GPT-6 Astra (reasoning low) 2026-10-19 одобрило связь
  preview/confirm/apply по условному разрешению пользователя продолжить после
  одобрения. `POST /deployments/preview` сохраняет неизменяемые вход, план,
  диагностику, время создания и истечения в существующем control-plane PostgreSQL.
  При ошибках применимого preview_id нет. Preview не меняет Kubernetes,
  не запускает миграции, не присваивает ownership и не занимает компонент/маршруты;
  новые внутренние ID в плане — символические либо только кандидаты.
  `POST /deployments/apply` принимает preview_id: он обозначает максимум одну
  операцию за весь жизненный цикл. Принятие атомарно связывает preview с операцией,
  занимает компонент и фиксирует намерения/резервы; до commit Kubernetes не меняется.
  Защита от гонок охватывает все читаемые политики PaaS, домены и маршруты
  приложения, а не только компонент. Конфликт с другой активной операцией
  возвращает её ID без очереди. Повтор/конкурентный apply того же preview возвращает
  прежний operation_id даже после потери ответа, ошибки выполнения или restart.
  Без сохранённой связи при недоступной БД выполнение не начинается.
  Перед принятием заново строится план; правила сравнения перечислены в
  independent-deployments. Изменение подтверждаемого плана требует нового preview
  и подтверждения; произвольное понятие «несущественного изменения» не используется.
  TTL отклоняет новый apply неиспользованного preview, но не поиск уже связанной
  операции. Истёкшие неиспользованные снимки удаляются; вход незавершённой операции
  сохраняется для восстановления. Связь preview → operation хранится минимум вместе
  с историей операции; старый ID после удаления истории не становится применимым.
  Хранилище preview имеет конечные пределы числа и суммарного объёма снимков.
  Restart не сбрасывает operation_id, вход, ID ресурсов, намерения и резервы.
  Неизвестный результат Kubernetes-запроса сверяется с кластером до безопасного
  продолжения; невозможность продолжить явно требует восстановления с сохранением
  опасных резервов. Мутация проверяет UID/версию или эквивалентные условия владения;
  чужой появившийся объект не присваивается. Транзакция PostgreSQL не означает
  транзакцию Kubernetes: возможны частичный результат и остановка без смены плана.
  `GET /operations/get?operation_id=...` возвращает сохранённые ID, состояние, этап
  и безопасную диагностику. Состояния различают принятие/выполнение/завершение,
  успех/ошибку и неизвестный/частичный результат с необходимостью восстановления.
  Ошибка не означает отсутствие изменений. YAML считается потенциально
  чувствительным: обычные preview/operation/logs не раскрывают body, значения
  env/ConfigMap или сырой diff; план показывает ресурсы, действия и пути полей.
  Доступ к снимкам имеет только доверенный daemon/административный контур.
  Перечень stages, SQL-блокировки, ёмкость активных операций и лимиты безопасной
  диагностики уточняются до реализации; TTL/хранение снимков согласованы ниже.
  Очередь, отмена, автоматический rollback/повтор и streaming не входят в эту схему.
  Одобрение не разрешает реализацию SDK/платформы и не закрывает пункт 1.1.
- Строгое ревью GPT-6 Astra (reasoning low) 2026-10-19 по условному разрешению
  пользователя одобрило пять state: ACCEPTED, RUNNING, SUCCEEDED, FAILED,
  RECOVERY_REQUIRED. Таблица переходов и инварианты закреплены в
  independent-deployments. SUCCEEDED/FAILED терминальны; FAILED допустим только
  при установленных последствиях и безопасном снятии активной блокировки.
  Известный частичный результат допускает FAILED; неизвестный или небезопасный —
  RECOVERY_REQUIRED с сохранением необходимых блокировок/резервов.
  Терминальность не снимает ownership ресурсов и занятых ими маршрутов;
  освобождаются только доказанно ненужные временные резервы согласованно с
  итоговым учётом PostgreSQL. Восстановление продолжает ту же операцию с прежним
  планом и ID, не повторяя завершившиеся миграции. Restart сам по себе не меняет
  state; недоступность API отображается отдельно. SUCCEEDED требует критериев
  конкретной операции и не подменяет отдельный production TLS READY.
  Обязательны operation_id, state, отдельный stage и безопасная диагностика;
  stage может отсутствовать до начала исполнения, после остановки это последний
  достигнутый этап. Перечень stages и readiness/таймауты
  остаются открытыми. Это документальное одобрение, не реализация.
- Пользователь согласовал единый DTO Diagnostic для preview и операций:
  обязательные severity (ERROR/WARN/INFO), стабильный code, безопасный message;
  необязательные file, document, field_path, line, column. Для ошибки конкретного
  документа file/document обязательны, нумерация document/line/column с 1.
  Диагностика передаётся массивом; code используется для машинной обработки,
  message не разбирается CLI и не раскрывает credentials/YAML/чувствительные значения.
  Это относится и к сообщениям парсера. Code различает известный частичный и
  неизвестный результат, не заменяя state. Строгое ревью Diagnostic выполнено
  в составе DTO/HTTP-контракта ниже. Остальной каталог code и лимиты сообщений
  остаются открытыми. Реализация не разрешена.
- Строгое ревью GPT-6 Astra (reasoning low) одобрило DTO/HTTP-контракт первого
  вертикального сценария; пользователь разрешил перенести уточнения в OpenSpec.
  Точный контракт закреплён в independent-deployments: preview возвращает 200
  либо с plan/preview_id/expires_at и без ERROR, либо с ERROR без этих полей.
  Ошибка сохранения даёт 503. Apply возвращает 202 при первом создании связи
  и 200 при найденной; GET — 200 при любом существующем state. Operation содержит
  неизменную цель, state, optional stage, diagnostics, created_at/updated_at и
  finished_at только и обязательно для SUCCEEDED/FAILED. Времена — RFC3339 UTC Z.
  Публичный Plan содержит resources с action CREATE/UPDATE/NO_CHANGE и JSON Pointer
  changed_fields, плюс additional_actions INITIAL_MIGRATION над app_id.
  Сравнивается полный внутренний план со значениями/зависимостями, не только
  безопасная публичная проекция. Новые дополнительные действия согласуются отдельно.
  ErrorResponse: code, message, diagnostics[], optional conflicting_operation_id
  (обязателен при COMPONENT_BUSY). Коды 409 различают COMPONENT_BUSY, PLAN_CHANGED,
  RECHECK_FAILED. 503 различает DEPENDENCY_UNAVAILABLE и ACCEPTANCE_UNKNOWN;
  неизвестный commit допускает уже созданную операцию, повторяет тот же preview_id.
  400 — некорректный envelope, 200 с ERROR — проверка содержимого пакета,
  404 — неизвестная цель/ID, 410 — ещё учтённый истёкший неиспользованный preview,
  413 — HTTP body, 503 — недоступная зависимость/неизвестное принятие.
  Diagnostic использует JSON Pointer, позиции относительно файла с 1,
  OUTCOME_KNOWN_PARTIAL/OUTCOME_UNKNOWN независимо от severity. Optional поля
  отсутствуют, не null; обязательные массивы передаются включая [].
  Текущий Flux не обещает generated/OpenAPI enum: закрытые наборы — строки с
  проверкой daemon. Унификация transport/service ErrorResponse не автоматическая:
  SDK-этап проверяет ErrorEncoder/Register…HandlersWithRuntime, включая 400/413.
  Ревью контракта было структурным; минимальный SDK реализован и проверяется
  в отдельно разрешённой части 2.3, результаты — в tasks.md.

- Штатное управление ресурсами выполняется через PaaS; пользовательские манифесты
  проходят через daemon. Документация рекомендует не обращаться к Kubernetes API
  в обход PaaS, чтобы состояние платформы и кластера оставалось согласованным.
  Прямые административные изменения находятся вне штатного сценария; механизм
  восстановления согласованности после них пока не определён.
- Служебные объекты (созданные PaaS NetworkPolicy, Secrets и полномочия мигратора)
  управляются PaaS целиком. В пользовательских workloads защищаются Namespace,
  идентификаторы, служебные метки принадлежности/доступа и ссылки на credentials.
  Эти настройки изменяются через CLI/TUI. Остальные пользовательские метки свободны.
- Для некритичного расхождения защищённого поля выводится WARN с путём поля,
  ожидаемым значением, допустимыми вариантами и способом корректного изменения;
  применяется значение PaaS. Изменения, нарушающие изоляцию, отклоняются.
- Мигратор выполняется защищённо: обычный workload не может получить его credentials
  или использовать его полномочия, включая ссылки на Secret и ServiceAccount.
  В первой версии миграционный Job и отдельный Secret мигратора находятся в Namespace
  приложения; дополнительный Namespace мигратора не требуется. Daemon проверяет
  пользовательские манифесты и создаёт Job по своему шаблону в рамках авторизованной
  операции миграции. Обычным workloads не выдаются Kubernetes-права на чтение Secret
  мигратора, создание или изменение workloads и полномочий, позволяющих обойти
  проверки daemon. Администратор кластера и daemon — доверенные стороны;
  рекомендация оператору сама по себе не заменяет этих ограничений доступа.
- Секреты выдаются по явным привязкам PaaS к конкретным контейнерам Deployment.
  Разрешение основному контейнеру не распространяется автоматически на sidecar
  или init-контейнер; init-контейнер требует отдельного разрешения. Ссылка на имя
  Secret сама по себе не даёт доступа. Daemon сверяет все ссылки с привязками
  в состоянии PaaS до применения пакета, включая env и тома; для Secret volume
  проверяется каждый монтирующий его контейнер. Ссылка без разрешения или попытка
  получить Secret мигратора обычным контейнером отклоняет пакет.
  Контейнеры с разрешённым доступом к БД используют общую роль приложения;
  отдельные роли по компонентам этим решением не вводятся.
- Разрешены `env[].valueFrom.secretKeyRef`, `envFrom[].secretRef`, `volumes[].secret`
  и `volumes[].projected.sources[].secret` с проверкой привязок. `envFrom` требует
  разрешения на весь Secret; каждый потребитель составного тома должен иметь доступ
  ко всем его Secrets. `optional: true` не отменяет проверку разрешения. Другие
  механизмы получения секретов, включая CSI-провайдеры, пока не поддерживаются.
  Контейнеру, которому выдан секрет, доверяем: эта привязка не создаёт отдельную
  границу безопасности между контейнерами одного Pod.
- PaaS создаёт один ServiceAccount приложения для обычных компонентов и отдельный
  ServiceAccount мигратора. Они не получают прав чтения Secrets через API, создания
  workloads и изменения RBAC. Пропущенный `serviceAccountName` заполняется ожидаемым,
  совпадающий принимается, другой отклоняет пакет. На ServiceAccount и Pod template
  задаётся `automountServiceAccountToken: false`; пропуск заполняется, явный `true`
  отклоняется. В пользовательских workloads запрещены явные проекции
  `serviceAccountToken` и подключение Secrets типа `kubernetes.io/service-account-token`.
  Мигратор также работает без API-токена; права изменения схемы даёт его роль БД.
  Registry credentials рассматриваются отдельно от выдачи credentials контейнерам;
  пользовательские `imagePullSecrets` в первой версии не используются.
- Выбран GHCR (`ghcr.io`), включая приватные образы; собственный registry не нужен.
  Credentials скачивания задаются через CLI и не включаются в Git или манифесты
  значениями. Требование пользователя — сквозное шифрование credentials.
  Пользователь выбрал скрыть открытый GHCR-токен от daemon. Для этих credentials
  прежнее доверие daemon как обработчику открытых Secrets не применяется.
  Для первой версии выбран доступ container runtime к GHCR через конфигурацию
  registry на узле (`/etc/rancher/k3s/registries.yaml`), без Kubernetes Secret с токеном.
  Получатель credentials — доверенная часть узла, недоступная daemon. Для первой
  версии CLI передаёт токен непосредственно через SSH с проверкой ключа сервера,
  скрытым вводом/stdin, без значения в аргументах команд и логах. На узле credentials
  хранятся в конфигурации `root:root`, режим `0600`, в каталоге, недоступном daemon
  для записи, без прикладного шифрования файла. Это согласованное упрощение;
  root узла остаётся доверенной стороной, защита от чтения диска не заявляется.
  CLI выполняет доверенную подготовку узла и Namespace через SSH; daemon работает
  внутри k3s с отдельным ServiceAccount и управляет только необходимыми ресурсами
  в подготовленных Namespace приложений. Он не получает SSH-ключ, sudo,
  административный kubeconfig, права изменения Namespace, RBAC/admission-защиты,
  системных workloads и собственного развёртывания, создания произвольных PV,
  доступа nodes/proxy, impersonation или выдачи себе дополнительных полномочий.
  Во всех Namespace, где daemon создаёт workloads, кластер независимо применяет
  Pod Security Restricted в режиме enforce; daemon не может изменить настройки
  или получить исключение. Проверка daemon дополняет эту защиту ранней диагностикой.
  Создание Namespace и начальных прав выполняется доверенным этапом CLI до
  передачи управления daemon. Общий root/SSH-доступ daemon не выдаётся.
  Узкая операция настройки GHCR принимает username и токен через stdin, меняет
  только ghcr.io в фиксированном файле, сохраняет root:root 0600, не возвращает
  credentials и не принимает произвольные команды/пути.
  Для registry выбран один root-owned helper с фиксированными действиями
  `set-ghcr`, `apply-registry`, `restore-registry`, `status`. Пользователь paas получает ограниченный
  NOPASSWD только на эти точные вызовы без wildcard; helper и каталог установки
  недоступны ему для записи. Отдельные права на shell, редактор, tee или произвольный
  systemctl не выдаются. Граница sudo установки и подготовки приложений согласована ниже.
  `set-ghcr` проверяет вход и существующий YAML; некорректный файл не заменяется.
  Меняется только auth ghcr.io с сохранением остальных registry/mirrors/TLS-настроек.
  Запись атомарная, root:root 0600; хранится одна предыдущая версия с такой же защитой.
  Параллельные изменения сериализуются, повтор тех же настроек сам по себе не требует
  нового перезапуска. Сохранение даёт статус «требуется применение» без рестарта.
  `apply-registry` по явному выбору оператора перезапускает только службу k3s
  и проверяет готовность. При ошибке нет циклов автоматических рестартов/откатов;
  показывается фактическое состояние и сохраняется предыдущая конфигурация.
  `status` не раскрывает credentials. Готовность k3s и проверка скачивания выбранного
  приватного образа учитываются отдельно; cache не подтверждает доступ к registry.
  `restore-registry` явно восстанавливает фиксированный файл из защищённой предыдущей
  конфигурации, атомарно, с root:root 0600 и сериализацией с другими изменениями.
  Отсутствующая/некорректная копия вызывает отказ без изменения текущего файла.
  Команда не принимает произвольный путь к backup и не возвращает credentials.
  После восстановления отдельно выбирается `apply-registry`; восстановление файла
  не перезапускает k3s и не означает применение runtime. Автовосстановление — PAAS-019.
  Этот доступ не обеспечивает автоматического разграничения
  скачивания образов по приложениям. Шифрование только передачи не закрывает доступ
  через чтение Kubernetes Secret или создание workload, монтирующего его;
  такой путь не считается выполнением требования. TLS и шифрование Secrets
  в хранилище сами по себе не считаются согласованным механизмом этой защиты.

- Daemon с единственным hostPath каталога socket размещается в отдельном системном
  Namespace, где workloads создаёт/обновляет только доверенная установка. Этот Pod
  не соответствует Baseline/Restricted из-за hostPath; Restricted приложений
  не ослабляется. Ни daemon, ни приложения не получают create/update/exec для
  системных workloads. Контейнер без root/privileged/hostNetwork/hostPID/дополнительных
  capabilities. Имя и policy системного Namespace уточняются при подготовке установки.
  Монтируется только /run/paas/daemon: hostPath.type Directory, без DirectoryOrCreate,
  subPath/mount propagation и монтирования отдельного inode socket. Установка проверяет
  реальные типы, владельцев и отсутствие symlink в цепочке и восстанавливает каталог
  после reboot (например systemd-tmpfiles). Права: /run/paas root:root 0755;
  каталог daemon — отдельный UID daemon : paas-api 0750; socket — тот же владелец/группа
  0660. Пользователь paas входит в paas-api для подключения, без права замены socket.
  Числовые UID/GID проверяются на узле и задаются в Pod; UID daemon отличается от
  SSH-пользователя paas и чужих/привилегированных identities. На fsGroup для hostPath
  не полагаемся; рекурсивных root chown/chmod/delete по записываемому каталогу нет.
  Старый socket удаляется только после установления остановки прежнего экземпляра;
  файл/symlink вместо socket вызывает отказ. Один Pod, upgrade Recreate или эквивалент,
  без двух активных экземпляров; краткий разрыв допустим. Проверки готовности через
  UDS, без скрытого TCP listener. Никаких SSH-ключей/admin kubeconfig/GHCR credentials
  в daemon этот mount не предоставляет.
- Граница доверия UDS включает root узла, пользователя paas и процессы локального
  пользователя оператора: они могут обращаться другим клиентом, не обязательно
  официальным CLI. Приложения не имеют доступа к host socket/system workloads,
  а сетевого управляющего endpoint нет. NetworkPolicy не защищает файловый UDS.
  Daemon не узнаёт исходный SSH fingerprint из HTTP/peer credentials; per-key аудит
  каждой API-операции не обещается. Отзыв SSH-ключа не закрывает уже открытый tunnel.
  Источники ревью: https://man.openbsd.org/ssh, https://man.openbsd.org/sshd_config,
  https://kubernetes.io/docs/concepts/security/pod-security-standards/,
  https://kubernetes.io/docs/concepts/storage/volumes/#hostpath.
- GitHub-интеграция входит в 0.x.x: TUI получает публичные SSH-ключи указанного
  аккаунта и автоматизирует добавление доступа на выбранный сервер через уже
  авторизованное SSH-подключение. GitHub username сам по себе не даёт доступ.
  Установка публичного ключа не передаёт приватный ключ и не создаёт его локально.
  Можно использовать отдельный PaaS-ключ либо явно выбранный ключ из GitHub.
  Получение публичного списка: GET /users/{username}/keys с обработкой пагинации.
  Источник: https://docs.github.com/en/rest/users/keys#list-public-keys-for-a-user.
  Клиент генерируется Flux при разработке из исходного API-контракта и включается
  в сборку paas-ctl; TUI вызывает готовый клиент, без runtime-генерации и второго
  рукописного HTTP-клиента. Место исходного контракта и возможности генератора
  проверяются на этапе SDK, не предполагаются уже работающими.
  Добавление запускается явным действием CLI/TUI; дубликаты не создаются,
  посторонние ключи не удаляются. TUI показывает fingerprint; добавляются только
  выбранные ключи, не весь аккаунт. Отзыв — отдельное явное действие CLI/TUI
  по конкретному ключу с сохранением остальных. Удаление ключа из GitHub само
  по себе серверный доступ не меняет. Фоновая синхронизация отложена в PAAS-015.
  Отзыв проверяется новой SSH-аутентификацией и не обещает закрытия открытых сессий.
- Нужен вспомогательный скрипт для отдельного ключа PaaS с возможностью отзыва
  без отключения основного ключа оператора.
- PostgreSQL нужен сразу для состояния control plane; этот же экземпляр
  переиспользуется через отдельные логические БД приложений.
- БД приложения, роли приложения/мигратора и credentials создаются только при
  наличии мигратора в конфигурации этого приложения. Служебная БД самой PaaS
  обязательна независимо от конфигураций приложений. При первом деплое мигратор
  запускается автоматически до старта компонентов; при ошибке они не запускаются.
  При последующих деплоях запуск миграции выбирается явно через TUI/флаги CLI.
- Для приложения создаётся отдельный пользователь PostgreSQL с именем приложения;
  общий пользователь всех приложений не подходит для изоляции и учёта обращений.
- Мигратор получает отдельного пользователя с правами изменения структуры своей
  выделенной схемы и SELECT/INSERT/UPDATE/DELETE для преобразования данных.
- Приложение получает SELECT/INSERT/UPDATE/DELETE без TRUNCATE, владения объектами,
  изменения постоянной структуры, SUPERUSER, CREATEDB и CREATEROLE.
- Удаление мигратора из конфигурации прекращает его последующие запуски, но сохраняет
  существующие БД, роли, credentials и доступ приложения. Удаление БД и отзыв доступа
  выполняются отдельными явными операциями PaaS; их подробный контракт ещё открыт.
- Credentials автоматически генерируются, хранятся в Kubernetes Secrets
  и могут быть явно получены оператором через CLI.
- Дополнительная инфраструктура поднимается при первом запросе, версия задаётся
  в конфигурации платформы. Kafka пока не нужна.
- Общий сервис объявляется один раз на уровне платформы; владелец явно выбирает,
  каким приложениям разрешено подключаться. По умолчанию доступ закрыт. Сервис
  обновляется независимо от приложений-потребителей. Примеры назначения сервиса:
  аутентификация, медиа или аналитика; конкретный набор не фиксируется.
- Каждое приложение и каждый общий сервис получают отдельный Kubernetes Namespace.
  PaaS задаёт NetworkPolicy так, чтобы разрешённые связи работали, а невыбранные
  приложения не могли подключиться.
- Приложение — группа независимо выпускаемых компонентов: API, frontend, worker,
  processor, scraper и другие роли. После первоначальной подготовки мигратор
  может запускаться отдельно.
- На старте компоненты, которым нужна БД, используют общую БД и пользователя
  приложения без прав создания, изменения или удаления таблиц/полей. Будущая задача — выдавать компонентам отдельные роли с минимальными
  правами только на требуемые таблицы.
- Выбран Goose как библиотека небольшой Go-программы в шаблоне образа с папкой
  SQL-миграций. Пишем только настройку запуска, без собственного движка истории
  и исполнения SQL. Версия Goose закрепляется при сборке, credentials поступают
  в Job при запуске и не включаются в образ/логи/полный DSN. Штатное действие
  применяет новые миграции, отсутствие новых — успех.
  Первый профиль предоставляет только up; down/redo/reset через PaaS отсутствуют,
  исправления выпускаются следующей миграцией. Занятая миграцией БД вызывает
  немедленный отказ нового запуска со ссылкой на текущую операцию, без очереди.
  Ошибка не вызывает автоматической новой попытки, включая настройки Job/Pod
  и восстановление daemon; после устранения причины запуск выбирает оператор.
  Управляемые обратные операции, очередь и безопасные политики повторов вынесены
  кандидатами в PAAS-018, без предварительного создания механизмов.
  CLI/TUI вызывает операцию API daemon; daemon создаёт защищённый Job и отдаёт
  статус/диагностические логи. Будущий Web использует те же операции, его реализация
  пока не разрешена. Статус определяется Job/завершением программы, не парсингом
  текстового вывода Goose. Точная версия, настройки Provider, DB-блокировка
  и поведение при частичном сбое требуют проверки до реализации; наличие Goose
  само по себе не считается подтверждением блокировки параллельных запусков.
- Окружения отложены; квоты рассматриваются в будущем.

### Сетевая модель — согласована пользователем, детали открыты

- Между разными приложениями сетевой доступ закрыт по умолчанию;
  необходимые связи разрешаются явно через PaaS у компонента-источника
  к Service целевого приложения. Встречное разрешение получателя не требуется;
  обратное инициирование соединения требует своего разрешения. Ответный трафик
  разрешённого соединения не является обратным инициированием.
- Компоненты одного приложения могут свободно обращаться друг к другу по сети.
  Точная схема переключателя внутриприкладной связи ещё уточняется.
- Внешний доступ задаётся отдельно для каждого компонента: none (по умолчанию),
  allowlist или all. Allowlist содержит точные домены без портов; разрешены все
  порты указанного домена, включая подключения к почтовым сервисам.
  Имя совпадает точно: example.com не разрешает api.example.com; поддомены
  добавляются отдельными записями. Маски, включая *.example.com, не поддерживаются.
  All разрешает весь внешний интернет, но не даёт этим разрешением доступ
  к внутренним адресам платформы/узла и Kubernetes API.
  Механизм исполнения списка, DNS/IP-сопоставления и защита от прямого IP-обхода
  отложены пользователем в PAAS-012 и не блокируют дальнейшее обсуждение SDD.
  Список сохраняет целевые требования, но до исполнения/проверки не считается
  гарантией сетевого запрета. Временное поведение первой реализации требует
  отдельного согласования; молчаливая замена allowlist на all не разрешена.
  Служебные исключения открыты.
- Мигратор имеет только DNS и доступ к целевой PostgreSQL, без доступа
  к компонентам/другим приложениям и внешним API. Разрешения обычных компонентов
  и режим all он не наследует. Служебные соединения Traefik/ACME и общей
  инфраструктуры уточняются отдельно от профиля приложений.
- Эти решения не разрешают реализацию платформы и не закрывают пункт 1.1.

### Согласовано архитектором в рамках делегирования пользователя

Пользователь разрешил три последовательных круга SDD-ревью с продолжением после
согласования архитектором GPT-6 Astra low; это не разрешение реализации платформы.

- Круг 1/3: пользовательский Ingress содержит один host и один path; несколько
  Ingress в пакете допустимы без скрытого разбиения ресурсов. Разрешены явно заданные
  Prefix/Exact, регистрозависимые буквальные пути без rewrite/StripPrefix.
  DefaultBackend, backend.resource, regex-режимы, percent-encoded объявленные paths
  и обратная косая черта не поддерживаются; Kubernetes-валидация обязательна.
  Строгий Prefix Traefik включается и проверяется для закреплённой версии k3s/Traefik.
  Priority задаёт PaaS: 2*L+1 для Prefix, 2*L+2 для Exact, где L — байтовая UTF-8
  длина пути; у Prefix игнорируется завершающий slash, кроме корня. Проверяется
  переполнение и предел 2147482647. Иные пользовательские priority/matcher/rule syntax/
  middleware отклоняются. Более длинный подходящий путь выигрывает.
  Вложение разрешено, дубликаты и одинаковые host/path у Exact и Prefix запрещены;
  Prefix сравнивается без завершающего slash, Exact буквально. Проверяются текущие,
  сохранённые и незавершённые маршруты всего приложения; update исключает собственную
  прежнюю запись, а сбой не освобождает её до установления результата Kubernetes.
  Backend — TCP-порт Service своего компонента/Namespace из пакета или состояния;
  проверяется результирующий Service, включая сохранённые Ingress вне пакета.
  Атомарность переключения трафика не обещается; encoded request-target и штатная
  очистка пути Traefik требуют проверки выбранной версии, не собственного URL-decoding.
- Круг 2/3: домены канонизируются одинаково при регистрации, в rules.host и TLS hosts:
  ASCII lowercase и удаление одной завершающей DNS-точки, затем проверка DNS labels
  (не более 63 символов каждый, 253 всё имя, минимум два labels). Unicode, пробелы,
  URL/порт/путь/credentials, wildcard, IP, localhost и .localhost отклоняются.
  Punycode принимается только как корректный обратимый IDNA A-label; для реализации
  используется готовый строгий профиль golang.org/x/net/idna, без собственного кодека
  и без изменения зависимостей на этапе SDD. Канонизация не подтверждает DNS/владение.
  Ingress class берётся из профиля; TLS — одна запись с единственным каноническим
  host без непустого secretName. PaaS включает TLS через router.tls и задаёт HTTPS
  entrypoint/resolver. Разрешены только точные ожидаемые строковые annotations
  router.priority/entrypoints/tls/tls.certresolver; другие входные Ingress annotations
  и непустые Service annotations отклоняются. Живые annotations доверенных контроллеров
  этим правилом не удаляются и обратно в пользовательский пакет не копируются.
  Для используемого Ingress TCP-порта Service запрещены port 443 и имя https*;
  targetPort 443 не запрещён сам по себе. Backend обслуживает HTTP; внутренние
  HTTPS/h2c/ServersTransport вне первого профиля.
- Круг 3/3: один активный ACME resolver с явными HTTPS CA directory endpoint,
  email и приватным постоянным storage; только HTTP-01. Опубликованные DNS A/AAAA
  должны вести на ожидаемые публичные адреса узла; требуются входящие TCP80/443,
  DNS-разрешение и исходящий HTTPS к CA. HTTP redirect штатный, встроенный solver
  обслуживает HTTP-01 с allowACMEByPass=false. Объявление самого challenge path
  и путей внутри него запрещено, широкие Prefix / и /.well-known разрешены.
  Приоритет solver проверяется на закреплённой версии; нет HTTP fallback к backend.
  SNI strict не добавляется: до выпуска может предъявляться default certificate,
  который не считается готовым или доверенным.
  TLS PENDING/READY/ERROR отделён от Deployment/БД/backend readiness. Внешний paas-ctl
  проверяет DNS к ожидаемому узлу и TLS с правильным SNI, доверенной цепочкой,
  SAN/hostname и сроком; результат содержит checkedAt и срок сертификата. Старый
  результат показывается со временем, без обещания непрерывной доступности.
  Точную ACME-причину не выводим из одного неуспешного TLS probe или парсинга логов.
  Ошибка renewal не удаляет state/действующий сертификат и не откатывает Deployment/БД;
  показывается известная диагностика, срок и предупреждение об истечении. После
  неуспешной новой проверки прежний READY не сохраняется. Повторы первичного выпуска
  ограничены подтверждённым поведением версии; явная проверка/контролируемый restart
  Traefik со state описываются для неустранившейся ошибки.
  Staging проверяется первым, не считается production READY и не добавляет тестовые
  корни в системное доверие. Переход CA явный; state staging/production в отдельных
  файлах одного приватного PVC, один активный resolver. Один writer обеспечивается
  также при upgrade (Recreate или эквивалент); replicas=1/RWO сами этого не доказывают.
  Zero-downtime не обещается. Первое пустое state отличается от утраты существовавшего;
  при потере/повреждении/недоступности требуется восстановление или явный перевыпуск,
  а не молчаливый старт с пустым файлом. Backup/restore до эксплуатации проверяются
  при остановленном writer; место копии и механизм выбираются на инфраструктурном этапе.
  Удаление/перенос домена проверяет все сохранённые маршруты и резервы; занятый домен
  не освобождается. Удаление регистрации не обещает удаления/остановки renewal
  сертификата; работающий acme.json для очистки не редактируется.

### Предлагаемая техническая реализация — требует согласования

- `paas-common`: контракты и generated transport; `paas-ctl`: команды оператора;
  `paas-daemon`: состояние и выполнение операций.
- TUI в `paas-ctl` вызывает те же операции установки и API управления;
  бизнесовая логика daemon не дублируется в экранах.
- Четыре экрана и сценарии деплоя согласованы выше; библиотека — Bubble Tea.
  Точная визуальная компоновка уточняется при реализации; новый веб-интерфейс
  для первой версии не требуется.
- Предлагаемый скрипт `paas-ctl/scripts/ssh-key.sh` использует штатные OpenSSH
  `ssh-keygen` и `ssh`; собственная реализация SSH не требуется.
- Предлагается отдельная пара Ed25519 для каждого сервера в `~/.ssh/paas/`;
  существующий ключ не перезаписывается. Passphrase вводится средствами OpenSSH,
  для повторного использования допускается ssh-agent; значения не сохраняются в конфигурации PaaS.
- Первичное добавление публичного ключа выполняется через текущий административный
  доступ. Приватная часть остаётся у оператора; сохраняется только путь к ней.
- Тем же административным доступом скрипт создаёт пользователя `paas`, если его нет,
  и устанавливает ключ в его разрешённые ключи. Существующая учётная запись
  проверяется и переиспользуется без удаления данных и чужих ключей.
- Первичная подготовка пользователя paas, SSH-ключей и root-owned служебных команд
  выполняется существующим административным доступом оператора с нужными правами,
  без передачи credentials daemon. Далее paas получает sudo только на фиксированные
  операции установки платформы, подготовки Namespace/начальных прав приложения,
  установки/обновления daemon и registry-helper. Запуск — явное действие CLI/TUI.
  Произвольные команды, shell, пути, административный kubectl с пользовательскими
  аргументами и пользовательские root-манифесты не принимаются; NOPASSWD ALL
  и общий административный kubeconfig не выдаются. Служебные команды и каталог
  root-owned и недоступны paas/daemon для записи. Точные команды/sudoers и параметры
  профиля установки закрепляются до реализации в этих границах.
  Более гибкое делегирование и автоматическое восстановление — кандидаты PAAS-019.
- Подключение PaaS выбирает отдельную identity; проверка не использует другие
  identity, пароль или существующий multiplexed connection. Host key проверяется.
- Отзыв выполняется через независимый административный доступ: удалить точную
  запись ключа, определяемую по публичному материалу/fingerprint, а не только комментарию;
  остальные ключи и права файлов сохраняются.
- Сам отзыв ключа блокирует новые SSH-аутентификации. Закрытие уже открытых сессий
  и отзыв отдельно выданных API-токенов или kubeconfig — другие операции.
- Для k3s использовать Kubernetes API; обычный Kubernetes рассматривать
  как следующую целевую конфигурацию, а не заранее отдельную систему адаптеров.
- Установщик проверяет сервер и наличие k3s; при отсутствии устанавливает
  закреплённую версию, при наличии проверяет доступность и совместимость.
- Недоступность API или отсутствие kubeconfig не доказывают отсутствие k3s;
  существующий кластер не переустанавливается и не обновляется автоматически.
- Последовательность установки: готовый k3s → PostgreSQL → служебная БД и Secrets
  → daemon. PostgreSQL состояния PaaS не становится обязательным datastore самого k3s,
  чтобы не создавать циклическую зависимость запуска.
- Первоначальную установку PostgreSQL и служебных Secrets выполнять до запуска
  daemon, которому уже требуется собственная БД.
- Владельцем БД оставить служебную сторону; мигратору выдать владение выделенной
  схемой и её объектами. Бизнесовый пользователь не владеет этими объектами.
- Настроить доступ к новым таблицам/sequences через default privileges роли мигратора;
  закрыть лишние права PUBLIC и подключения к чужим/служебным БД.
- Отдельные Secrets приложения и мигратора; значения не дублируются в состоянии daemon.
- Включить шифрование Secrets в хранилище k3s и ограничить доступ через RBAC.
- Сборку образа мигратора выполнять локально или в CI.
- Привязку credentials определяет явная операция миграции приложения;
  произвольная метка контейнера не выдаёт повышенные права.
- Запуски миграций одной БД сериализуются; инструмент учитывает историю применений.
- Повторные операции сохраняют ресурсы и пароли; частично выполненная подготовка
  восстанавливается без выдачи приложению неполностью настроенного доступа.
- Обычный деплой не меняет версии общих сервисов; их обновление — отдельная операция.
- Удаление приложения по умолчанию сохраняет данные; удаление БД и смена пароля
  требуют отдельных явно выбранных операций.

## Risks / Trade-offs

- Прямые изменения управляемых ресурсов через Kubernetes API могут рассинхронизировать
  состояние daemon и кластера → штатные операции выполняются через PaaS;
  документация рекомендует избегать обхода. Автоматическое восстановление пока
  не определено и не считается гарантией этой модели.
- Общий PostgreSQL означает общий отказ и общие ресурсы → отдельные пользователи
  изолируют доступ, а резервное копирование, ограничения и мониторинг проектируются явно.
- Разные пользователи дают атрибуцию, но сами не собирают метрики и не вводят квоты
  → отдельные задачи PAAS-002 и PAAS-003.
- Утечка credentials мигратора позволяет менять его схему → отдельный Secret,
  выдача только задаче миграции, отсутствие credentials в образе и логах.
- Независимые миграции могут сломать старый backend → совместимые изменения схемы;
  автоматический откат образа не означает обратную миграцию БД.
- Потеря кластера может означать потерю Secrets → резервное копирование
  PostgreSQL, секретов и необходимых ключей восстановления.
- Обновление packages-go может потребовать регенерации → закрепить совместимые
  версии и проверить generated client/server без ручного исправления generated files.
- Прерванная установка k3s или недоступный кластер → отличать отсутствие установки
  от неисправного состояния, показывать причину и не выполнять разрушительную замену.
- Потеря доступа PaaS → основной административный доступ остаётся независимым;
  отзыв проверяется новой сессией с единственным ключом PaaS.

## Предложение следующего подэтапа: PostgreSQL и каталог — 2026-10-21

**Статус: пользователь одобрил реализацию подэтапа 3.3.1–3.3.5** после выбора
pgx + pgxpool + Squirrel + Goose. Первая версия — без шардирования control plane
и БД приложений; шардирование обеих областей остаётся будущим развитием.
Репликация/CloudNativePG/PgBouncer сейчас не устанавливаются. Предыдущее ревью
Astra не распространяется на этот новый runtime. Снимок 68 Requirements и 25/45 выше
исторически соответствует коду до этого предложения. Теперь delta содержит
ещё три предложенных требования и пять незавершённых подзадач; код прежний.

### Итерация 1 — фактическая основа

Runtime PostgreSQL, driver и Goose в трёх PaaS go.mod отсутствуют. В проверенном
packages-go v0.3.0 есть configx/httpx, но нет DB repository/driver для переиспользования.
Daemon регистрирует только health/ready, восемь PaaS endpoints пока только в SDK.
Схема preview/operations не выбрана: наличие DTO не задаёт транзакции/ownership.
В PATH есть docker, но готовность engine/образа/тестовой БД не проверялась;
psql/postgres в PATH отсутствуют. Установка зависимостей/БД в этом этапе не выполнялась.

### Итерация 2 — границы и данные

Предлагается служебный каталог на PostgreSQL, не искусственная таблица для ping.
По решению пользователя от 2026-10-22 PostgreSQL хранит данные, все проверки
каталога выполняет приложение. Схема v2: paas_apps(app_id text, name text,
deleted_at timestamptz), paas_components(component_id text, app_id text, name text,
deleted_at timestamptz). CHECK/FK/NOT NULL/PK/UNIQUE и триггеров в таблицах каталога
нет; обычные неуникальные индексы поддерживают lookup и пагинацию. История Goose
остаётся служебным механизмом мигратора. Существующая v1 обновляется отдельной
транзакционной миграцией без потери записей. ID — прежний label-compatible формат
до 63 ASCII байт, name — 1–128 UTF-8 байт без controls; приложение проверяет DTO,
единственность Get и сортировку/дубликаты всей прочитанной страницы с lookahead.
Будущие writers обязаны проверять поля, уникальность и принадлежность в приложении
в общей сериализованной транзакции; простой SELECT перед INSERT не защищает от гонки.
В текущем этапе production writers отсутствуют. Удаление записей каталога — только
UPDATE deleted_at; SELECT скрывает tombstones. Удалённый родитель скрывает компоненты
и даёт 404 для component Get/List; физический DELETE и каскады не используются.
ID-колонки имеют COLLATE "C" для соответствия Go byte ordering, а не locale БД.
Связь app/component неизменна для будущих writers; этот read-only этап её не меняет.
Удаления/переименования и генерация новых ID через production API не добавляются.

Служебная БД, две identity и начальные grants заранее подготовлены доверенным
оператором/тестовым fixture. Мигратор владеет только служебными таблицами;
runtime identity имеет CONNECT/USAGE/SELECT на них и историю версии, без DDL,
SUPERUSER/CREATEDB/CREATEROLE и доступа к бизнесовым БД. Команда не управляет ролями
и credentials. Installation остаётся 3.1/3.2. Реальный источник production-записей
не подменяется фиктивным Create: пока каталог может быть пустым.

### Итерация 3 — подключение, schema lifecycle и readiness

Выбранный стек: native pgx/v5 + pgxpool v5.11.0, Squirrel v1.5.4 для
параметризованного SQL; Goose Provider v3.29.0 через pgx/stdlib только в отдельной
команде `paas-daemon migrate`. sqlc/ORM, универсальный storage interface и
второй runtime datastore не добавляются.
Один runtime pgxpool: MaxConns=8, MinConns=0, MaxConnIdleTime=30 минут,
MaxConnLifetime=30 минут. Migrate подключается напрямую, не через transaction pooler.
Конкретный Store внедряется в HTTP services; жизненным циклом владеет main.

Обычный `paas-daemon` получает путь PAAS_CONTROL_DB_DSN_FILE, команда migrate —
PAAS_CONTROL_DB_MIGRATION_DSN_FILE. Значения — secret-файлы, не DSN в argv/env.
Файл читается один раз с пределом 16 KiB, допускается один завершающий newline.
URL PostgreSQL требует явно заданных host/database/user/password/sslmode;
libpq environment/service fallback не используется. Разрешён verify-full с явно
заданным trust root; disable допускается только явно для локального integration
профиля, без заявления о шифровании. PG* environment не меняет выбранную identity/БД.
Ошибки конфигурации/драйвера наружу переводятся в безопасные фиксированные сообщения.
Не создаётся YAML/Vault/profile-конфигурация для единственного пути к secret-файлу:
stdlib os/read limit и разбор URL покрывают этот первый объём; configx можно
подключить, когда появится содержательная конфигурация сервиса.

Migrate читает только отдельные DDL credentials, работает со встроенными SQL
и Goose version history в служебной БД. Команда: только up до версии бинарника,
без произвольного каталога SQL, down/redo/reset и автоматических повторов после
ошибки. Goose Provider получает Postgres session locker; общий deadline 30 секунд
ограничивает ожидание lock и исполнение. Все начальные SQL — транзакционные.
Обычный daemon не содержит migration credentials и не вызывает Up при старте.
Команда migrate перед Up отклоняет неизвестную/более новую применённую версию;
обычный повтор возможен только для известной совместимой истории. Secret-файлы
читаются при запуске, изменение подключения/credentials требует restart; hot reload
и ротация credentials в этом подэтапе не добавляются.

Readiness: один общий context 2 секунды на pgxpool.Ping, чтение версии и запросы
проверки доступа к обеим таблицам. Ожидаемая версия равна последней встроенной;
неизвестная/старая/будущая — 503 без исправления. /health остаётся liveness 200.
Пул восстанавливает соединения, а следующий ready повторяет проверку: отдельный
reconcile loop или кеш успеха не вводится. Shutdown останавливает HTTP и закрывает DB.
В ctl текст `Platform: ready` заменяется на `Control plane: ready`, аналогично
not ready; wire schema common ReadyResponse не меняется. Это service/dependency
readiness, не готовность к deploy или health/TLS бизнесовых приложений.

### Итерация 4 — сервисы чтения и отказы

Регистрируются прежние generated apps/components handlers; применяются прежние
явные validation.Query и validation.Summary/Page. Ошибка input/cursor даёт
declared 400, unknown app/component или чужая принадлежность — прежний 404,
DB outage/schema mismatch — безопасный declared 503. Нарушение сохранённого DTO —
generic 500 через runtime adapter, без выдачи или исправления повреждённого снимка.
Preview/apply/operations handlers не регистрируются до их отдельного runtime.

SQL параметризован; LIMIT = requested limit + 1, ORDER BY ID COLLATE "C",
продолжение WHERE ID > last ID. Next cursor строится по последнему возвращённому,
не по лишнему lookahead элементу. Формат cursor — canonical JSON {v:1,kind,app_id,after}
в base64url без padding; kind разделяет apps/components, app_id задан только
components. Декодирование ограничено существующими 1024 байтами, проверяет версию,
точные поля/каноничность, shape ID и scope. Limit не входит в cursor.
Cursor не секрет и не полномочие, HMAC/key lifecycle не вводится. Не требуется
исходная строка after: удаление позиции не ломает продолжение. Для Components.List
проверка родителя и SELECT страницы выполняются в одном read-only repeatable-read
snapshot. Snapshot между страницами не обещается согласно прежнему контракту.

Integration fixture в реальном PostgreSQL выполняет миграцию, вставляет отдельной
identity тестовые записи, запускает и перезапускает daemon на подготовленном UDS.
Проверяются: пустая БД; Get/List и 101+ записей; переходы страниц; смена limit;
чужой scope; soft delete after/родителя/компонента; application ownership; невалидные сохранённые данные; outage/
recovery; missing/old/future schema; отказ DDL runtime role; concurrent migrate;
ошибка транзакционной миграции; repeated up; таймауты; canary credentials.
Fixtures не создают production API и не доказывают k3s/RBAC/изоляцию бизнесовых БД.

## Предложенный подэтап 3.3.6–3.3.10 — чтение истории, 2026-10-23

### Границы и выбор объёма

Сначала реализуются два уже существующих GET operations. Чтение истории
проверяемо отдельно от исполнения деплоя и не требует придумывать worker/stages.
Preview/apply пока не регистрируются. Производителя production операций нет;
integration fixtures создают записи отдельной identity и не являются API записи.
Это не завершение общего 3.3 и не доказательство восстановления исполнения.

### Предложенная схема v3

Отдельная embedded Goose up-миграция добавляет public.paas_operations:
operation_id text COLLATE "C", state text, snapshot bytea, deleted_at timestamptz.
Все колонки nullable, без CHECK/FK/PK/UNIQUE, триггеров, JSONB/enum и серверной
валидации. snapshot хранит JSON существующего Operation; BYTEA не требует от БД
разбирать JSON. Обычные индексы: (operation_id), (state, operation_id).
Go проверяет snapshot, совпадение operation_id/state с колонками, единственность
Get и порядок/дубликаты страницы с lookahead. NULL/ошибка JSON/расхождение
колонок со снимком/невалидный DTO означают безопасную внутреннюю ошибку.
Это согласованный снимок одной SQL-строки; state не читается отдельным запросом.

История не соединяется с текущими apps/components: удаление приложения
не скрывает операции. Soft delete задаёт deleted_at через UPDATE; GET выбирают
только deleted_at IS NULL. Cleanup worker и TTL-запись не добавляются;
будущий cleanup обязан соблюдать прежние 30 дней terminal history и запрет
удаления ACCEPTED/RUNNING/RECOVERY_REQUIRED. DB constraints не заменяют эти правила.
Повтор миграции и переход v2 → v3 сохраняют каталог и tombstones. Точная schema
version readiness становится 3; runtime role сохраняет SELECT-only доступ к новой
таблице. DDL/grants выполняет отдельный оператор, startup их не изменяет.

### Предложенные пределы выдачи

Все длины строк ниже — UTF-8 байты, не число символов; новые ограниченные поля
требуют корректный UTF-8 без управляющих символов. Открытые code/stage каталоги
остаются открытыми; новый UUID/label-формат operation_id не вводится.

| Значение | Верхняя граница |
| --- | --- |
| operation_id | 96 байт, непустой opaque ID |
| app_id / component_id снимка истории | 256 байт каждый, непустые opaque ID |
| stage при наличии | 64 байта, непустой |
| diagnostics | 32 элемента, non-null; прежние требования state сохраняются |
| Diagnostic.code | 64 байта, непустой |
| Diagnostic.message | 1024 байта, непустой |
| Diagnostic.file при наличии | 256 байт; прежние правила имени сохраняются |
| Diagnostic.field_path при наличии | 512 байт; прежний JSON Pointer, пустой корень допустим |
| Каждый timestamp | 40 байт и прежний RFC3339 UTC с Z |
| snapshot и JSON одного Operation | 64 KiB каждый, включая JSON escaping |
| JSON OperationPage | 8 MiB, включая envelope/cursor/escaping |

Это runtime-профиль истории, не молчаливое изменение всех прежних SDK validators,
preview diagnostics или OpenAPI. В common добавляется отдельный явный helper,
который использует прежний Operation validator и эти bounds. Прежние validators
сохраняют поведение; подключение helper к preview/apply согласуется с их этапом.
Малый field limit не отменяет общий JSON limit: проверяются оба. Нет обрезки,
пропуска невалидных записей или замены диагностики пустым массивом.

В сервисе перед отправкой сериализуется и проверяется полный response. До записи
успешных HTTP headers превышение/повреждение даёт generic 500 через прежний
runtime adapter, без тела snapshot, SQLSTATE или драйверной ошибки.
Слишком длинный/невалидный operation_id запроса даёт прежний 400 INVALID_REQUEST.
Новый HTTP status/DTO не добавляется. Приложение проверяет размер полученного
snapshot до JSON decoding; произвольная повреждённая DB-строка всё ещё может
потребовать выделения памяти драйвером — строгая защита от враждебного DB server
в этом объёме не заявляется. Восемь pool connections и конечный query deadline
сохраняются, дополнительных HTTP concurrency настроек не вводится.

Проверка формы текста не распознаёт секреты в произвольной строке. Будущий writer
должен формировать безопасные сообщения из контролируемых шаблонов; сырые YAML,
env/ConfigMap/DSN/driver errors в snapshot не сохраняются. Нынешнее чтение выдаёт
только поля Operation, без отдельного сырого payload endpoint.

### Запросы и ошибки

SQL строится существующим Squirrel: параметры для ID/state/after/limit,
ORDER BY operation_id COLLATE "C", LIMIT requested+1. Прежние default 50,
range 1–100, пять state, 404 Get/пустой List и 503 при сбое БД сохраняются.
Проверка schema/чтение выполняются в прежнем read-only repeatable-read transaction
с общим deadline 2 секунды. Parent lookup не требуется. Чтение не обновляет
state/timestamps/TTL, не запускает recovery и не снимает резервы.

Cursor — canonical JSON {v:1,kind:"operations",state,after} в base64url без padding;
state null означает отсутствие фильтра, after — последний выданный operation_id.
Проверяются точная каноничность, версия, scope, state и bounded ID. Прежний token
каталога сюда не подходит и наоборот. Limit в scope не входит. Предел cursor
1024 байта сохраняется; ID 96 байт помещается даже с JSON escaping.
После soft delete позиции lookup after не требуется. Snapshot между страницами
не обещается. Все прочитанные строки, включая lookahead, валидируются; при
неизменной истории обход возвращает каждый подходящий ID ровно один раз.

### Проверки и последующий этап

Приёмка — настоящий PostgreSQL с прежним pinned image и отдельный daemon process
по UDS с generated clients: пусто/404, все пять state, 105+ записей, фильтр,
смена limit, scope, byte ordering, soft delete after и restart. Проверяются
повреждённые/NULL/oversized snapshots, дубликат на границе страницы, mismatch
ID/state, отсутствие parent dependency, ошибки 400/503/500, canary и отсутствие
side effects. Границы строк/diagnostics/wire проверяются unit-тестами с escaping.
Также v2 → v3/repeated migrate, grants/schema failure, readiness и старый каталог.
Build/test/race/vet/tidy/fmt/lint, Linux build и OpenSpec validate обязательны;
SDK source/generated прежнего снимка сохраняются побайтно. Без live DB/UDS
приёмка остаётся открытой, skip не считается доказательством.

После этого отдельно согласуются production writers и durable preview/apply:
сериализация проверок без UNIQUE/FK, неизменяемый вход, сравнение подтверждённого
плана, атомарное принятие с резервами и связью preview → operation, tombstones
после очистки и восстановление неизвестного Kubernetes результата. Создавать
ACCEPTED без этих условий или запускать фиктивный worker запрещено.
