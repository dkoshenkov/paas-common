# Design

## Context

- Статус: архитектура платформы обсуждается; отдельно согласован только локальный
  этап переименования и переноса документов, без реализации PaaS.
- Мотивация и границы репозиториев: [proposal.md](proposal.md).
- `paas-ctl` и `paas-daemon` пока шаблоны; `paas-common` содержит исходные API.
- Текущий API использует `compose_yaml` и `compose_sha256`; Makefile генерирует
  только общие контракты из `docs/api/common`.
- SDK зависит от packages-go `v0.2.0`, локальный Flux — от `v0.3.0`.
- Документ Flux относит path-параметры к отложенным возможностям;
  API PaaS уже содержит `/apps/{name}`. Нужна проверка на минимальном контракте.
- Существующий `common/migration.yaml` описывает Up/Down API;
  это не реализация отдельного контейнера мигратора.

## Goals / Non-Goals

**Goals:**

- Зафиксировать подтверждённые требования и проверяемые границы первой версии.
- Переиспользовать один PostgreSQL, сохраняя разные БД и пользователей приложений.
- Независимо управлять версиями компонентов и запусками миграций.
- Использовать Flux и packages-go по их назначению.

**Non-Goals:**

- Реализация кода в текущем документальном этапе.
- Окружения, квоты БД, Kafka, Compose и Swarm в первой реализации.
- Обязательный Vault, общий релиз frontend/backend и автоматические миграции при каждом последующем деплое.
- Мультинод в `0.x.x`; он относится к будущему этапу продукта `1.0.0`/`1.x.x`.

## Decisions

### Подтверждено пользователем

- Репозиторий называется `paas-common`: контракты, сгенерированные SDK-артефакты
  и общие определения PaaS. Локальный каталог и module path переименованы;
  OpenSpec и backlog находятся внутри него. GitHub-репозиторий переименован в
  `dkoshenkov/paas-common`; origin указывает на `git@github.com:dkoshenkov/paas-common.git`.
- Начинаем с k3s вместо Docker Compose.
- Входной формат начального деплоя — обычные Kubernetes-манифесты. Это нативный
  формат k3s/Kubernetes; будущие адаптеры Compose или Swarm потребуют отдельного
  способа описания или преобразования.
- Способ подачи манифестов и PaaS-метаданные для привязки ресурсов к приложению,
  БД, Secrets и разрешённым связям ещё не выбраны.
- Служебные объекты (созданные PaaS NetworkPolicy, Secrets и полномочия мигратора)
  управляются PaaS целиком. В пользовательских workloads защищаются Namespace,
  идентификаторы, служебные метки принадлежности/доступа и ссылки на credentials.
  Эти настройки изменяются через CLI/TUI. Остальные пользовательские метки свободны.
- Для некритичного расхождения защищённого поля выводится WARN с путём поля,
  ожидаемым значением, допустимыми вариантами и способом корректного изменения;
  применяется значение PaaS. Изменения, нарушающие изоляцию, отклоняются.
- Мигратор выполняется защищённо: обычный workload не может получить его credentials
  или использовать его полномочия, включая ссылки на Secret и ServiceAccount.
  Конкретный механизм защиты и необходимость Vault ещё не выбраны.
- Продукт `0.x.x` поддерживает одну ноду; `1.0.0`/`1.x.x` требует мультинод.
- Автоматическое версионирование нужно в каждом репозитории. Только для `0.x.x`: minor
  по умолчанию, patch по `fix:`, minor по `!` или `BREAKING CHANGE:`. Переход на
  `1.0.0` согласуется отдельно после готовности мультинода. В `1.x.x` API проектировать
  с обратной совместимостью; правило bump для `0.x.x` на него не распространяется.
  Политика записана в AGENTS.md.
- Установка PaaS включает установку k3s на выбранном сервере, если его ещё нет.
- Первоначальная установка выполняется через SSH с компьютера оператора.
- SSH-подключения PaaS выполняются отдельным Linux-пользователем `paas`.
- Основной пользовательский интерфейс `paas-ctl` — интерактивный TUI.
- Нужен вспомогательный скрипт для отдельного ключа PaaS с возможностью отзыва
  без отключения основного ключа оператора.
- PostgreSQL нужен сразу для состояния control plane; этот же экземпляр
  переиспользуется через отдельные логические БД приложений.
- БД приложения, роли приложения/мигратора и credentials создаются только при
  наличии мигратора в конфигурации этого приложения. Служебная БД самой PaaS
  обязательна независимо от конфигураций приложений. При первом деплое мигратор
  запускается автоматически до старта компонентов; при ошибке они не запускаются.
  При последующих деплоях запуск миграции выбирается явно через TUI/флаги CLI.
- Для приложения создаётся отдельный пользователь PostgreSQL с именем приложения;
  общий пользователь всех приложений не подходит для изоляции и учёта обращений.
- Мигратор получает отдельного пользователя с правами изменения структуры своей БД.
- Приложение получает доступ к данным без SUPERUSER, CREATEDB и CREATEROLE.
- Credentials автоматически генерируются, хранятся в Kubernetes Secrets
  и могут быть явно получены оператором через CLI.
- Дополнительная инфраструктура поднимается при первом запросе, версия задаётся
  в конфигурации платформы. Kafka пока не нужна.
- Общий сервис объявляется один раз на уровне платформы; владелец явно выбирает,
  каким приложениям разрешено подключаться. По умолчанию доступ закрыт. Сервис
  обновляется независимо от приложений-потребителей. Примеры назначения сервиса:
  аутентификация, медиа или аналитика; конкретный набор не фиксируется.
- Каждое приложение и каждый общий сервис получают отдельный Kubernetes Namespace.
  PaaS задаёт NetworkPolicy так, чтобы разрешённые связи работали, а невыбранные
  приложения не могли подключиться.
- Приложение — группа независимо выпускаемых компонентов: API, frontend, worker,
  processor, scraper и другие роли. После первоначальной подготовки мигратор
  может запускаться отдельно.
- На старте компоненты, которым нужна БД, используют общую БД и пользователя
  приложения без прав создания, изменения или удаления таблиц/полей. Будущая задача — выдавать компонентам отдельные роли с минимальными
  правами только на требуемые таблицы.
- Основа мигратора — папка SQL и шаблон образа; собственный Go-мигратор не выбран.
- Окружения отложены; квоты рассматриваются в будущем.

### Предлагаемая техническая реализация — требует согласования

- `paas-common`: контракты и generated transport; `paas-ctl`: команды оператора;
  `paas-daemon`: состояние и выполнение операций.
- TUI в `paas-ctl` вызывает те же операции установки и API управления;
  бизнесовая логика daemon не дублируется в экранах.
- Предлагаемые экраны: серверы и установка, приложения/компоненты, деплой,
  миграции, статус и логи операций, явное получение credentials.
- Библиотека TUI и точная структура экранов ещё не выбраны; новый веб-интерфейс
  для первой версии не требуется.
- Предлагаемый скрипт `paas-ctl/scripts/ssh-key.sh` использует штатные OpenSSH
  `ssh-keygen` и `ssh`; собственная реализация SSH не требуется.
- Предлагается отдельная пара Ed25519 для каждого сервера в `~/.ssh/paas/`;
  существующий ключ не перезаписывается. Passphrase вводится средствами OpenSSH,
  для повторного использования допускается ssh-agent; значения не сохраняются в конфигурации PaaS.
- Первичное добавление публичного ключа выполняется через текущий административный
  доступ. Приватная часть остаётся у оператора; сохраняется только путь к ней.
- Тем же административным доступом скрипт создаёт пользователя `paas`, если его нет,
  и устанавливает ключ в его разрешённые ключи. Существующая учётная запись
  проверяется и переиспользуется без удаления данных и чужих ключей.
- Права sudo пользователя `paas` требуют отдельного согласования;
  выбор отдельного пользователя не означает выдачу `NOPASSWD: ALL`.
- Подключение PaaS выбирает отдельную identity; проверка не использует другие
  identity, пароль или существующий multiplexed connection. Host key проверяется.
- Отзыв выполняется через независимый административный доступ: удалить точную
  запись ключа, определяемую по публичному материалу/fingerprint, а не только комментарию;
  остальные ключи и права файлов сохраняются.
- Сам отзыв ключа блокирует новые SSH-аутентификации. Закрытие уже открытых сессий
  и отзыв отдельно выданных API-токенов или kubeconfig — другие операции.
- Для k3s использовать Kubernetes API; обычный Kubernetes рассматривать
  как следующую целевую конфигурацию, а не заранее отдельную систему адаптеров.
- Установщик проверяет сервер и наличие k3s; при отсутствии устанавливает
  закреплённую версию, при наличии проверяет доступность и совместимость.
- Недоступность API или отсутствие kubeconfig не доказывают отсутствие k3s;
  существующий кластер не переустанавливается и не обновляется автоматически.
- Последовательность установки: готовый k3s → PostgreSQL → служебная БД и Secrets
  → daemon. PostgreSQL состояния PaaS не становится обязательным datastore самого k3s,
  чтобы не создавать циклическую зависимость запуска.
- Первоначальную установку PostgreSQL и служебных Secrets выполнять до запуска
  daemon, которому уже требуется собственная БД.
- Владельцем БД оставить служебную сторону; мигратору выдать владение выделенной
  схемой и её объектами. Бизнесовый пользователь не владеет этими объектами.
- Настроить доступ к новым таблицам/sequences через default privileges роли мигратора;
  закрыть лишние права PUBLIC и подключения к чужим/служебным БД.
- Отдельные Secrets приложения и мигратора; значения не дублируются в состоянии daemon.
- Включить шифрование Secrets в хранилище k3s и ограничить доступ через RBAC.
- Запускать мигратор как отдельный Job; сборку образа выполнять локально или в CI.
- Привязку credentials определяет явная операция миграции приложения;
  произвольная метка контейнера не выдаёт повышенные права.
- Запуски миграций одной БД сериализуются; инструмент учитывает историю применений.
- Повторные операции сохраняют ресурсы и пароли; частично выполненная подготовка
  восстанавливается без выдачи приложению неполностью настроенного доступа.
- Обычный деплой не меняет версии общих сервисов; их обновление — отдельная операция.
- Удаление приложения по умолчанию сохраняет данные; удаление БД и смена пароля
  требуют отдельных явно выбранных операций.

### Граница следующего обсуждения

- Этот change фиксирует основу; формат API/описания приложения пока не утверждён.
- Принято использовать Kubernetes-манифесты как вход деплоя; способ доставки,
  точное сопоставление ресурсов манифеста с выделенным Namespace и контракт
  PaaS-метаданных ещё открыты. Изоляция строится на отдельных Namespace и
  NetworkPolicy для явного списка разрешённых потребителей.
- Требуется уточнить реестр защищённых объектов/полей, допустимые значения и
  диагностику WARN/отказа. Хранение ожидаемых значений и использование hash пока
  не определены; механизм не должен доверять копии или hash из пользовательского YAML.
- Защищённое выполнение мигратора согласовано как требование; размещение его Secret,
  контроль ссылок workloads и возможная интеграция Vault требуют отдельного решения.
- Мультинод и HA не отождествляются; требования будущей реализации отдельны.
- Release-аудит по локальным файлам: SDK содержит caller и release-конфиги;
  ctl/daemon содержат только reusable workflow и скрипт генерации callers.
  Политика minor по умолчанию в существующем SDK-конфиге не настроена.
- Для `0.x.x` breaking change повышает minor, а автоматический переход на `1.0.0`
  запрещён. Начиная с `1.0.0`, API проектировать с обратной совместимостью.
- Модель приложения, общая БД/роль его компонентов и доступ к общим сервисам только
  для явно выбранных приложений согласованы. Способ задания разрешённого списка
  (например, селектор или метка) и контракт подключения остаются открытыми.
- Перед соответствующими этапами нужно отдельно выбрать способ установки,
  аутентификацию оператора, SQL-инструмент и состав мониторинга.
- SSH-установка и отдельный пользователь `paas` согласованы;
  отдельно нужно определить необходимые права sudo.
- TUI согласован; библиотека и компоновка экранов выбираются перед его реализацией.
- Профиль данных пока гарантирует SELECT/INSERT; права UPDATE/DELETE требуют уточнения.
- Условие наличия мигратора определяет первичное создание БД приложения. Поведение
  уже созданных ресурсов при удалении мигратора из конфигурации ещё требует
  обсуждения в рамках жизненного цикла данных.
- Требуется определить флаги последующих миграций, сохранение результата первой
  подготовки при сбоях daemon и добавление мигратора уже развёрнутому приложению.
- Получение секрета является требованием; произвольный доступ всех пользователей CLI
  к секретам не подразумевается.

## Risks / Trade-offs

- Общий PostgreSQL означает общий отказ и общие ресурсы → отдельные пользователи
  изолируют доступ, а резервное копирование, ограничения и мониторинг проектируются явно.
- Разные пользователи дают атрибуцию, но сами не собирают метрики и не вводят квоты
  → отдельные задачи PAAS-002 и PAAS-003.
- Утечка credentials мигратора позволяет менять его схему → отдельный Secret,
  выдача только задаче миграции, отсутствие credentials в образе и логах.
- Независимые миграции могут сломать старый backend → совместимые изменения схемы;
  автоматический откат образа не означает обратную миграцию БД.
- Потеря кластера может означать потерю Secrets → резервное копирование
  PostgreSQL, секретов и необходимых ключей восстановления.
- Обновление packages-go может потребовать регенерации → закрепить совместимые
  версии и проверить generated client/server без ручного исправления generated files.
- Прерванная установка k3s или недоступный кластер → отличать отсутствие установки
  от неисправного состояния, показывать причину и не выполнять разрушительную замену.
- Потеря доступа PaaS → основной административный доступ остаётся независимым;
  отзыв проверяется новой сессией с единственным ключом PaaS.

## Migration Plan

- Сейчас сохранить и проверить документы; не менять код или установленные сервисы.
- Согласовать недостающие контракты и архитектуру выбранного этапа.
- Подготовить обновление SDK и проверку Flux; затем двигаться по этапам tasks.md.
- При замене Compose-полей явно согласовать несовместимость API.
- Основные specs синхронизировать и change архивировать только после реализации
  согласованного объёма и проверок; статус документов не равен готовности платформы.
