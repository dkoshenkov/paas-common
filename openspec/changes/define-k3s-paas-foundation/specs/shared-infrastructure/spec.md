# Spec Delta

## Purpose

Определить общую инфраструктуру PaaS и её создание по потребности без отдельного
экземпляра каждого инфраструктурного сервиса для каждого приложения.

## ADDED Requirements

### Requirement: Версия 0.x.x поддерживает одну ноду

PaaS версии 0.x.x SHALL устанавливать и обслуживать только однонодовый k3s.
Добавление других нод SHALL NOT входить в операции этой версии.

#### Scenario: Однонодовая установка
- **WHEN** оператор устанавливает PaaS версии 0.x.x
- **THEN** один узел k3s размещает control plane PaaS, общий PostgreSQL и приложения

#### Scenario: Обнаружение нескольких нод
- **WHEN** установка PaaS версии 0.x.x обнаруживает несколько нод выбранного кластера
- **THEN** конфигурация помечается как неподдерживаемая до изменения компонентов PaaS
- **AND** существующие ноды не удаляются для приведения к однонодовой конфигурации

### Requirement: Установка выполняется через SSH с отдельным ключом

Установщик PaaS SHALL выполнять первоначальную установку на выбранном сервере
через SSH с отдельным ключом PaaS. Вспомогательный скрипт SHALL обеспечивать
создание ключа, установку публичной части через имеющийся административный доступ,
проверку подключения и отзыв доступа этого ключа.

#### Scenario: Подготовка ключа PaaS
- **WHEN** оператор запускает подготовку SSH-доступа
- **THEN** скрипт создаёт отдельную пару ключей без перезаписи основного ключа
- **AND** приватная часть остаётся на компьютере оператора вне Git и не копируется на сервер
- **AND** публичная часть добавляется без удаления других разрешённых ключей

#### Scenario: Повторная подготовка доступа
- **WHEN** для выбранного сервера уже подготовлен ключ PaaS
- **THEN** повторный запуск не перезаписывает его и не дублирует разрешённую запись

#### Scenario: Проверка отдельного ключа
- **WHEN** скрипт проверяет подключение PaaS
- **THEN** выполняется новая аутентификация только выбранным ключом PaaS
- **AND** отсутствие доступа не маскируется основным ключом, паролем или готовой SSH-сессией
- **AND** проверка подлинности сервера не отключается

#### Scenario: Отзыв SSH-доступа PaaS
- **WHEN** оператор через независимый административный доступ отзывает ключ PaaS
- **THEN** удаляется разрешение только соответствующего публичного ключа
- **AND** новая аутентификация этим ключом отклоняется, основной доступ сохраняется
- **AND** результат не объявляет уже открытые сессии или отдельные API-токены отозванными

### Requirement: SSH-доступ использует отдельного Linux-пользователя

Подготовка сервера SHALL обеспечивать отдельную Linux-учётную запись `paas`
для подключений PaaS. Первоначальное создание пользователя и установка публичного
ключа SHALL выполняться через существующий административный доступ оператора.

#### Scenario: Первоначальная подготовка пользователя
- **WHEN** оператор подготавливает сервер без пользователя paas
- **THEN** создаётся пользователь paas и его доступ по отдельному ключу PaaS
- **AND** дальнейшая SSH-установка PaaS выполняется от его имени
- **AND** основной пользователь и его ключи сохраняются

#### Scenario: Пользователь уже существует
- **WHEN** учётная запись paas уже существует
- **THEN** подготовка проверяет её пригодность без удаления пользователя и его данных
- **AND** существующие разрешённые ключи не заменяются целиком

### Requirement: Административная подготовка отделена от полномочий daemon

Доверенный этап CLI через SSH SHALL выполнять административную подготовку узла,
создание Namespace приложений и начальную настройку прав до передачи управления
daemon. Daemon SHALL работать внутри k3s с отдельным ServiceAccount и получать
только необходимые права на ресурсы приложений в подготовленных Namespace.
Он SHALL NOT получать SSH-ключ оператора, sudo, административный kubeconfig,
права изменения Namespace, RBAC/admission-защиты, системных workloads и собственного
развёртывания, создания произвольных PersistentVolume, доступа к nodes/proxy,
impersonation или других способов выдачи себе дополнительных полномочий.
Кластер SHALL независимо применять Pod Security Restricted в режиме enforce
во всех Namespace, где daemon может создавать workloads. Daemon SHALL NOT иметь
возможности ослабить эти настройки или получить исключение. Проверка манифестов
в daemon SHALL дополнять, а не заменять ограничение Kubernetes.

#### Scenario: Передача подготовленного приложения daemon
- **WHEN** оператор создаёт приложение через PaaS
- **THEN** доверенный этап CLI подготавливает Namespace, защитные настройки и начальные права
- **AND** daemon управляет ресурсами приложения в установленных границах

#### Scenario: Попытка daemon расширить полномочия
- **WHEN** daemon пытается изменить защитные настройки Namespace, RBAC, системный workload или собственное развёртывание
- **THEN** Kubernetes отклоняет действие из-за отсутствия необходимых прав

#### Scenario: Попытка получить доступ к узлу через Pod
- **WHEN** daemon создаёт workload с нарушением Restricted, например privileged или hostPath
- **THEN** Kubernetes отклоняет создание Pod независимо от проверки в daemon

### Requirement: Установщик подготавливает отсутствующий k3s

Установщик PaaS SHALL определять наличие k3s на выбранном сервере и устанавливать
его закреплённую в конфигурации версию, если k3s отсутствует. Подготовка компонентов
PaaS SHALL начинаться после готовности кластера.

#### Scenario: Установка на сервер без k3s
- **WHEN** оператор запускает установку PaaS на сервере без k3s
- **THEN** установщик проверяет требования сервера и устанавливает заданную версию k3s
- **AND** после готовности кластера продолжает подготовку PostgreSQL и control plane PaaS

#### Scenario: Повторная установка с существующим кластером
- **WHEN** на выбранном сервере уже доступен совместимый k3s
- **THEN** установщик использует существующий кластер без переустановки
- **AND** сохраняет существующие ресурсы и credentials

#### Scenario: Существующий кластер недоступен или несовместим
- **WHEN** k3s обнаружен, но его готовность или совместимость не подтверждена
- **THEN** установщик сообщает причину и не переустанавливает кластер автоматически
- **AND** отсутствие доступа не трактуется как отсутствие установленного k3s

### Requirement: Traefik обеспечивает внешний HTTPS и автоматическое продление сертификатов

В первой версии PaaS SHALL использовать один экземпляр встроенного Traefik k3s
для внешнего HTTP/HTTPS-доступа к приложениям. Traefik SHALL получать и автоматически
продлевать управляемые сертификаты через ACME. Caddy и отдельный сервис продления
SHALL NOT требоваться. Состояние ACME, включая ключи и сертификаты, SHALL храниться
на постоянном томе, недоступном обычным workloads приложений, и сохраняться при
пересоздании Pod. Настройки Traefik SHALL управляться PaaS.

#### Scenario: Получение и продление сертификата
- **WHEN** через PaaS настроен HTTPS-маршрут с доменом и выполнены условия выбранной ACME-проверки
- **THEN** Traefik получает сертификат и автоматически продлевает его до истечения срока
- **AND** оператору не требуется вручную заменять сертификат или запускать отдельный сервис продления

#### Scenario: Пересоздание Traefik
- **WHEN** Pod Traefik пересоздаётся после успешного получения сертификата
- **THEN** сохранённое состояние ACME и сертификаты остаются доступны Traefik
- **AND** пересоздание Pod само по себе не требует повторной регистрации ACME-аккаунта и выпуска действующего сертификата

### Requirement: HTTP-01 и перенаправление HTTP на HTTPS управляются платформой

Платформа SHALL использовать один активный ACME resolver встроенного Traefik с
явными HTTPS CA directory endpoint, регистрационным email и путём приватного
постоянного storage. В первой версии SHALL поддерживаться только HTTP-01.
Опубликованные A/AAAA, непосредственно или через CNAME, SHALL вести на ожидаемые
публичные адреса узла; неработающий опубликованный AAAA SHALL NOT игнорироваться
из-за работающего IPv4. Внешние TCP80 для HTTP-01 и TCP443 для приложения, DNS-разрешение
и исходящий HTTPS к CA SHALL быть доступны. Ошибки DNS/сети/challenge SHALL NOT
считаться успешной настройкой TLS.
Установщик SHALL настроить штатный HTTP→HTTPS redirect Traefik. HTTP-01 SHALL
обслуживаться встроенным solver без передачи challenge пользовательскому backend;
allowACMEByPass SHALL оставаться false. Приоритет solver и совместимость redirect
SHALL проверяться на закреплённой версии. Маршруты непосредственно на
/.well-known/acme-challenge, /.well-known/acme-challenge/ и внутри этого поддерева
SHALL отклоняться. Широкие Prefix / и /.well-known SHALL оставаться допустимыми
без перехвата HTTP-01 на HTTP entrypoint. Пользователь SHALL NOT менять redirect,
entrypoint или solver через annotations/middleware. При проблеме TLS платформа
SHALL NOT включать HTTP-доступ к пользовательскому backend.

#### Scenario: Root маршрут и ACME challenge
- **WHEN** приложение использует Prefix / и центр сертификации выполняет HTTP-01
- **THEN** solver обслуживает challenge, не передавая его пользовательскому backend
- **AND** обычный HTTP-запрос перенаправляется на HTTPS

### Requirement: Готовность TLS определяется внешней наблюдаемой проверкой

TLS SHALL иметь отдельный статус от Deployment, backend readiness и миграций.
Внешний paas-ctl SHALL выполнять проверку по запросу операции/статуса без нового
постоянного сервиса мониторинга и без доступа daemon к acme.json.
Проверка SHALL связывать DNS с ожидаемым endpoint платформы и выполнять TLS handshake
на нём с каноническим hostname в SNI. Сертификат SHALL проходить обычную проверку
доверенной цепочки, SAN/hostname, NotBefore и NotAfter без отключения проверки.
Сертификат другого сервера SHALL NOT подтверждать готовность выбранного узла.
READY SHALL означать успешное наблюдение из указанной точки в указанное время;
результат SHALL содержать checkedAt и срок действия сертификата. Без новой проверки
SHALL показываться последний результат с его временем без утверждения непрерывной
доступности. До результата SHALL использоваться PENDING, завершённая неуспешная
проверка SHALL давать ERROR с наблюдаемой причиной. Timeout, DNS/connection error,
недоверенная цепочка, чужой hostname или недействительный срок SHALL NOT давать READY.
Статус SHALL NOT придумывать точную ACME-причину по отсутствию сертификата или
неустойчивому парсингу логов.
До первого пригодного сертификата endpoint MAY предъявлять default certificate
Traefik; PaaS SHALL NOT считать его готовым/доверенным или рекомендовать обход
проверки сертификата. Первая версия SHALL NOT обещать блокировку TLS handshake
до первого сертификата и SHALL NOT требовать дополнительного SNI strict.
Продлением SHALL управлять Traefik. Ошибка renewal SHALL NOT удалять действующий
сертификат/state, отключать TLS, включать HTTP backend или автоматически откатывать
Deployment/БД. Действительный наблюдённый сертификат MAY оставаться READY с отдельным
предупреждением при достоверно известной ошибке renewal; иначе SHALL показываться
срок и предупреждение о приближении истечения без выдуманного renewal failed.
После истечения или новой неуспешной проверки текущий READY SHALL NOT сохраняться.
Автоматические повторы SHALL ограничиваться подтверждённым поведением версии;
PaaS SHALL NOT обещать восстановление первичного выпуска после любой ошибки CA.
Для неустранившейся ошибки SHALL документироваться явная повторная проверка и,
при необходимости, контролируемый restart Traefik с сохранением state.

#### Scenario: Проверка сертификата и неверного endpoint
- **WHEN** paas-ctl проверяет HTTPS домена выбранного приложения
- **THEN** READY возможен только для ожидаемого endpoint и доверенного действительного сертификата с нужным hostname
- **AND** результат содержит время проверки и срок сертификата отдельно от состояния backend

#### Scenario: Ошибка продления или истечение
- **WHEN** renewal не удался либо новая внешняя проверка сертификата неуспешна
- **THEN** ACME state не удаляется, HTTP backend не включается, Deployment и БД автоматически не откатываются
- **AND** неуспешная проверка не сохраняет текущий READY

### Requirement: ACME state сохраняется и имеет единственного writer

Приёмка SHALL сначала использовать staging CA; тестовый результат SHALL явно
отличаться от production READY. Тестовые корни SHALL NOT добавляться в системное
доверенное хранилище. Переход на production SHALL быть явным изменением профиля
установки с новой обычной проверкой доверия. Staging и production SHALL использовать
отдельные файлы state на одном приватном постоянном PVC при одном активном resolver.
Смена endpoint CA SHALL NOT очищать или перезаписывать production state.
PVC SHALL быть недоступен обычным workloads и daemon; приватный файл SHALL иметь
ограниченные права, подходящие пользователю Traefik. Активный файл SHALL записываться
не более чем одним процессом Traefik одновременно, включая upgrade: Recreate либо
эквивалентный порядок SHALL останавливать прежний процесс до запуска нового.
replicas=1 или ReadWriteOnce SHALL NOT считаться достаточным доказательством одного
writer. Перезапуск SHALL сохранять state; zero-downtime SHALL NOT обещаться.
Первое создание пустого state SHALL отличаться от утраты существовавшего.
При потере/повреждении/недоступности прежнего state запуск SHALL NOT молча создавать
новый пустой файл с массовым перевыпуском; SHALL требоваться восстановление либо
явно выбранная процедура восстановления с перевыпуском.
До эксплуатации SHALL быть определены и проверены защищённые backup/restore,
согласованность копии, сохранение прав и восстановление при остановленном writer.
Место копии и механизм SHALL определяться на инфраструктурном этапе.

#### Scenario: Перезапуск upgrade или утрата ACME state
- **WHEN** Traefik перезапускается либо обновляется
- **THEN** прежний state сохраняется без двух одновременно пишущих процессов
- **AND** потеря прежнего state требует восстановления или явно выбранного перевыпуска

#### Scenario: Переход от staging к production
- **WHEN** оператор явно меняет профиль на production после тестовой проверки
- **THEN** используется отдельный production state и новая обычная проверка доверия
- **AND** staging-сертификат не считается production READY

### Requirement: Домены регистрируются за приложением через PaaS

Оператор SHALL явно регистрировать домен за приложением через CLI/TUI.
Один домен SHALL принадлежать только одному приложению; приложение SHALL иметь
возможность зарегистрировать несколько доменов. Host в пользовательском YAML
SHALL NOT регистрировать домен или подтверждать право его использования.
Компоненты приложения SHALL иметь возможность использовать его домены с разными
путями по согласованному профилю маршрутов Ingress.
Ingress SHALL использовать только явные доменные имена, зарегистрированные
за его приложением. Чужие или незарегистрированные домены, wildcard и правила
без host SHALL отклоняться до применения пакета.
Смена и удаление регистрации SHALL выполняться отдельными операциями PaaS;
отсутствие Ingress в пакете SHALL NOT автоматически удалять регистрацию домена.
Регистрация внутри PaaS SHALL NOT считаться настройкой DNS или подтверждением
домена центром сертификации.
Удаление регистрации или смена владельца SHALL проверять все сохранённые Ingress
и незавершённые резервы; занятый домен SHALL отклонять операцию без изменения чужих
маршрутов. Удаление регистрации SHALL NOT обещать удаление сертификата из ACME state
или прекращение renewal. PaaS SHALL NOT редактировать работающий acme.json для очистки.

#### Scenario: Компоненты используют домен приложения
- **WHEN** компоненты одного приложения описывают разные разрешённые пути на зарегистрированном за ним домене
- **THEN** PaaS проверяет маршруты без требования отдельного домена каждому компоненту

#### Scenario: Чужой или незарегистрированный домен
- **WHEN** Ingress ссылается на домен другого приложения либо домен без регистрации в PaaS
- **THEN** пакет отклоняется до применения и регистрация домена не меняется

#### Scenario: Wildcard или правило без host
- **WHEN** Ingress содержит wildcard host или правило без host
- **THEN** пакет отклоняется до применения как неподдерживаемый внешний маршрут

#### Scenario: Ingress отсутствует в следующем пакете
- **WHEN** новый пакет компонента не содержит прежний Ingress
- **THEN** регистрация домена приложения сохраняется до отдельной операции

### Requirement: Домены канонизируются одинаково при регистрации и в Ingress

Регистрация домена, rules.host и явно заданные TLS hosts SHALL использовать одну
канонизацию: непустой ASCII-ввод, перевод A–Z в a–z, удаление не более одной
завершающей DNS-точки. Затем имя SHALL содержать минимум два непустых DNS labels,
каждый не более 63 символов, всё имя не более 253. Label SHALL содержать только
a–z, 0–9 и дефис с буквой/цифрой на концах.
Пробелы SHALL NOT обрезаться. URL, scheme, port, path, credentials, wildcard,
IP literals, localhost и имена под .localhost SHALL отклоняться. Unicode SHALL
отклоняться с предложением передать ASCII A-label; другие исправления и сокращения
SHALL NOT выполняться. Label xn-- SHALL быть корректным IDNA A-label с проверкой
обратимого соответствия A-label/U-label и точного канонического ASCII результата.
PaaS SHALL использовать готовую библиотеку IDNA со строгой валидацией, а не сырой
Punycode-кодек. Эта проверка SHALL NOT преобразовывать пользовательский Unicode-ввод.
Каноническое имя SHALL использоваться в ownership, уникальности, резервировании,
Ingress host и TLS host и показываться в диагностике. Проверка синтаксиса SHALL NOT
подтверждать существование DNS или права на домен.

#### Scenario: Эквивалентные доменные имена
- **WHEN** оператор передаёт API.Example.COM. при регистрации или в Ingress
- **THEN** PaaS использует api.example.com для проверки принадлежности и конфликтов

#### Scenario: Некорректное доменное имя
- **WHEN** ввод содержит пробелы, URL, двойную завершающую точку, Unicode, недопустимый label или некорректный IDNA A-label
- **THEN** операция отклоняется без эвристического исправления имени

### Requirement: Class TLS и annotations Ingress управляются PaaS

spec.ingressClassName SHALL определяться закреплённым профилем Traefik: пропуск
или пустое значение заполняется, точное совпадение принимается, другое отклоняется.
Аннотация kubernetes.io/ingress.class SHALL NOT приниматься.
Отсутствующий/пустой spec.tls SHALL заполняться одной записью с hosts, содержащим
единственный канонический rules.host, без secretName. Непустой spec.tls SHALL
содержать ровно одну запись и ровно один совпадающий после канонизации host,
без непустого secretName; иной состав SHALL отклоняться. Пустой secretName SHALL
считаться отсутствием ссылки. PaaS SHALL NOT создавать сертификатные Kubernetes
Secrets для этого профиля.
Во входном Ingress SHALL допускаться только четыре annotations с префиксом
traefik.ingress.kubernetes.io/: router.priority, router.entrypoints, router.tls,
router.tls.certresolver. Все SHALL быть строками с точными ожидаемыми значениями:
вычисленный decimal priority, единственный настроенный HTTPS entrypoint, true,
единственный настроенный ACME resolver соответственно. Пропуски SHALL заполняться,
конфликты и остальные входные annotations SHALL отклонять пакет. Это включает
middlewares, pathmatcher, rulesyntax, tls.options и tls.domains.*.
Непустая карта пользовательских Service annotations SHALL отклоняться; пустая
или отсутствующая SHALL приниматься. Допустимые labels SHALL сохраняться по
ранее согласованным правилам. Эти ограничения SHALL относиться к пользовательскому
вводу и SHALL NOT требовать удаления annotations, добавляемых в живой объект
Kubernetes/доверенным контроллером. Они SHALL NOT автоматически копироваться
обратно во входной пользовательский пакет.

#### Scenario: Управляемые поля отсутствуют
- **WHEN** Ingress не содержит class TLS и управляемые annotations
- **THEN** PaaS заполняет их значениями своего профиля и каноническим host

#### Scenario: Обход через аннотацию или сертификатный Secret
- **WHEN** пользователь передаёт конфликтующий class/TLS, непустой secretName, неподдерживаемую Ingress annotation или непустые Service annotations
- **THEN** пакет отклоняется до применения

### Requirement: Маршруты Ingress однозначны и проверяются в пределах приложения

Каждый пользовательский Ingress SHALL содержать ровно один `spec.rules[]` с явным
host и ровно один `http.paths[]`. Пакет SHALL допускать несколько Ingress со
стабильными именами; PaaS SHALL NOT создавать скрытые Ingress для разбиения ресурса.
`spec.defaultBackend` и `backend.resource` SHALL NOT приниматься.
`pathType` SHALL явно задаваться как Prefix или Exact; отсутствие значения и
ImplementationSpecific SHALL отклоняться. Пути SHALL проходить Kubernetes-валидацию
выбранной версии и сопоставляться регистрозависимо. Prefix SHALL совпадать по
сегментам: /api соответствует /api, /api/ и /api/users, но не /apix; Prefix /
SHALL быть fallback только своего host. Exact SHALL совпадать с полным путём.
PaaS SHALL NOT добавлять rewrite или StripPrefix.

PaaS SHALL включать `providers.kubernetesIngress.strictPrefixMatching=true`;
поддержка и поведение SHALL проверяться на закреплённой версии k3s/Traefik.
Отсутствие поддержки SHALL означать несовместимость, а не посимвольный Prefix.
PaaS SHALL задавать `traefik.ingress.kubernetes.io/router.priority`: 2*L+1 для Prefix,
2*L+2 для Exact. L SHALL быть длиной пути в байтах UTF-8 после удаления завершающего
slash у Prefix, кроме корня; путь Exact SHALL оставаться буквальным. Расчёт SHALL
проверять переполнение и положительный результат не более 2147482647.
Пользователь SHALL NOT менять вычисленный priority, matcher, rule syntax или
middleware; пропуск управляемого значения SHALL заполняться, конфликт SHALL
отклонять пакет. Более длинный подходящий путь SHALL выигрывать.

Daemon SHALL проверять пакет против маршрутов всего приложения, включая старые
Ingress вне пакета и резервы незавершённых операций. Тот же Ingress SHALL обновляться
без конфликта с собой. Проверка и резервирование SHALL исключать гонку разных
компонентов. Сбой обновления SHALL NOT освобождать прежний маршрут другому владельцу
до установления результата изменения Kubernetes. Проверка SHALL NOT обещать
атомарное переключение трафика. Вложенные пути SHALL допускаться. Дубликаты SHALL
отклоняться независимо от backend. Prefix SHALL сравниваться без завершающего slash,
кроме корня; Exact SHALL сравниваться буквально. Exact и Prefix с одинаковыми host
и сравниваемым путём SHALL NOT сосуществовать.

Backend SHALL быть Service своего компонента и Namespace из пакета либо состояния
PaaS. Его port SHALL содержать ровно одно name/number и соответствовать TCP-порту
`Service.spec.ports[].name`/`port`, а не targetPort. Проверка SHALL учитывать
результирующий Service после обновления. Изменение Service SHALL NOT оставлять
сохранённые Ingress со ссылками на удалённые/переименованные порты, включая Ingress
вне текущего пакета.
В первом профиле backend SHALL обслуживать обычный HTTP. Выбранный Ingress порт
Service SHALL NOT иметь port 443 или имя с началом https; проверка SHALL выполняться
по фактическому порту независимо от ссылки по имени/номеру и охватывать сохранённые
Ingress при обновлении Service. targetPort 443 сам по себе SHALL NOT запрещаться
или считаться включением TLS. Внутренние HTTPS/h2c и ServersTransport SHALL NOT
поддерживаться в первом профиле. Остальные порты Service без Ingress этим правилом
SHALL NOT ограничиваться.

Prefix и Exact SHALL трактоваться как буквальные пути; regex-режимы и их annotations
SHALL NOT поддерживаться. Daemon SHALL NOT распознавать regex эвристически по символам.
Объявленные paths SHALL NOT содержать percent-encoded последовательности или
обратную косую черту; daemon SHALL NOT URL-декодировать, менять регистр или сворачивать
сегменты при регистрации. Недопустимые Kubernetes query/fragment и формы сегментов
SHALL отклоняться. Отсутствие rewrite SHALL NOT обещать побайтовую передачу любого
некорректного/закодированного request-target. Поведение входящих encoded paths и
штатной очистки пути Traefik SHALL проверяться отдельно для закреплённой версии.

#### Scenario: Строгий Prefix и Exact
- **WHEN** запросы проверяются на Prefix /api и Exact /health
- **THEN** /api и /api/users совпадают с Prefix, /apix не совпадает
- **AND** /health совпадает с Exact, а /health/ не совпадает

#### Scenario: Вложенные маршруты разных компонентов
- **WHEN** существуют Prefix /, Prefix /api и Exact /api/health на одном домене приложения
- **THEN** /api/health выбирает Exact, /api/users выбирает Prefix /api, остальное выбирает Prefix /

#### Scenario: Дубликат или конкурентное резервирование
- **WHEN** другой Ingress занимает тот же маршрут, включая эквивалентный Prefix с завершающим slash или резерв незавершённой операции
- **THEN** пакет отклоняется до применения без перехвата чужого маршрута

#### Scenario: Обновление Service нарушает прежний Ingress
- **WHEN** пакет удаляет или переименовывает порт Service, используемый сохранённым Ingress вне пакета
- **THEN** пакет отклоняется до применения с указанием нарушенной ссылки

### Requirement: Общий PostgreSQL доступен control plane

PaaS SHALL использовать обязательный PostgreSQL для состояния control plane
и переиспользовать этот экземпляр для отдельных БД приложений.

#### Scenario: Запуск платформы
- **WHEN** завершается первоначальная установка PaaS
- **THEN** PostgreSQL доступен, состояние control plane хранится в отдельной БД
- **AND** приложения не получают credentials control plane

### Requirement: Дополнительная инфраструктура создаётся по потребности

PaaS SHALL создавать поддерживаемый дополнительный общий сервис при первом запросе
приложения и переиспользовать существующий экземпляр при следующих запросах.

#### Scenario: Нет потребителей дополнительного сервиса
- **WHEN** ни одно приложение не запросило дополнительный сервис
- **THEN** PaaS не устанавливает его заранее

#### Scenario: Повторный запрос общего сервиса
- **WHEN** два приложения запрашивают один поддерживаемый сервис
- **THEN** используется один общий экземпляр, включая одновременные запросы
- **AND** ресурсы и права приложений подготавливаются отдельно

### Requirement: Версии управляются конфигурацией платформы

PaaS SHALL требовать явно закреплённую версию устанавливаемого компонента
в конфигурации платформы до начала его установки.

#### Scenario: Версия отсутствует
- **WHEN** требуется установить компонент без заданной версии
- **THEN** операция завершается понятной ошибкой до установки компонента

### Requirement: Штатное управление ресурсами выполняется через PaaS

PaaS SHALL предоставлять штатные операции управления ресурсами через CLI/TUI и API
платформы. Пользовательские манифесты SHALL проходить проверку daemon до применения.
Документация SHALL рекомендовать не обращаться к Kubernetes API в обход PaaS
и объяснять, что прямые изменения управляемых ресурсов могут нарушить согласованность
состояния платформы и кластера. Прямые административные изменения SHALL NOT считаться
штатным сценарием с гарантированным автоматическим восстановлением согласованности.

#### Scenario: Штатное изменение ресурсов
- **WHEN** оператор изменяет управляемый ресурс через PaaS
- **THEN** операция проходит проверки daemon и учитывается в состоянии платформы

#### Scenario: Рекомендация оператору
- **WHEN** оператор изучает документацию по управлению ресурсами
- **THEN** документация рекомендует использовать PaaS и избегать прямых обращений к Kubernetes API в обход платформы
- **AND** объясняет риск рассинхронизации при прямых изменениях

### Requirement: Пользовательские манифесты ограничены начальным набором ресурсов

В первой версии PaaS SHALL принимать в пользовательском пакете только
`apps/v1 Deployment`, `v1 Service` типа `ClusterIP`, `v1 ConfigMap` и
`networking.k8s.io/v1 Ingress`. Неподдерживаемые виды или версии ресурсов и Service
другого типа SHALL отклоняться до начала применения пакета с указанием ресурса,
причины и поддерживаемых вариантов. Отсутствующий `Service.spec.type` SHALL
трактоваться как `ClusterIP`.
Namespace, служебные Secrets, ServiceAccount/RBAC, NetworkPolicy, Job мигратора
и постоянные тома инфраструктуры SHALL создаваться операциями PaaS.
Пользовательские Job, CronJob, StatefulSet и PersistentVolumeClaim SHALL NOT
приниматься в этом этапе. Разрешённый вид ресурса SHALL NOT освобождать его
от проверки защищённых полей и принадлежности приложению.
Для Ingress PaaS SHALL проверять принадлежность домена и backend приложения
и управлять выбором Traefik и ACME resolver.

#### Scenario: Пакет из поддерживаемых ресурсов
- **WHEN** оператор передаёт Deployment, Service типа ClusterIP, ConfigMap и Ingress в поддерживаемых версиях API
- **THEN** daemon проверяет их поля и привязки до применения
- **AND** служебные ресурсы создаются соответствующими операциями PaaS

#### Scenario: Неподдерживаемый ресурс в пакете
- **WHEN** пакет содержит неподдерживаемый вид, версию ресурса или Service другого типа
- **THEN** PaaS отклоняет пакет до начала его применения и сообщает причину и поддерживаемые варианты
- **AND** остальные ресурсы этого пакета не применяются

### Requirement: Namespace определяется приложением операции деплоя

PaaS SHALL определять целевой Namespace по приложению операции деплоя.
Отсутствующий `metadata.namespace` SHALL заполняться целевым значением; явно
совпадающее значение SHALL приниматься. Любое другое значение, включая `default`,
SHALL приводить к отказу до начала применения пакета, без WARN и автоматической
замены. Диагностика SHALL указывать ресурс, путь поля и ожидаемый Namespace.

#### Scenario: Namespace пропущен или совпадает
- **WHEN** ресурсы пакета не указывают Namespace либо указывают Namespace выбранного приложения
- **THEN** PaaS использует Namespace приложения для всех ресурсов пакета

#### Scenario: Чужой Namespace
- **WHEN** хотя бы один ресурс явно указывает другой Namespace
- **THEN** пакет отклоняется до применения с указанием поля и ожидаемого Namespace
- **AND** ресурсы пакета не применяются

### Requirement: Идентичность и принадлежность ресурсов учитываются PaaS

Пользовательский ресурс SHALL иметь явное стабильное `metadata.name`;
`generateName` SHALL NOT приниматься. PaaS SHALL идентифицировать ресурс по API group,
типу ресурса, Namespace и имени, без включения версии API. При первом создании
PaaS SHALL сохранять принадлежность ресурса приложению и единственному компоненту в своём состоянии;
пользовательская метка SHALL NOT считаться подтверждением принадлежности.
До изменения Kubernetes PaaS SHALL сохранять намерение создания, идентичность,
владельца и стабильный ID ресурса. Повтор операции после сбоя SHALL использовать
те же записи и ID без автоматического присвоения произвольных неизвестных объектов.
Параллельные операции одного компонента SHALL сериализоваться либо явно отклоняться
как конфликтующие. Предварительная проверка пакета SHALL NOT считаться гарантией
транзакционного применения ресурсов Kubernetes.
Повторный деплой SHALL обновлять тот же ресурс только в пределах разрешённых полей.
Конфликт со служебным ресурсом, другим владельцем или объектом вне учёта PaaS
SHALL отклоняться без автоматического присвоения ресурса приложению.
Дубликаты идентичности в пакете SHALL отклоняться до начала его применения.
Новое имя SHALL означать новый ресурс и SHALL NOT приводить к автоматическому
удалению старого; переименование и удаление SHALL требовать явной операции.

#### Scenario: Повторный деплой ресурса приложения
- **WHEN** ресурс с той же идентичностью уже учитывается PaaS за выбранным приложением
- **THEN** PaaS обновляет его разрешённые поля без изменения принадлежности

#### Scenario: Конфликт или дубликат идентичности
- **WHEN** пакет содержит конфликт со служебным ресурсом, другим владельцем, объектом вне учёта PaaS либо повторяющуюся идентичность
- **THEN** PaaS отклоняет пакет до начала его применения и объясняет конфликт
- **AND** существующий ресурс не присваивается приложению автоматически

#### Scenario: Имя отсутствует или генерируется
- **WHEN** ресурс не содержит metadata.name либо использует metadata.generateName
- **THEN** пакет отклоняется до применения с требованием явного стабильного имени

#### Scenario: Изменение имени в манифесте
- **WHEN** оператор передаёт ресурс с новым именем вместо ранее использованного
- **THEN** PaaS рассматривает его как новый ресурс с проверкой конфликтов
- **AND** прежний ресурс не удаляется автоматически

### Requirement: Служебные метки и selectors формируются из состояния PaaS

PaaS SHALL управлять следующими метками:
- `app.kubernetes.io/part-of` — стабильный ID приложения;
- `app.kubernetes.io/component` — стабильный ID компонента;
- `app.kubernetes.io/instance` — стабильный ID экземпляра компонента, представленного Deployment;
- `app.kubernetes.io/managed-by` — информационное значение `paas`.

Deployment metadata и Pod template SHALL содержать три метки идентичности и
`managed-by`. Metadata Service, ConfigMap и Ingress SHALL содержать ID приложения,
компонента и `managed-by`. ID SHALL быть непустыми, стабильными и соответствовать
формату значений Kubernetes labels: не более 63 символов, ASCII-буква или цифра
на концах, внутри также допустимы `-`, `_`, `.`. Изменение отображаемого имени
или релиза SHALL NOT менять ID; обрезание имени с риском коллизии SHALL NOT
использоваться вместо стабильной идентичности.
`Deployment.spec.selector.matchLabels` и `Service.spec.selector` SHALL содержать
ровно три метки идентичности целевого Deployment. Непустые
`Deployment.spec.selector.matchExpressions` SHALL NOT приниматься.
Пропущенные управляемые ключи меток SHALL заполняться; заданные SHALL проверяться
во всех перечисленных местах. Отсутствующий или пустой selector SHALL генерироваться;
явно заданный непустой SHALL полностью совпадать с ожидаемым. Противоречащие метки
идентичности и selectors SHALL приводить к отказу до начала применения пакета.
Только расхождение `managed-by` SHALL исправляться с WARN после проверки владения.
Допустимые описательные метки SHALL сохраняться и SHALL NOT участвовать в выдаче
сетевых/секретных полномочий или подтверждать ownership. Свобода пользовательских
меток SHALL NOT распространяться на управляемые ключи и системные метки контроллеров,
включая `pod-template-hash`.

#### Scenario: Метки или selector пропущены
- **WHEN** пакет не содержит управляемые ключи меток либо содержит отсутствующий или пустой selector
- **THEN** PaaS заполняет их ожидаемыми значениями из своего состояния до применения

#### Scenario: Противоречащие метки или selector
- **WHEN** в metadata Deployment, Pod template либо других управляемых местах задана неверная метка идентичности или selector не совпадает целиком
- **THEN** PaaS отклоняет пакет до применения с указанием поля и ожидаемого значения

#### Scenario: Информационная метка отличается
- **WHEN** принадлежность ресурса подтверждена, но managed-by отличается от paas
- **THEN** PaaS выводит WARN и использует значение paas без изменения владельца

#### Scenario: Повтор после частичного сбоя
- **WHEN** операция прервана после сохранения намерения и частичного применения Kubernetes-ресурсов
- **THEN** повтор использует сохранённые ID и selectors без генерации новой идентичности
- **AND** неизвестные объекты не присваиваются приложению только по совпавшим меткам

### Requirement: Сетевые связи приложений разрешаются явно

Платформа SHALL закрывать сетевые связи между разными приложениями по умолчанию;
необходимые связи SHALL разрешаться явно через PaaS у компонента-источника к Service
целевого приложения. Встречное разрешение получателя SHALL NOT требоваться.
Обратное инициирование соединения SHALL требовать своего разрешения; ответный
трафик разрешённого соединения SHALL проходить без отдельного обратного разрешения.
Компоненты одного приложения SHALL по умолчанию иметь возможность свободного
сетевого взаимодействия между собой; схема переключателя этой связи ещё открыта.

Внешний доступ SHALL задаваться отдельно для каждого компонента режимом none,
allowlist или all; по умолчанию SHALL применяться none. None SHALL закрывать
внешний доступ; allowlist SHALL разрешать только точные домены из конфигурации;
разрешение родительского домена SHALL NOT автоматически разрешать поддомены.
Поддомены SHALL задаваться отдельными записями; маски, включая *.example.com,
SHALL отклоняться.
all SHALL разрешать весь внешний интернет. Список SHALL содержать домены без
портов; разрешение домена SHALL распространяться на все его порты, включая
протоколы почтовых сервисов. All SHALL NOT сам по себе разрешать внутренние адреса
платформы, узла или Kubernetes API. Исполнение доменного allowlist, DNS/IP-сопоставления
и защита от прямого IP-обхода отложены пользователем в PAAS-012. Связанные требования
и сценарии сохраняются как целевой контракт, не как выполненный механизм первой
версии. До реализации и проверки список SHALL NOT считаться гарантией сетевого
запрета. Временное поведение первой реализации требует отдельного согласования;
allowlist SHALL NOT молча заменяться на all. Служебные исключения пока открыты.

Мигратор SHALL иметь только DNS и подключение к целевой PostgreSQL. Он SHALL NOT
наследовать внешний доступ и межкомпонентные разрешения обычных компонентов;
доступ к компонентам, другим приложениям и внешним API SHALL быть закрыт.

#### Scenario: Связь разных приложений без разрешения
- **WHEN** компонент обращается к другому приложению без явного разрешения PaaS
- **THEN** сетевое соединение запрещено

#### Scenario: Связь компонентов одного приложения
- **WHEN** обычный компонент обращается к другому компоненту того же приложения
- **THEN** отдельное разрешение межкомпонентной связи не требуется

#### Scenario: Внешний API отсутствует в списке
- **WHEN** компонент в режиме allowlist обращается к внешнему API вне разрешённого ему списка
- **THEN** исходящее соединение запрещено

#### Scenario: Почтовый сервис на разрешённом домене
- **WHEN** компонент в режиме allowlist подключается к почтовому сервису на разрешённом домене
- **THEN** порт подключения не ограничивается значением 443 и не требует отдельной записи в списке

#### Scenario: Разрешение домена не распространяется на поддомены
- **WHEN** в allowlist указан только example.com и компонент обращается к api.example.com
- **THEN** соединение запрещено до отдельного разрешения api.example.com

#### Scenario: Маска во внешнем allowlist
- **WHEN** оператор указывает *.example.com в списке разрешённых внешних доменов
- **THEN** конфигурация отклоняется с требованием указать точные имена

#### Scenario: Одностороннее разрешение между приложениями
- **WHEN** компонент-источник имеет разрешение на Service другого приложения
- **THEN** соединение и ответы разрешены без встречного разрешения получателя
- **AND** это не разрешает получателю самостоятельно инициировать обратное соединение

#### Scenario: Мигратор не наследует весь интернет
- **WHEN** обычный компонент имеет внешний режим all и запускается миграция
- **THEN** мигратор по-прежнему имеет только DNS и доступ к целевой PostgreSQL

### Requirement: Служебные ресурсы и поля управляются через PaaS

Созданные PaaS NetworkPolicy, Secrets и полномочия мигратора SHALL управляться PaaS
целиком. В пользовательских workloads PaaS SHALL защищать Namespace, идентификаторы,
служебные метки принадлежности/доступа и привязки credentials. Такие настройки SHALL
изменяться через CLI/TUI. Обычные пользовательские метки SHALL оставаться доступными
для редактирования.

#### Scenario: Некритичное расхождение защищённого поля
- **WHEN** манифест содержит отличающееся значение защищённого поля без нарушения изоляции
- **THEN** PaaS выводит WARN с путём поля, ожидаемым значением, допустимыми вариантами и способом корректного изменения
- **AND** при применении сохраняется значение, управляемое PaaS

#### Scenario: Изменение нарушает изоляцию
- **WHEN** входной манифест пытается перенести workload в чужой Namespace или использовать недоступные ему полномочия
- **THEN** PaaS отклоняет операцию до применения ресурсов и объясняет причину

### Requirement: Общий бизнесовый сервис переиспользуется

PaaS SHALL позволять объявить сервис на уровне платформы один раз и SHALL позволять
владельцу явно выбирать приложения, которым разрешено подключение. По умолчанию
доступ других приложений SHALL быть запрещён. Сервис SHALL обновляться независимо
от приложений-потребителей. Конкретный механизм задания списка разрешённых
приложений не определяется этим требованием.
Каждое приложение и каждый общий сервис SHALL размещаться в отдельном Kubernetes
Namespace. PaaS SHALL применять NetworkPolicy, обеспечивающие доступ только для
явно разрешённых потребителей.

#### Scenario: Разрешённые потребители сервиса
- **WHEN** владелец сервиса явно разрешил двум выбранным приложениям подключение
- **THEN** оба приложения используют один экземпляр сервиса
- **AND** приложения получают способ подключения к сервису без прямых credentials его БД

#### Scenario: Доступ между несвязанными приложениями запрещён
- **WHEN** приложение не указано среди разрешённых потребителей сервиса
- **THEN** PaaS запрещает ему сетевой доступ и не выдаёт credentials для подключения к сервису

#### Scenario: Изоляция пространствами имён и сетевыми правилами
- **WHEN** PaaS создаёт приложение или общий сервис
- **THEN** workload размещается в отдельном Namespace
- **AND** сетевой доступ между Namespace разрешается только созданными PaaS правилами для выбранных потребителей
