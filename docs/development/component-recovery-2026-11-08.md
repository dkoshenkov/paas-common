# Хранение и восстановление операции деплоя

На отдельной однодовой установке k3s v1.37.2+k3s1 с PostgreSQL 18.6
зарегистрировали два компонента одного приложения. Оба реально запустились.

| Что проверено | Наблюдение |
| --- | --- |
| Обновление из TUI | После подтверждения UPDATE операция `a2e2d7dc3e170b19de3dc62b5ff4be96` достигла SUCCEEDED. Kubernetes показал две доступные реплики. |
| Независимость | Операция `6b5cf9d9f1deca43bd6659aea0fba6b4` обновила первый компонент. У соседнего остались тот же UID Deployment `856dbcc8-2edd-416e-95da-d0534266c534`, generation 1, образ и UID Pod `0b9a6f88-b888-4ae4-b6f4-f1d7709a32d0`. В Namespace этого приложения миграционных Jobs не появилось. |
| Перезапуск во время rollout | Для операции `f7be3987e528201c321267e7c3e71a3e` ввели minReadySeconds 35, дождались RUNNING/WAIT_READY и удалили тестовый Pod daemon. Новый Pod продолжил операцию. Результат — SUCCEEDED, UID управляемого Deployment `51e0b80c-91cc-44a0-88cc-72a51bbea4a2` и generation 4 сохранились. |
| Повтор принятого запроса | После замены Pod daemon прежний preview_id вернул исходный operation_id. |
| Недоступность PostgreSQL | При остановке БД процесс сохранял доступный /health, возвращал 503 на /ready и восстановил готовность после запуска БД. [Проверка на ноде](tui-node-check-2026-11-07.md). |

Приёмка относится к хранению состояния control plane (3.3). Для 5.1 ещё проверяется
независимое обновление приложения с уже выполненной первоначальной миграцией;
для 7.1 предстоит объединить прикладные БД, ручную миграцию и изоляцию в одном сценарии TUI.
