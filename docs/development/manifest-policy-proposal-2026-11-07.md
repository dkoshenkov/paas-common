# Предложение для 1.1 и 2.3.3. Метаданные и проверка деплоя на одной ноде

**Решение 7 ноября 2026 года.** Пользователь одобрил первую группу 1.1/2.3.3,
включая семь маршрутов и их DTO, метаданные, защищённые поля, временный отказ
allowlist, стадии и квоты исполнения. Формы отдельной app-scoped миграции и
последующего деплоя с миграцией требуют следующего решения. Точная матрица
первой группы находится в [delta](../../openspec/changes/define-k3s-paas-foundation/specs/independent-deployments/spec.md#requirement-первая-группа-sdk-для-регистрации-и-политик). На сегодня SDK уже описывает preview/apply, а daemon читает каталог и историю. Производителя операций и API записи политик ещё нет. Номера этапов, статусы и пределы ниже нужно читать с учётом этого различия.

Основание — пять действующих delta: [пакеты и операции](../../openspec/changes/define-k3s-paas-foundation/specs/independent-deployments/spec.md), [инфраструктура и сеть](../../openspec/changes/define-k3s-paas-foundation/specs/shared-infrastructure/spec.md), [доступ к БД](../../openspec/changes/define-k3s-paas-foundation/specs/application-database-access/spec.md), [секреты](../../openspec/changes/define-k3s-paas-foundation/specs/application-secrets/spec.md), [TUI](../../openspec/changes/define-k3s-paas-foundation/specs/operator-tui/spec.md). Фактический состав генерируемого SDK задаёт [корневой Flux YAML](../api/paas/api.yaml).

## Что вводит оператор

Предлагается хранить настройки в PostgreSQL control plane. Оператор меняет их через экран приложения в Bubble Tea. При деплое он по-прежнему передаёт только `app_id`, `component_id` и исходные YAML-файлы. Дополнительный файл манифеста, произвольные аннотации и отображаемое имя приложения не дают полномочий.

| Владелец настройки | Предложение | Как проверить |
| --- | --- | --- |
| Приложение | Неизменный `app_id`, отображаемое `name`. Отдельная необязательная конфигурация `migrator.image`. Для первой итерации предлагаем неизменяемую OCI-ссылку с digest SHA-256. Удаление настройки — отдельное явное действие. | Два приложения с одинаковым именем различимы по выданным сервером ID. Переименование сохраняет ID и Namespace. На чистом приложении без мигратора БД не создаётся. Удаление мигратора после подготовки БД сохраняет БД, обе роли, Secrets и действующий доступ. |
| Домен приложения | Регистрация и снятие регистрации по одному каноническому домену. Глобальная уникальность на ноде. Занятый маршрут или активный резерв блокирует снятие. Список в форме приложения читается из реестра доменов. | Регистрация `Orders.Example.COM.` и использование `orders.example.com` обозначают один домен. Попытка другого приложения зарегистрировать его отклоняется. |
| Компонент | Стабильный `component_id` и неизменная принадлежность приложению. Версии образов и имена контейнеров берутся из Deployment. Права связаны со стабильной идентичностью Deployment (group, kind, Namespace и name), типом контейнера `container/init` и точным Kubernetes-именем. | Переименование Deployment, замена обычного контейнера одноимённым init-контейнером и появление sidecar не переносят разрешение. Несуществующий потребитель не получает доступ. Наличие привязки само по себе не добавляет Secret в Pod. |
| Credentials БД | Привязка относится только к логическому `app_database` своего приложения. Предлагаем список разрешённых ключей или явное `whole_secret`; оба одновременно запрещены. Имя служебного Secret и названия доступных ключей TUI получает у daemon без значений. | `secretKeyRef` требует разрешённого ключа; `envFrom` и volume без `items` требуют всего Secret. При `items` проверяются все ключи для каждого монтирующего контейнера. Secret мигратора недоступен при любом варианте привязки. |
| Сеть компонента | `external.mode` — `none` по умолчанию, `all` по явному выбору. `allowlist` временно отклоняется, см. ниже. Направленное разрешение обычной связи у источника содержит `target_app_id`, `target_component_id`, `service_name`; daemon разрешает ссылку только в учтённый Service указанного владельца. В пределах приложения обычные компоненты общаются по умолчанию; для v1 предлагаем не вводить отдельный переключатель. | Запись от A к Service B допускает установление соединения A → B и ответы B. Решение не позволяет B инициировать соединение к A. Удалённый или сменивший идентичность Service не наследует допуск. |
| Общий бизнесовый сервис | Отдельная сущность `shared_service_id`, свой Namespace и свой цикл обновления. Владелец сервиса ведёт множество `allowed_app_ids`; по умолчанию оно пусто. Обычная межкомпонентная ссылка не обходит этот список. Разрешённое приложение получает адрес прикладного сервиса. | Два разрешённых приложения используют один экземпляр. Третье приложение не может к нему подключиться. Ни одно не получает credentials его БД. |

По этому предложению сервер создаёт ID один раз в допустимом для Kubernetes labels формате. В `AppSummary` и `ComponentSummary` остаются только согласованные идентичности и имена до 128 байт UTF-8. TUI открывает настройки отдельным запросом. Основание — [DTO каталога](../api/paas/catalog_types.yaml).

Пример **предлагаемого** тела записи политики компонента. Здесь `deployment_name` разрешается в Namespace приложения и проверяется по учёту владения. До первого деплоя допустима привязка к будущему имени конкретного Deployment собственного компонента; резервирование имени и проверка, что объект свободен или принадлежит этому компоненту, происходят при apply.

```json
{
  "app_id": "app-orders",
  "component_id": "cmp-api",
  "expected_revision": "r7",
  "policy": {
    "database_grants": [
      {"deployment_name": "api", "container_kind": "container", "container_name": "api", "keys": ["password"]}
    ],
    "external": {"mode": "none", "domains": []},
    "service_grants": [
      {"target_app_id": "app-billing", "target_component_id": "cmp-billing", "service_name": "billing-api"}
    ]
  }
}
```

Отсутствующий мигратор и пустой список привязок — разные состояния. После первого принятия daemon связывает привязку с сохранённым instance ID. При явном удалении Deployment привязку нужно закрыть: новое воплощение с тем же именем не получает старое разрешение. Уже подготовленная БД продолжает существовать после удаления настройки мигратора. Изменение разрешения на Secret не удаляет копию значения из уже работающего процесса. Предлагаем блокировать снятие привязки, пока её использует учтённый или незавершённый workload. TUI указывает связанный Deployment; оператор сначала убирает потребление из YAML, применяет пакет и дожидается замены прежних Pods. Экстренный отзыв с ротацией пароля требует отдельной операции. Аналогично, изменение сетевых разрешений нельзя объявлять исполненным до применения и проверки обеих сторон NetworkPolicy.

## Границы SDK и полномочий

Для решения 2.3.3 предлагаем согласовывать небольшие группы статических HTTP-путей. Идентификаторы чтения передаются через query, команды — JSON body. В примерах используются пути-кандидаты. Первой итерации достаточно каталога записи и настроек; остальных контрактов требует полный операторский сценарий.

| Итерация | Предлагаемая граница |
| --- | --- |
| Регистрация и настройки | `POST /apps/create`, `POST /components/create` возвращают 201 и соответствующий Summary. Для безопасного повтора выдачи ID от клиента нужен стабильный `request_id`: тот же payload даёт 200 и прежнюю запись, другой с тем же ключом — 409. Регистрацию приложения daemon связывает с фактом доверенной подготовки Namespace через ctl/SSH. Создание Namespace и начального RBAC делает привилегированная операция узла. Для компонентов — `GET /components/policy`, `POST /components/set-policy` с полной политикой, `expected_revision` и ответом с новой revision, для конфигурации мигратора — отдельные get/set/remove в пространстве `/apps/`. Начальная revision возвращается чтением даже для пустой политики. |
| Домены и общие сервисы | Команды регистрации/снятия и чтения доменов по `app_id`; создание/чтение общего сервиса и допуск/отзыв потребителя по `shared_service_id,app_id`. Реквизиты общей инфраструктуры в команду потребителя не входят. Явный отзыв сетевого допуска учитывает активные резервы. |
| Управление приложением после деплоя | Предусмотреть отдельное чтение версий образов, preview обновления выбранного контейнера по сохранённому пакету и новый снимок с явным подтверждением. Для отдельного Goose up и его логов требуется цель «приложение»: действующий Operation требует непустой `component_id`. Предлагаем в отдельном решении распространить DTO операции и чтение истории на цель приложения с различимым типом, мигрировать существующие записи как компонентные и проверить старых клиентов. Фиктивный компонент не заводится. Явный последующий деплой с миграцией также требует согласования новой формы плана: текущий AdditionalAction разрешает только INITIAL_MIGRATION. |
| Секреты и состояние | Узкая операция явного получения сохранённых DB credentials одной из двух ролей через защищённый UDS, без кэширования/логирования. Обычные ответы каталога, статуса, сырой истории и TUI не переносят значения. Статус/безопасные логи операции и результат внешней проверки TLS с checkedAt и сроком сертификата нужны для экранов «Приложение» и «Операции». GHCR остаётся у доверенного helper узла, открытый токен не передаётся daemon. |

Для set-policy предлагаем 200 при сохранении, 400 для неверной формы, 404 для неизвестной цели или чужого компонента, 409 `POLICY_CHANGED` для устаревшей revision и 503 при недоступности хранилища. Сверка revision и запись выполняются атомарно. После потери ответа клиент перечитывает политику. Уникальность, связи и идемпотентность проверяет приложение в транзакции с конкурентной защитой по правилам каталога; проверить применимость общей транзакционной микробиблиотеки packages-go до написания адаптера. Новая revision сама по себе не заменяет согласованное сравнение полного internal plan при apply. Для операций записи политики, меняющих работающую сеть, необходимо показывать сохранённое намерение и результат применения раздельно; соответствующий контракт согласуется до появления таких команд в TUI.

Сгенерировать эти группы можно только после утверждения точных DTO и матрицы ошибок соответствующей итерации. Сейчас `apps.yaml` и `logs.yaml` с Compose-полями и путями по имени не импортируются в корневой профиль. Прежние `GET /apps/get`, `GET /components/get`, `POST /deployments/preview` и `POST /deployments/apply` сохраняют свои тела. [Действующий профиль SDK](../api/paas/api.yaml) · [Рабочие DTO](../api/paas/types.yaml).

## Объекты и защищённые пути

Для всего пакета действует один порядок: строгий разбор YAML и схемы закреплённого API, затем проверка владельца, ссылок, защищённых полей и изоляции, затем построение плана. Неизвестные поля, дубликаты ключей и неподдерживаемые виды ресурсов предлагаем отклонять целиком до изменений. При отсутствии ошибки допустимо только документированное заполнение. Единственная предлагаемая замена явно конфликтующего значения с WARN — уже согласованный `managed-by`. В таблице `*` обозначает каждый элемент; в реальной диагностике передаётся JSON Pointer с номером элемента и экранированием ключей.

| Объект и путь входа | Политика |
| --- | --- |
| Корневые `/apiVersion`, `/kind` | Ровно один apps/v1 Deployment, дополнительно v1 Service, v1 ConfigMap и networking.k8s.io/v1 Ingress. Namespace, ServiceAccount, RBAC, Secret, NetworkPolicy, Job мигратора, PV/PVC/StorageClass, HelmChartConfig, CRD и весь системный Namespace принадлежат платформе. Любой другой объект пакета — ERROR. Namespace и начальные права готовит доверенная операция ctl, оператор управляет ими через PaaS. |
| У каждого объекта `/metadata/{name,generateName,namespace}` | Стабильное имя обязательно, generateName запрещено; Namespace пропущен — подставить, совпал — принять, иной, включая default, — ERROR. Проверить owner/UID по учёту и живому объекту, отказать при дубликате или конфликте. Пакет не присваивает и не удаляет неуказанный ресурс. |
| У всех `/metadata/{uid,resourceVersion,generation,managedFields,ownerReferences,finalizers,creationTimestamp,deletionTimestamp,deletionGracePeriodSeconds}`, `/status`; метаданные Pod template | Предлагаем запрещать серверные поля и управление удалением во входе, включая пустые подстановки. Метаданные шаблона принимать только в форме допустимых labels/annotations. Объект, возвращённый Kubernetes целиком, требует подготовки перед отправкой в PaaS. |
| `/metadata/labels`, `/spec/template/metadata/labels`, `/spec/selector` | У Deployment и шаблона — part-of, component, instance и managed-by; у Service/ConfigMap/Ingress — part-of, component и managed-by. Ключи имеют префикс `app.kubernetes.io/`. Всякое несовпадение идентичности — ERROR. managed-by заполняется значением paas; явное другое — WARN с точным путём, ожидаемым значением и указанием управления через PaaS. Описательные labels свободны. Платформенные метки сетевых допусков и системные метки контроллеров (например pod-template-hash) запрещены во входе. Selector пуст — сгенерировать, иначе требуется точное равенство трём меткам Deployment, без дополнительных выражений. |
| Service `/spec` | Только ClusterIP, выбранные порты и selector своего Deployment. Предлагаем принимать обычные `ports[].{name,port,protocol,targetPort}` и запрещать явное управление clusterIP/clusterIPs, externalIPs/externalName, nodePort, loadBalancer*, healthCheckNodePort и другими путями обхода изоляции. Пустая/отсутствующая карта annotations допустима. Для Ingress backend ссылается на фактический TCP port/name Service; для такого порта запрещены 443 и имена с началом https, независимо от targetPort. Именованный targetPort разрешается в заявленный порт одного из контейнеров своего Deployment. Проверить зависимости прежних Ingress при изменении Service. |
| Ingress `/spec/{ingressClassName,tls,rules,defaultBackend}`, `/metadata/annotations` | Один точный зарегистрированный host, одно правило и один путь Exact/Prefix на Service своего компонента и существующий порт. defaultBackend и backend.resource запрещены. Отсутствующие class/TLS и четыре разрешённые Traefik-аннотации заполняются по профилю, явные значения проверяются точно. Произвольные annotations, непустой TLS secretName и иной backend — ERROR. Правила канонизации, совпадения путей, приоритета, резервирования и HTTP-01 применяются целиком из delta. |
| Deployment `/spec/template/spec` и `containers/*`, `initContainers/*` | SA только ожидаемый для обычного приложения, automountServiceAccountToken=false. Предлагаем запрещать alias serviceAccount, imagePullSecrets, ephemeralContainers, hostNetwork/hostPID/hostIPC=true, hostPort, hostPath/CSI/PVC, projected serviceAccountToken, внешние устройства, произвольные runtimeClassName, nodeName и DNS/nodes-переопределения. Запретить host в HTTP/TCP probes и сетевых lifecycle hooks, через которые kubelet подключался бы к чужой цели. Применять Linux Pod Security Restricted в daemon и независимо enforce в Namespace. Обходы через capabilities, privileged, procMount, sysctls, seccomp и служебные volumes отклонять. Для отсутствующих параметров Restricted предлагаем безопасные значения пакета (runAsNonRoot, RuntimeDefault, allowPrivilegeEscalation=false, drop ALL). |
| Deployment, Pod template, ConfigMap `metadata.annotations`; ссылки на ConfigMap/Secret и volumes | Предлагаем по умолчанию отклонять их пользовательские annotations до согласования конкретной необходимости. ConfigMap содержит только несекретные данные; ссылки через env, envFrom и прямые/составные volumes — только на ConfigMap этого компонента. Для Secret допустимы четыре согласованных механизма: secretKeyRef, envFrom.secretRef, volumes.secret, projected.sources.secret. Проверить каждый контейнер и init-контейнер с mount, включая subPath и все составляющие projected volume. optional=true не снимает проверку. Мигратор, токен SA, state ACME, файл GHCR и сокет daemon недоступны обычным Pods. |

Справочные таблицы доменов, маршрутов и Secret-форм входят в приёмку по ссылкам выше. При обновлении daemon защищает UID/resourceVersion и сохраняет поля чужого менеджера, включая аннотации доверенного контроллера. Запрет YAML-поля не означает удаление этого поля из живого объекта.

## Сеть до реализации PAAS-012

Предлагаем **отклонять попытку включить allowlist** с кодом `EGRESS_ALLOWLIST_UNAVAILABLE` и оставлять прежнюю политику без изменений. В TUI видны текущий режим, отказ и причина. Для новой цели фактический режим — none. Если уже действовал all, отказ оставляет all; интерфейс должен сказать об этом прямо и дать явно выбрать none. Нельзя показывать отказанный список как частичное ограничение.

Если в сохранённой конфигурации обнаружен allowlist, а исполняемого механизма нет, новая операция деплоя блокируется. Для уже работающего компонента daemon должен установить политику none и подтвердить результат; пока проверка не прошла, статус — «изоляция не подтверждена», с блокировкой новых запусков. При отсутствии доказанной изоляции Kubernetes для этого сценария включение поддержки существующих работающих приложений потребует отдельной процедуры. Целевой список для PAAS-012 — точные DNS-имена без портов и wildcard, все порты каждого имени, поддомен только отдельной записью.

У none остаются только необходимые внутрикластерные разрешения: DNS через назначенный кластерный resolver, согласованные внутриприкладные и явные межсервисные связи, БД по утверждённому профилю. Межсервисный допуск ограничивает целевые Pods и реально опубликованные Service протоколы и targetPorts. Политика, разрешающая лишь целевой Namespace целиком, не исполняет контракт. На этапе 4.3 проверить выбор нескольких Services с одинаковыми Pods и границы их портов, подключение к ClusterIP и прямому Pod IP. Трафик ответа и инициирование обратных соединений различаются. Мигратор получает только DNS и целевой PostgreSQL. Для all проверять из тестового Pod, что прямые IP ноды, localhost хоста, metadata/link-local, Pod/Service сети инфраструктуры, API Kubernetes и их эквиваленты по IPv6 недоступны вне явных разрешений; проверять обход через Service, DNS и поведение фактически установленного CNI. Если изоляцию нельзя обеспечить на этом кластере, all не активируется. Штатный вход Traefik проверяется отдельно. [Цель и отложенное исполнение PAAS-012](../backlog/paas.md#paas-012--исполнение-доменного-allowlist-исходящих-соединений).

## Этапы, диагностика и предел активных операций

Предлагаем следующие значения открытого строкового `stage` нового производителя. При ACCEPTED до первого действия поле отсутствует. При остановке сохраняется последний достигнутый этап, в том числе в RECOVERY_REQUIRED. Старые неизвестные значения отображаются безопасно. Восстановление проверяет сохранённые намерения и UID, а не начинает последовательность заново.

| Stage деплоя | Когда этап пройден |
| --- | --- |
| PREPARE_RESOURCES | Сверены подготовленный Namespace, владение и зависимости. Установлены требуемые сетевые ограничения и служебные привязки до запуска Pod. Если нужна БД, БД/роли/Secrets приготовлены или переиспользованы. |
| INITIAL_MIGRATION | Только если есть подтверждённое дополнительное действие первого запуска. Успех защищённого Job установлен по его UID и состоянию завершения. Существующий Job после рестарта наблюдается по прежнему UID. Новый Job после ошибки автоматически не создаётся. |
| APPLY_RESOURCES | Подтверждённый пакет применён с условиями владения/версии. Deployment допускается к запуску после успеха обязательной операции подготовки схемы. Service/Ingress не публикуют трафик до применения сетевых ограничений. |
| WAIT_READY | Для предлагаемого профиля `replicas >= 1`: у собственной актуальной generation Deployment достигнуты целевые updated, ready и available replicas и завершено снятие прежних реплик. Для опубликованных backends подтверждены готовые EndpointSlice нужного Service с ожидаемыми Pod UID и портом. У worker без Service достаточно его Deployment. TLS PENDING/READY/ERROR показывается отдельно независимо от SUCCEEDED. |

Предлагаем предел ожидания rollout 10 минут по времени сервера от сохранённого начала WAIT_READY, с продолжением исходного срока после рестарта. Истечение инициирует сверку фактических последствий. Если старое действие ещё может выполняться и безопасный итог не установлен, результат должен остаться RECOVERY_REQUIRED. Для долгого Goose up время ожидания UI не завершает Job; отдельный deadline мигратора нуждается в решении на этапе 5.2. Отдельный ручной up будет иметь собственный этап MIGRATE_DATABASE после решения по типу цели.

| Семейство | Код, ответ и применение |
| --- | --- |
| Существующие HTTP-ошибки | 400 INVALID_REQUEST, 413 BODY_TOO_LARGE, 404 NOT_FOUND, 409 COMPONENT_BUSY с обязательным conflicting_operation_id, 409 PLAN_CHANGED / RECHECK_FAILED, 503 DEPENDENCY_UNAVAILABLE / ACCEPTANCE_UNKNOWN / PREVIEW_CAPACITY_EXCEEDED. Для согласованного 410 предлагаем закрепить PREVIEW_EXPIRED, уже использованный в контрактном тесте. После удаления записи возвращается 404. |
| Диагностика корректного envelope | В `200 PreviewResponse` предлагаем ERROR с кодами YAML_INVALID, YAML_LIMIT, RESOURCE_UNSUPPORTED, RESOURCE_CONFLICT, FIELD_FORBIDDEN, SECRET_BINDING_DENIED, SERVICE_REFERENCE_INVALID, ROUTE_CONFLICT, EGRESS_ALLOWLIST_UNAVAILABLE. WARN MANAGED_FIELD_NORMALIZED — только для managed-by. При любом ERROR отсутствуют plan, preview_id и expires_at. Вызов записи политики с неподдерживаемым allowlist получает 409 EGRESS_ALLOWLIST_UNAVAILABLE. |
| Исполнение | В Operation предлагаем применять MIGRATION_FAILED, RESOURCE_APPLY_FAILED и ROLLOUT_NOT_READY с безопасным пояснением; согласованные OUTCOME_KNOWN_PARTIAL и OUTCOME_UNKNOWN сохраняются при соответствующих последствиях. Причина и state передаются раздельно. CONFLICT по БД или временному резерву маршрута с известным владельцем предлагается выразить 409 DATABASE_BUSY / ROUTE_BUSY и реальным conflicting_operation_id. Постоянный конфликт маршрута не имеет такой ссылки. |
| Ограничение вывода | Предлагаем до 32 Diagnostic на ответ preview/операцию, code 64, message 1024, field_path 512 байт UTF-8. Весь сериализованный публичный Operation ≤64 KiB. Сохранить приоритет причин ERROR и обеих применимых OUTCOME, оставить место для DIAGNOSTICS_TRUNCATED при превышении числа/байтов. Усечение списка выполняется детерминированно; внутренний план для согласования WARN сравнивает все предупреждения, включая невместившиеся. Если оператору нельзя показать все исправления, требующие подтверждения, preview возвращает ERROR DIAGNOSTICS_TRUNCATED без применимого ID. Вместившиеся WARN сами по себе не делают preview ошибочным. Нельзя скрыть первый ERROR, обе причины частичного/неизвестного результата или изменить результат проверки из-за сокращения. Для ошибки конкретного документа остаются точные file и document. Пользовательские значения, YAML, Secret, DSN, необработанные исключения и diff не включаются. |
| Совместимость писателя с историей | Входной file уже допускает 512 байт, а действующий history reader — 256 байт. Предлагаем сначала расширить только допустимый file читаемого Diagnostic до 512 и проверить старые записи, сохраняя бюджет 64 KiB. Затем включать writer. При сокращении диагностик нельзя усечь имя файла и выдать его за имя из снимка. Для большого/чувствительного ключа карты допустим безопасный JSON Pointer до самой карты. |

Предлагаем **до 4 активных операций и до 256 MiB их сохранённых снимков на ноду**. Числа — начальная настройка для обсуждения, замеров производительности под ними пока нет. Учитываются ACCEPTED, RUNNING и RECOVERY_REQUIRED. Используется та же закреплённая логическая сериализация input + internal plan + diagnostics, что для preview; для принятия бюджет резервируется атомарно. Чтобы рост рабочих диагностик не исчерпал резерв посреди исполнения, предлагаем учитывать отдельно фиксированный запас 64 KiB на операцию. Бюджет 256 MiB относится только к первоначальным снимкам; отдельный резерв публичного состояния — не более 4 × 64 KiB суммарно. Поэтому один допустимый снимок размером ровно 256 MiB может быть принят на свободной ноде. Это квота принятия работы. PostgreSQL/WAL и Kubernetes-постоянные данные требуют независимого учёта места.

Сначала ищется уже принятая связь, затем занятость компонента, БД и маршрутов и, при новом принятии, срок preview, повторная проверка плана и общая ёмкость под блокировками. Два конкурентных приёма не превышают лимит. Если свободной ёмкости нет, новая попытка получает 503 ACTIVE_CAPACITY_EXCEEDED без вымышленной блокирующей операции, очереди или запуска Job. Действующий preview сохраняется до своего TTL. Повтор для уже связанного preview возвращает 200 и прежний ID, в том числе при заполненной ноде. Освобождение активной квоты согласовано с доказанным SUCCEEDED/FAILED. Резервы неизвестного исхода сохраняются до ручной сверки, терминальная история — 30 дней. Независимая квота неиспользованных preview остаётся 64/256 MiB, TTL 30 минут.

## Проверяемые случаи для приёмки

1. **Разрешённый Secret и sidecar.** У `api` разрешён только ключ password, в пакете `containers[0].env[0].valueFrom.secretKeyRef` ссылается на него. Добавление того же через envFrom или secret-том у sidecar без разрешения даёт 200 preview с ERROR SECRET_BINDING_DENIED, точными file/document и JSON Pointer, без ID. Текст и логи не содержат значение ключа.
2. **Ресурсы и предупреждения.** У корректного Deployment `metadata.labels["app.kubernetes.io/managed-by"]="tool"` даёт WARN с путём `/metadata/labels/app.kubernetes.io~1managed-by`, ожиданием paas и указанием управлять ресурсом через PaaS. Добавление `metadata.namespace=default` в пакет приложения с иным Namespace даёт ERROR, без изменений Kubernetes.
3. **Гонка политик.** Сохранить preview при действующем разрешении. Затем отозвать ещё не используемое разрешение и применить старый ID. Если план теперь недопустим — 409 RECHECK_FAILED; если допустим, но изменился подтверждаемый план — 409 PLAN_CHANGED. Ни операция, ни доступ не создаются.
4. **Временный allowlist.** На компоненте с mode none запросить allowlist для mail.example.com. Ожидается 409, прежняя revision и подтверждённый none. Повторить на компоненте с all — получить отказ с сохранённым all. Отдельный явный переход на none должен действительно блокировать внешний TCP 25 и 443 с Pod.
5. **Квота и восстановление.** Одновременно применить пять валидных preview разных независимых компонентов при свободном бюджете размера. Не больше четырёх первых 202; оставшийся — 503. Для повторного apply уже принятого ID ожидается 200. После перезапуска RECOVERY_REQUIRED продолжает занимать место. Повторить с двумя большими снимками так, чтобы общий бюджет превысился раньше счётчика.
6. **Граница истории.** Обработать имена файлов длиной 256, 257 и 512 байт и диагностический путь с символами / и ~. Ошибка конкретного документа после принятия возвращает исходное имя в GET операции, безопасный RFC 6901 pointer и сериализованный JSON не более 65 536 байт. Прогнать с 33 причинами и с максимальными длинами строк.
7. **HTTP/SDK.** После утверждения выбранной группы добавить source Flux, сгенерировать HTTP/OpenAPI дважды закреплённым генератором, проверить идентичность артефактов и сохранность common/gRPC. Вызвать generated client/server для новых успешных DTO, отказов и неизвестных полей. Повторить существующие preview/apply, каталог и чтение сохранённой истории с прежними DTO. Контрактные тесты, отдельная проверка PostgreSQL и live k3s покрывают разные части результата.

**Объём рассмотренного предложения:** (1) хранение политик и границу первой группы API, привязку к Deployment и ключам Secret, immutable digest мигратора; (2) реестр защищённых путей и выбранный временный отказ allowlist; (3) stages, readiness и таймаут; (4) число/размер активных операций, диагностику и расширение history file с 256 до 512; (5) отдельно выбрать форму app-scoped операции и способ явного последующего деплоя с миграцией до генерации соответствующего SDK. Их принятие само по себе не завершает 1.1 или 2.3.3: потребуются изменения delta и проверенные результаты реализации.
