# SQL-доступ из workload на v5-fresh

8 ноября 2026 года на k3s со схемой v12 разрешение на ключи `paas-app-db` выдано до первого деплоя приложения `775a2a48bfcc40d7b57e02998ef9d32c`. Операция `03f551806afb21d865878da78ed63c69` подготовила БД и завершилась SUCCEEDED. Разрешённый контейнер получил реквизиты через `secretKeyRef`; из этого контейнера psql исполнил `SELECT current_user` под выделенной ролью APPLICATION.

Проверка preview отклонила ссылку из другого контейнера в том же Pod, Secret мигратора и ключ вне разрешённого набора. Соседний workload не смог открыть соединение с PostgreSQL. Пока Deployment использовал ключи, попытка сузить разрешение получила HTTP 409. Деплой `2cc7bd7d8275d9ed54350dc965b392d4` убрал ссылку. После rollout сужение получило HTTP 200. UID Deployment `2bc9c588-0ff5-4748-934a-9e5088d3dbdb` и UID Deployment соседнего приложения сохранились. [Сценарий SQL и сужения](../../../paas-ctl/scripts/testdata/workload-database-live.py).

На отдельном приложении `3d9395d33fb14bd58a969baf231acfb4` первый деплой с разрешением прошёл. В тесте администратор заменил Deployment одноимённой копией. Его UID изменился с `e0d49c4e-0ba6-47fe-8c26-3bda5b91d28f` на `8214ec92-d01d-4375-a8ee-68792afd5c3b`, а Secret сохранил UID. Preview вернул HTTP 503 без preview_id. Таким образом, старое разрешение через PaaS применить к копии не удалось. [Сценарий подмены](../../../paas-ctl/scripts/testdata/workload-database-uid-live.py).

На изолированном PostgreSQL 18.6 проверены гонки при первом занятии имени Deployment и при конкуренции workload apply с отзывом доступа или удалением БД. При моделировании потери ответа после CREATE PostgreSQL сохранял настоящий журнал, а Kubernetes обрабатывал тестовый клиент. После отмены контекста заново созданный worker не послал второй CREATE и не присвоил чужой UID. Резерв остался доступным для разбора операции. Физического падения процесса в этом сценарии не вводили.

Обновление существующей ноды, повтор install-postgres, фактические SQL-права и границы проверки свежей установки описаны в [профиле v12](workload-database-access-proposal.md#проверка-установки-схемы-v12--8-ноября-2026).
