# Сверка пользовательских сценариев однодовой установки

Срез 8 ноября относится к `define-k3s-paas-foundation`. Таблица охватывает проверенные пользовательские маршруты и известные пробелы приёмки. Октябрьская матрица в design.md фиксирует более ранний этап SDK.

| Сценарий | Наблюдение и открытая часть |
| --- | --- |
| Установка и каталог через SSH | В PTY проверены установка, четыре основных экрана, история, потеря готовности при остановке PostgreSQL и чтение после холодного старта. [Приёмка TUI](tui-node-check-2026-11-07.md). |
| Независимый деплой и восстановление worker | Деплой через TUI завершился SUCCEEDED. При смене Pod daemon worker продолжил WAIT_READY. В сокращённом сценарии оператор выбрал один контейнер, проверил план и подтвердил обновление. На отдельном rollout сменились digest и ответ v1 → v2, соседний Deployment сохранил UID и spec. [Восстановление](component-recovery-2026-11-08.md) и [обновление образа](image-preview-node-check-2026-11-08.md). |
| БД приложений и выдача credentials | Проверены изоляция SQL-ролей, явная выдача credentials, вход из разрешённого контейнера и отказ старой привязке после замены UID Deployment. Отзыв завершил активную сессию выбранной роли. Удаление одной БД сохранило соседнюю. [Изоляция](app-database-isolation-2026-11-08.md), [привязка к workload](workload-database-node-check-2026-11-08.md), [отзыв и удаление](database-lifecycle-node-check-2026-11-08.md). |
| Миграции | Проверены остановка деплоя при ошибке, первый успешный деплой, ручная миграция и продолжение Job после перезапуска daemon. На v5-fresh TUI и UDS показали VERSION_APPLIED при первом запуске и NO_PENDING_MIGRATIONS при повторе. [Приёмка миграций](initial-database-deploy-2026-11-08.md). |
| Владение доменом | С тестовым именем в зоне .invalid через Unix-сокет на схеме v8 регистрация вернула 201 и каноническое имя в нижнем регистре без конечной точки. Повтор вернул 200. Другой app_id получил 409 DOMAIN_CONFLICT. После снятия регистрации оба списка вернулись в исходное состояние. Отдельно пройдены регистрация и отзыв через [TUI](tui-node-check-2026-11-07.md#дополнительная-приёмка-на-control-check-8-ноября). Для внешнего TLS остаются отдельные проверки DNS, endpoint и сертификата. |
| Общий сервис | Два разрешённых приложения получили ответы сервиса по DNS и ClusterIP до и после независимого обновления; третьему приложению доступ был закрыт. Проверены отзыв и подмена UID. На этом стенде новое TCP-соединение после отзыва отклонялось, а существующее продолжало передавать данные. Отдельный статус пары доступен через TUI. [Приёмка общего сервиса](shared-service-node-check-2026-11-08.md). |
| Сеть обычного компонента | При одной NetworkPolicy новый адрес ноды был доступен Pod до обновления исключений. Добавление отдельной таблицы nftables на network-check закрыло этот путь и после холодного старта. Служебные Pod после перезапуска увидели новый Service и Ingress. При ошибке загрузки правил тестовый k3s остался остановлен. Для 5.5 открыты штатная установка и сквозная проверка политик обычных компонентов через PaaS. [Протокол стенда](component-network-node-check-2026-11-08.md) и [профиль узла](component-network-host-isolation-proposal-2026-11-08.md). |
| Внешний HTTPS | На tls-check тестовая CA подтвердила HTTP-01 и продление. После ручного восстановления внешний клиент увидел прежний сертификат. В ctl локально проверены TLS handshake, ошибки SAN и цепочки, а также сброс результата при смене сессии. Открыта приёмка штатного установщика, восстановления на новый PVC и отображения профиля в TUI. [Протокол и условия приёмки](registry-tls-node-proposal.md). |
| Ключи рабочих мест | Production-клиент по TLS прочитал три публичных Ed25519 из GitHub. Две страницы ответа, выбор ключа, запись на узле, SSH-вход и отзыв проверены отдельно с HTTPS-фикстурой и тестовым sshd. [Протокол и тест](tui-node-check-2026-11-07.md#импорт-и-отзыв-публичных-ed25519). |
| Приватный образ GHCR | На ghcr-check синтетический прогон проверил скрытый ввод через TUI, сохранение и возврат файла конфигурации и явный перезапуск k3s. При очистке этого прогона прежняя резервная версия файла была утрачена. Исправление возврата всех трёх файлов проверено локально. На ноде подтверждён отказ анонимной загрузки. Для закрытия нужен успешный pull приватного digest после ввода токена в TUI. [Проверка образа и ноды](registry-tls-node-proposal.md). |

По каждому из 77 требований составлена [матрица свидетельств](foundation-requirement-matrix.md). Для релизов трёх репозиториев подготовлен [отдельный change PAAS-006](../../openspec/changes/automate-single-node-releases/proposal.md). Открытые границы реализации и проверки сохраняются в [tasks.md](../../openspec/changes/define-k3s-paas-foundation/tasks.md). Kafka и полноценный CLI для автоматизации отложены в [продуктовом backlog](../backlog/paas.md).

### Проверка Ingress без подготовленного HTTPS-профиля

На control-check регистрация тестового имени прошла, но исходный preview пакета из Deployment, Service и Ingress ошибочно вернул план CREATE без диагностики. Этот preview не исполняли. В установленном Traefik 3.7.15 из chart `41.6.101+up41.6.1` не был настроен ACME resolver. В профиле, полученном daemon из хранилища, отсутствовали класс Ingress, HTTPS entrypoint и resolver. Поэтому этот вариант установки не мог подтвердить обещанный HTTPS.

После обновления daemon на `sha256:5970a817929571a96249601c9531e967a7c63945fa8daaab3f5f37d936907485` повтор того же preview вернул ERROR INGRESS_PROFILE_UNAVAILABLE без плана и ID. Запрос apply с прежним ID `5a967f4eeb278e59001f578730795168` получил HTTP 409 PLAN_CHANGED. Проверка Kubernetes подтвердила отсутствие трёх запрошенных объектов. Пакет с одними Deployment и Service получил обычный применимый preview. Тестовое имя `ingress-379a2e23f1.invalid` сняли через API; отдельный пустой тестовый компонент сохранился. Положительный rollout Ingress, запрет отзыва реально используемого домена и внешний сертификат требуют [подготовки профиля узла](registry-tls-node-proposal.md).

## Граница v1 по продуктовому backlog

Сверка относится к [PAAS-001–020](../backlog/paas.md). У каждого пункта отдельно указан объём, который влияет на однодовую v1.

| Пункт | Объём для этого выпуска |
| --- | --- |
| PAAS-001, окружения | На приложение с мигратором предусмотрена одна БД. Выбор нескольких окружений отложен. |
| PAAS-002, мониторинг | Соединения двух приложений и их миграторов уже различимы по БД и LOGIN. Состав общего мониторинга, сбор метрик и UI ещё требуют выбора. |
| PAAS-003, квоты PostgreSQL | Атрибуция есть. Лимиты потребления PostgreSQL приложениями относятся к будущему этапу. |
| PAAS-004, Kafka | Отложено. В 5.4 проверяется доступ к зарегистрированному общему бизнесовому сервису. |
| PAAS-005, среды исполнения | В рамках v1 проверяется k3s. Дополнительные среды исполнения требуют отдельного решения. |
| PAAS-006, релизы | Отдельный [change автоматизации](../../openspec/changes/automate-single-node-releases/proposal.md). У common опубликован тег v1.1.0, у ctl и daemon на момент сверки тегов в origin нет. |
| PAAS-007, мультинод | Относится к v2. Однодовый установщик проверен на отказ при обнаружении нескольких нод. |
| PAAS-008, доступ к таблицам | В v1 приложение использует собственную БД и отдельные LOGIN. Более узкие табличные права для отдельных компонентов отложены. |
| PAAS-009, переименование | Завершено в 0.1–0.4 текущего foundation change. |
| PAAS-010, imagePullSecrets | Переход на независимую выдачу через imagePullSecrets отложен. Для узлового helper v1 остаётся проверить авторизованную загрузку приватного образа на пустом кеше. |
| PAAS-011, усиленное хранение registry credentials | Последующее усиление хранения и обработки в памяти вынесено из v1. Приёмка прав узлового файла и защиты токена входит в текущий профиль GHCR. |
| PAAS-012, исходящий доменный allowlist | Исполнение доменного allowlist отложено. В v1 неподдерживаемый режим должен отклоняться до применения. |
| PAAS-013, роли операторов | В v1 один администратор PaaS. Несколько ролей отложены. |
| PAAS-014, внешний HTTPS управления | Управляющий API v1 использует SSH/UDS. Этот пункт отделён от пользовательского HTTPS приложений, который остаётся частью v1. |
| PAAS-015, синхронизация ключей | В v1 явные импорт и отзыв выбранных ключей проверены на sshd. Автоматическая синхронизация с GitHub отложена. |
| PAAS-016, пользовательские Secrets | Произвольные секреты вроде SMTP-пароля отложены. В текущем профиле требуется контролировать привязку прикладных DB credentials к контейнерам. |
| PAAS-017, метрики и дашборды как код | Отложено; состав этого расширения будет согласован отдельно. |
| PAAS-018, расширенные миграции | В v1 есть initial, manual и requested up. Очереди, автоматические повторы и дополнительные операции остаются кандидатами. |
| PAAS-019, восстановление узла и делегирование | Расширенное восстановление и делегирование отложены. Восстановление принятой операции после перезапуска daemon уже проверено на ноде. |
| PAAS-020, CLI для автоматизации | Интерфейс оператора в v1 — TUI; отдельный обычный CLI для автоматизации относится к v2. |

По смежным репозиториям сверены [потребности Flux](../backlog/flux.md) и [packages-go](../backlog/packages-go.md). Контракт GitHub использует генератор Flux v0.7.0, чтение снимка в daemon использует `pgxtx.ReadSnapshot` из packages-go v0.6.0.
