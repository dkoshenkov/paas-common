# Предложение: восстановление сетевого доступа общего сервиса (5.4)

8 ноября пользователь одобрил модель восстановления и реализацию этапа 5.4. Предложение дополняет согласованный API 5.4 и касается `paas-daemon`, схемы control DB и installer в `paas-ctl`. Номер миграции выбирается после сверки параллельных изменений.

## Идентичность и журнал

Для каждой пары «сервис — потребитель» reconciler хранит отдельный intent для ingress и egress: desired revision и allow, сторону, имя и UID Namespace, имя NetworkPolicy, случайный стабильный intent ID, каноническую спецификацию или её хеш и состояние операции. Namespace потребителя и его UID читаются из единственной действующей записи `paas_app_preparations` в той же транзакции, что и intent; Namespace владельца и Service UID сверяются с регистрацией. Перед записью в Kubernetes UID обоих Namespace и Service повторно читаются из API.

До каждого внешнего `create` intent фиксируется в БД. Создаваемый объект содержит его защищённый маркер. После ответа API UID и resourceVersion фиксируются сразу для каждой стороны, вместе с записью ownership, которую проверяет installer. При потере ответа reconciler ищет объект по сохранённому имени и принимает его только при совпадении Namespace UID, маркера, стороны и полной ожидаемой спецификации с intent; неоднозначность, несовпадение или чужой объект означают остановку и восстановление оператором. Для подтверждённого UID последующие изменения и удаление используют UID/resourceVersion preconditions. Метка сама по себе не доказывает владение: механизм предполагает, что посторонний субъект не может читать intent и создавать или менять NetworkPolicy в этих Namespace; эту границу RBAC необходимо проверить. Без неё усыновление объекта после потерянного ответа небезопасно и должно завершаться отказом.

Пара политик применяется идемпотентно; после сбоя между сторонами повтор продолжает сохранённый intent. Revoke устраняет разрешающие правила с обеих сторон и подтверждается только после readback обеих политик с deny-состоянием или проверенного отсутствия. Default-deny остаётся действующим. До подтверждения allow reconciler повторно читает обе политики, их UID, resourceVersion, спецификации и идентичности Namespace/Service, затем выполняет CAS по desired revision и Service UID. При несовпадении revision подтверждение отклоняется, адрес потребителю не выдаётся. Для v1 предлагается следующий порядок. Ответ set-access подтверждает сохранённый выбор оператора. С момента записи revoke список потребителя скрывает адрес. Пока у пары есть незавершённая операция Kubernetes, правила могут ещё разрешать новое соединение.

1. На ноде работает один сетевой исполнитель, защищённый от параллельного запуска. В короткой транзакции под общим замком записи операций он проверяет текущую desired_revision, сохраняет намерение для одной стороны и завершает транзакцию до вызова Kubernetes. Для пары допускается одно незавершённое изменение. Перед второй стороной исполнитель снова проверяет ревизию.
2. CREATE создаёт только пустую политику с маркером намерения. Потерянный ответ CREATE можно восстанавливать по проверенным Namespace UID, имени, маркеру и полной пустой спецификации; запоздалое создание такой политики само по себе доступа не даёт. Разрешение добавляется отдельным UPDATE с подтверждёнными UID и resourceVersion.
3. При неизвестном исходе разрешающего UPDATE исполнитель перечитывает политику. Для отзыва он условно записывает пустые правила с новой меткой намерения, даже если правила уже выглядят пустыми. Если старый UPDATE выиграл гонку, конфликт версии требует нового чтения. Если выиграл новый, старый запрос не сможет примениться с прежней resourceVersion. Один лишь GET или локальный таймаут эту гарантию не обеспечивают. После revoke обе пустые политики остаются в кластере.
4. После рестарта исполнитель начинает с незавершённой стороны. Обе стороны и identity Service проверяются через Kubernetes до CAS по desired_revision в БД. Чужой объект или недоказуемый исход останавливает подтверждение. Установщик при встрече с незавершённым намерением возвращает повторяемый статус ожидания.
5. Подтверждённый revoke означает, что обе политики проверены и ранее выданная операция не сможет снова разрешить доступ через старую resourceVersion. На реальном k3s отдельно проверяется отказ **новому** соединению после распространения правил. Состояние соединения, установленного раньше, зависит от dataplane.


## Граница сети

Ingress разрешает только трафик от Namespace потребителя к pod выбранного сервиса; egress потребителя — только к этим pod и портам. Обратное инициирование соединений не разрешается. Селектор живого Service сверяется с подтверждённой идентичностью развёрнутого компонента и его ownership; произвольный селектор, пустой selector, изменившийся UID или неподтверждённые endpoints приводят к отказу. Существующий manifest pipeline задаёт Service selector через `manifest.Identity`, но для live-объекта это нужно проверить заново.

Для правил нужны протоколы и **целевые порты pod** из Service, включая именованный `targetPort` и значение по умолчанию; разрешение только номера Service port не доказывает корректность после трансляции. Изменение selector или портов Service требует повторной проверки и согласованного обновления политик; до неё доступ не считается подтверждённым. Общая прикладная БД и её политики в эту пару не входят. Нужно отдельно проверить, что другие NetworkPolicy не дают более широкий доступ: политики Kubernetes складывают разрешения, поэтому сама пара не доказывает изоляцию.

## Installer и права БД

Сейчас `prepare-app.py` признаёт дополнительные NetworkPolicy только по совпадающей записи `paas_execution.ownership`. Между `create` и сохранением UID возможен сбой, поэтому installer должен либо безопасно ждать завершения активного intent, либо проверять его по тому же контракту доверия, что reconciler; иначе он ошибочно объявит принадлежащую PaaS политику чужой. Foreign policy, несовпадающий UID и неоднозначные записи остаются ошибкой. Обычные записи ownership и проверка default-deny сохраняются.

Для новой таблицы журнала миграция и installer должны согласовать минимальные SQL-права: `paas_operation_writer` — `SELECT`, `INSERT` и ограниченный необходимыми полями `UPDATE` журнала, а также существующие права на ownership; `paas_namespace_preparer` — только `SELECT` полей, нужных для проверки intent и identity. У обеих ролей нужен `USAGE` на `paas_execution`; удаление записей журнала и доступ к несвязанным данным не выдаются. Конкретные имена столбцов и `GRANT` фиксируются вместе со схемой; проверка прав runtime и порядок установки grants обязательны. Kubernetes RBAC должен отдельно подтверждать доступ daemon к Namespace, Service, pod и NetworkPolicy обеих сторон и отсутствие прав на чужие Namespace.

## Проверки перед приёмкой

- PostgreSQL: миграция, права обеих ролей, уникальность intent/ownership, CAS при смене revision, сбой между сохранением intent и каждого UID, повтор после перезапуска и отказ при чужом объекте; installer проверяет также незавершённый intent.
- Kubernetes fake: точная пара ingress/egress, селектор и targetPort, allow/revoke, readback обеих сторон, подмена UID/spec, потерянный ответ, сбой между двумя вызовами и гонка revoke с устаревшим allow. Fake не подтверждает работу сетевого dataplane.
- Живой k3s: два разрешённых потребителя подключаются к одному экземпляру, третий получает отказ до и после обновления сервиса; после revoke ранее разрешённый потребитель не может установить **новое** соединение. Проверить обратное инициирование, числовой и именованный targetPort, default-deny, отсутствие доступа к БД, замену Service/Namespace UID, сбой и перезапуск между операциями, а также повторный installer preflight. Для уже установленных соединений отдельно зафиксировать наблюдаемое поведение dataplane.

## Повторная регистрация после замены Service

На схеме v9 пара Namespace/name уникальна, а проверка чтения требует сохранённого UID. Если Deployment-поток пересоздаёт Service, чтение останавливается на расхождении UID. Повтор исходного register также отклоняется. Новый request_id для того же имени упирается в уникальность. Положительная повторная регистрация требует явного пути восстановления.

Предлагается при новом register сначала убедиться, что текущие Namespace и Service подтверждены Kubernetes и действующим ownership, а прежние разрешения более не действуют. Старая регистрация сохраняет свой request_id и привязку к прежнему UID, помечается снятой. Новый экземпляр получает отдельный shared_service_id и пустой список допусков. Регистрации с одним именем допускаются в истории, активная запись одна. Старые ID нельзя использовать для выдачи нового доступа; подключение нового потребителя требует отдельного set-access. Проверка должна охватить старые NetworkPolicy до публикации нового адреса и безопасное восстановление при незавершённом отзыве. Миграция существующих v9-записей, проверка индексов и полномочий входят в изменение журнала. Исходная Goose v9 сохраняется воспроизводимой.


## Статус для оператора

Предлагается отдельное чтение `GET /shared-services/access?shared_service_id=…&consumer_app_id=…` в существующем Flux-сервисе. В ответе: оба ID, запрошенные `desired_allow` и `desired_revision`, последний подтверждённый результат `applied_allow` и `applied_revision` (оба отсутствуют до первого подтверждения), статус PENDING, APPLIED или BLOCKED. Для BLOCKED выдаётся только безопасный код причины. Неверные ID — 400, отсутствующая пара — 404, недоступное достоверное чтение — 503. Даже во время ожидающего отзыва оператор видит предыдущее подтверждённое состояние; адрес для потребителя по-прежнему выдаёт только существующий отфильтрованный список. При обновлении существующей v9 сохранённые applied-данные подлежат повторной проверке до выдачи адреса.
