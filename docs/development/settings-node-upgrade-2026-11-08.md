# Приёмка обновления служебной БД с v3 до v4

На отдельной Debian 13 ВМ `lima-control-check` с одной Ready-нодой k3s
`v1.37.2+k3s1` установлены PostgreSQL 18.6, миграции Goose и daemon.
Узел до проверки содержал рабочий каталог, компоненты, историю операций и завершённый Job v3.
В исходный каталог добавлена запись с tombstone. Образ для ARM64 собран
`paas-daemon/scripts/build-image.sh` и импортирован в containerd по ссылке
`localhost/paas/paas-daemon@sha256:6633a851ae272eb4083813491a311a87497e8be3f3d265a5baff2391737c9244`.

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Совместимый reader установлен первым, на схеме v3 | `/health` и `/ready` ответили 200; попытка регистрации вернула 503. |
| Отдельная SQL-сессия держит штатную advisory-блокировку Goose | Настоящий `control-migrate-v4` исчерпал 30-секундный таймаут и завершился в `Failed`. Схема осталась v3. Прежний Pod продолжал отдавать каталог и готовность. |
| Явный повтор после освобождения блокировки | Установщик заменил неуспешный v4 Job. Новый Job с согласованным digest выполнил миграции, после проверки grants отдельная установка daemon заменила его Pod через Recreate. |
| Повтор установки PostgreSQL и daemon | UID завершённых Jobs, Deployment, Pod v4, Namespace, PVC и PV сохранились. Сверены прежние данные каталога и истории, PostgreSQL system identifier, UID и содержимое трёх исходных Secrets и двух новых, SCRAM-верификаторы ролей. |
| Попытка повторной установки только по исходному v3-профилю | Установщик потребовал v4-профиль и завершился с ошибкой. После возвращения исходного файла профиль и данные продолжили работать на v4. |
| Регистрация через `paas-ctl node prepare-app` и UDS | Фиксированная SSH-команда вернула назначенные ID и UID Namespace. Первая регистрация через API дала 201, повтор — 200 с тем же приложением. Изменение имени при том же ключе было отвергнуто. |
| Чужой Namespace заранее занял имя резерва | Установщик отказал. Проверены прежний UID чужого Namespace и отсутствие подтверждения в БД. Тест удалил свой объект с предусловием UID. |
| Потеря права preparer записать `namespace_uid` после подготовки Kubernetes | До записи proof API вернул 503. После восстановления исходного column grant повтор подтвердил уже созданный Namespace с тем же UID; API вернул 201. |
| Разрешения приложения | На созданном Namespace Kubernetes отклонил server-side dry-run привилегированного Pod. `auth can-i get secrets` для `paas-workload` вернул `no`. Проверены default-deny обоих направлений, отсутствие RoleBinding и выключенная автопередача токена. |
| Все семь HTTP-маршрутов | На работающем Pod проверены регистрация компонента и повтор, чтение и изменение политики, 409 на старой revision, чтение, установка и удаление migrator. Тело POST в 1 048 577 байт получило `413 BODY_TOO_LARGE`, повтор того же ключа с телом в 1 048 576 байт дал 201. |

Для повторения нужны отдельная тестовая нода v3, собственный административный
SSH-ключ и ключ `paas`. Сначала передать новый `--daemon-image` через `node prepare`
и выполнить `node install-daemon` на v3. Затем передать тот же pinned digest как
`--settings-migration-image`, выполнить `node install-postgres`, затем
`node install-daemon`. Для воспроизведения отказа перед первым запуском
`install-postgres` в отдельной сессии к `paas_control` удерживать
`pg_advisory_lock(4097083626)` до завершения Job, закрыть сессию и повторить.
Разрушающие тестовые проверки отказов проводились только в выделенной fixture.

Три production-модуля Python проверены по совпадающим SHA исходных файлов:
совмещены трассировка повторной установки на ВМ, 37 проверок в Linux и сценарий
аварийного Unix-сокета с SIGKILL. Максимальный измеренный CRAP — 9,3. Dryer при
пороге 0,8 не нашёл похожих функций. Для выбранных границ регистрации и UID
Mutator дал 26 убитых мутантов из 26 запущенных.
