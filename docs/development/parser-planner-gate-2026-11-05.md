# Проверка внутреннего parser/planner — 2026-11-05

Статус: **BLOCKED на 3.3.16**, не приёмка planner. Пользователь одобрил внутренний
профиль; OpenSpec обновлён в пределах явного одобрения. Итог 43/67: новые
3.3.16–3.3.19 открыты. Common #24 и daemon #5 остаются незлитыми зависимостями.

## Воспроизводимый результат

Изолированный Go-модуль [yaml-parser-gate](yaml-parser-gate/README.md) использует
только публичные API `go.yaml.in/yaml/v4 v4.0.0` на Go 1.27.3. Origin:
`f2f9563503f11b7a60da0c532175dcc693ce8d5a`; checksum/provenance, тесты и логи
включены в каталог. В production go.mod всех трёх репозиториев изменений нет.

| Сценарий с DepthValue(64) | Результат |
| --- | --- |
| Чистая block/flow глубина 64 | Принят |
| Чистая block/flow глубина 65 | Отклонён |
| Block 32 + flow 33 | Построено дерево глубины 65 — нарушение |
| Block 64 + flow 64 | Построено дерево глубины 128 — нарушение |
| 33 пары mapping + indentless sequence | Построено дерево глубины 66 — нарушение |
| Alias с WithDisable(true) | Отклонён во время composition |
| Merge с mergekey.WithDisable(true) | Дерево принято; отключение merging не запрещает синтаксис |
| Документ 129 с глубоко вложенным телом | Ранний публичный document callback отклоняет его до дерева |
| Широкий документ | 300003 узла, depth callback вызван один раз |
| HTTP body 8388608 / 8388609 bytes | Пограничный reader принимает / отклоняет соответственно |

Тесты контрпримеров с race detection **PASS**: они проверяют воспроизведение
дефекта, а не соответствие контракту. Обязательный `TestRequiredEarlyDepth64`
**FAIL**. `run.sh` намеренно завершается с кодом 1; положительный статус тестов
контрпримеров не переводит gate в PASS. `go mod verify` и SHA-256 manifest PASS.
Независимый reviewer Astra прочитал upstream и повторил контрпримеры глубины.
Root повторил опубликованный reproducer. Stress/RSS приёмка не заявляется.
Число 262144 узла остаётся дополнительным предложением, не новым одобрением.

Причина: scanner сообщает отдельно flow level и стек block-отступов. Нет
публичных структурных enter/leave callbacks для общего счётчика collections.
`ParserPlugin` заменяет parser целиком, а не перехватывает native events;
native parser находится в internal. Последующий обход Node не удовлетворяет
требованию ограничения во время разбора.

## Что подготовлено независимо

- OpenSpec фиксирует одобрение и четыре новых открытых пункта, сохраняя
  дополнительные рекомендации отдельно от уже утверждённых требований.
- Проверено, что pure planner не требует CLI/generated SDK/HTTP изменений.
  Существующие handlers и DB grants сохранены.
- Независимое ревью выделило приёмочные случаи: absent/null/unknown,
  integer без float64, порядок списков, сохранённые/чужие ресурсы, различие
  private plans при одинаковых public paths, неизменность входа, redaction.
- Выявлен второй gate: точная field ownership/update/defaulting семантика.
  Raw observed Kubernetes objects нельзя напрямую сравнивать с неполным target.
  Например, controller-added Service annotations не должны удаляться только
  потому, что пользовательские annotations запрещены входным профилем.

Типы production state и частичный planner не добавлялись как заглушки:
полнота read set и current/target semantics должны быть определены до их приёмки.
Нормативные требования не ослаблены, открытые задачи не закрыты отрицательным
результатом проверки. Полный planner, Kubernetes conformance и выполнение
деплоя не проверены.

## Конкретный следующий шаг

Рекомендуется небольшой upstream-compatible hook до создания очередного узла
в native composer: общий collection depth (root=1), отказ alias/merge и
доступный счётчик узлов без замены YAML grammar. Существующие scanner limits
сохраняются. Его приёмка — те же контрпримеры должны стать отказами до создания
деревьев, корректная глубина 64 остаться допустимой; upstream tests также проходят.

Готового достаточного публичного API в проверенной версии не найдено. Варианты:
ждать upstream hook либо отдельно разрешить минимальный закреплённый локальный
fork v4.0.0 с сохранением лицензий, явным patch и планом возврата upstream.
Альтернатива cgo/libyaml требует отдельного решения и усложняет сборку.
Ни fork, ни cgo, ни отправка upstream issue/PR в этом этапе не выполнялись.
Предыдущее предложение прямо оставляло fork/cgo на отдельное согласование;
одобрение проверки библиотеки не превращает неудачный gate в разрешение обхода.

После решения parser gate требуется завершить per-field registry и приёмку
bounded state, затем основной planner. Public preview/apply, установка k3s,
merge и deployment по-прежнему вне этого этапа.
