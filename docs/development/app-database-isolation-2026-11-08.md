## Восстановление после прерванной подготовки

Для приложения `f381d0a5afb24e6ebb22c8183dde0b5d` отдельная сессия PostgreSQL удерживала advisory lock подготовки ролей. После подтверждения деплоя исполнитель создал оба Secret и стал ждать блокировки. Запись подготовки оставалась в PENDING. Попытки получить credentials APPLICATION и MIGRATOR через API обе вернули HTTP 409.

На стенде остановили сервис и таймер подготовки, освободили тестовую блокировку и вновь запустили подготовку. У каждого Secret сверили UID и хеш данных до остановки и после восстановления. Оба совпали. Для приложения обнаружены одна БД и две LOGIN-роли, запись подготовки перешла в READY. Исходная операция `edf975a0ad7db4e3e6ce7516a6cae19a` завершилась SUCCEEDED. При контрольном чтении через Unix-сокет подтверждён её терминальный статус, таймер активен.

## Удаление мигратора у существующего приложения

У того же приложения через `POST /apps/remove-migrator` сняли конфигурацию с проверкой текущей ревизии. GET подтвердил отсутствие мигратора. Попытка получить новый preview ручной миграции с актуальной ревизией вернула HTTP 409 MIGRATOR_NOT_CONFIGURED. Набор UID Jobs сохранился.

До и после снятия конфигурации проверили OID прикладной БД, наличие двух LOGIN-ролей, UID и данные обоих Secrets. Прикладная роль по TCP с прежним паролем выполнила SELECT из `app.notes` в обоих случаях. После проверки прежний образ восстановили через `POST /apps/set-migrator` и сверили с GET.

Для обычного Pod приложения `f381d0a5afb24e6ebb22c8183dde0b5d` без выданной контейнеру привязки выполнен `pg_isready` с явно указанным пользователем на ClusterIP PostgreSQL, порт 5432. Клиент получил no response (код 2). В это же время сервер принимал подключения на loopback, EndpointSlice Service был Ready. Этот результат покрывает отказ обычному workload. Для проверки положительного доступа нужна выданная привязка конкретному экземпляру Deployment.

## DML и привилегии обеих ролей

На control-check для приложений `b816c1ef8f8847a89f20392b02823b66` и `f381d0a5afb24e6ebb22c8183dde0b5d` выполнены четыре независимых TCP-входа. При каждом проверены current_database и current_user. Каждый из четырёх LOGIN выполнил INSERT, UPDATE, SELECT и DELETE в своей app.notes с ROLLBACK. Прикладная роль каждого приложения получила отказ для CREATE, ALTER, DROP и TRUNCATE; ни одна из них не владела таблицей. Обе роли мигратора выполнили CREATE, ALTER и DROP в транзакции с ROLLBACK.

Для всех четырёх LOGIN подтверждено отсутствие SUPERUSER, CREATEDB, CREATEROLE, REPLICATION, BYPASSRLS, INHERIT и членства в ролях. Каждый получил именно PostgreSQL permission denied for database при попытках подключиться к чужой прикладной БД и к paas_control. Права приложений в ходе проверки не меняли.

[Изолированный проверочный скрипт](../../../paas-ctl/scripts/testdata/app-db-schema.sh) дополнительно создаёт новые таблицу и sequence от имени мигратора и проверяет права приложения на созданные объекты. В нём временный pgpass создаётся через mktemp. Пароль сопоставляется с ролью для всех тестовых БД, а отрицательный тест проверяет причину SQL-отказа. Прежняя версия могла принять отсутствие подходящего пароля за успешную проверку изоляции.
