# Первый деплой приложения с мигратором на одной ноде

Стенд — `lima-control-check`, приложение `b816c1ef8f8847a89f20392b02823b66`,
компонент `672130f4fd34e6a7a04ee1eebb66bbb4`, PostgreSQL 18.6.

## Сверка после неудачной попытки

Первая операция `b5e4b574903fddd2fe0270367ac20209` подготовила отдельную
БД (OID 16534) и два immutable Secrets. Job с UID
`c5aa4175-d279-4bbe-aa02-df0959edd8da` завершился в Failed. Пользовательский
Deployment отсутствовал. Перед повтором отдельно проверены отсутствие таблицы
`app.notes`, таблицы истории `paas_migrations.goose_db_version` и активных
соединений роли мигратора. Сохранённые UID Secrets —
`ebec1c03-f26e-4c72-986b-e548c782af88` и
`777d08eb-6577-4815-b290-2b8deb471967`.

Исправленный reader сверил созданный Job с намерением, сохранил его реальный
UID и перевёл исходную операцию в RECOVERY_REQUIRED. Для подтверждения
потребовалось учесть нормализацию поля serviceAccount сервером Kubernetes.
У первой версии мигратора было только общее сообщение об отказе. Сетевой
тест отдельного Pod впоследствии подтвердил подключение и права CREATE на
служебную схему миграций; точная причина отказа первого процесса по старому
сообщению неизвестна.

## Явная повторная попытка

После сверки исходную операцию вручную перевели в FAILED одной административной
транзакцией под замком приёма. Предусловия включали ID приложения, операции,
стадию, подтверждённый UID Job и готовность существующей БД. Очищены приватный
снимок завершённой попытки и только её резервы. Строка истории и неуспешный
Job сохранены. Это был административный шаг на тестовом стенде.

В settings записали образ мигратора с digest
`sha256:257d8dd053a80f56a37a0f4dcfe9448171e5a9f41b7cbe36a176cd7553d72473`.
В нём проверка подключения к PostgreSQL предшествует единственному вызову Goose
up. Новый preview `354cc04ebbd789c858f75d8fc73eb68a` явно включил
INITIAL_MIGRATION. Через обычный API подтвердили тот же компонент.

| Проверка | Результат на ноде |
| --- | --- |
| Операция | `c33eb93e80c0d00b3bbee989a25066ce` прошла ACCEPTED, INITIAL_MIGRATION и WAIT_READY, затем SUCCEEDED. Повтор apply того же preview вернул тот же ID. |
| Порядок | Новый Job с UID `4815e1d2-7754-4a2f-8ac0-0ac212d3caf6` завершился в 10:47:48 UTC 8 ноября. Kubernetes создал Deployment `orders-backend` в 10:47:49 UTC. Первый Pod достиг 1/1 Ready без перезапусков. |
| Схема приложения | В действительной БД приложения появилась `app.notes`. В `paas_migrations.goose_db_version` версия 1 записана как применённая. |
| Сохранность | БД осталась READY с OID 16534. У обоих Secrets сохранились прежние UID. Старый Job остался Failed, новый — Complete. После обеих терминальных попыток число их активных резервов равно нулю. |
| Независимое обновление после миграции | Обычный preview увеличения реплик вернул UPDATE с пустым additional_actions. Операция `a7cba1cb6c483c5db30b424a798fbca2` завершилась SUCCEEDED, набор UID миграционных Jobs не изменился. [Проверка соседнего компонента](component-recovery-2026-11-08.md). |

Эта проверка выполнена через SSH/UDS API. Ручной запуск через TUI и проверка блокировки описаны ниже. Позднее пройден [полный сценарий 7.1](tui-node-check-2026-11-07.md#71-два-приложения-после-перезапуска-daemon).

## Защита запуска мигратора

На control-check через SSH/UDS проверены семь вариантов одного Deployment с образом, закреплённым по digest. Образ daemon — `sha256:8c4fd6d5b65a4e7b0106f61274f87a9cab79cc3e9f4caba722bc235b79308e5c`. Контрольный манифест получил preview ID. Во всех шести отрицательных случаях сервер вернул HTTP 200 с диагностикой уровня ERROR и без preview ID. Apply не вызывался.

| Изменение манифеста | Диагностика preview |
| --- | --- |
| ServiceAccount `paas-migrator` | `FIELD_FORBIDDEN` |
| Secret `paas-migrator-db` в env, envFrom, прямом томе, projected-томе или env init-контейнера | `SECRET_BINDING_DENIED` в каждом из пяти случаев |

На отдельном PostgreSQL 18.6 два процесса вызвали функцию `up()` из примера мигратора с тестовым SQL. Пока первый выполнял `pg_sleep(8)`, в `pg_locks` наблюдалась его блокировка 4097083626. Второй завершился с ошибкой захвата блокировки. В этот момент тестовая таблица отсутствовала. После завершения первого процесса таблица появилась, мигратор выдал VERSION_APPLIED для версии 1. Конкуренция двух запросов к API проверена отдельно [на тестовой ноде](app-database-isolation-2026-11-08.md).

У реально завершившегося Job проверены UID в ownerReference его Pod, ServiceAccount `paas-migrator` и единственный том Secret `paas-migrator-db`. Автоматическое монтирование API-токена выключено, projected-токен отсутствует. У Deployment `orders-backend` подтверждены ServiceAccount `paas-workload` и отключённый automount.

Ручная миграция, подтверждённая в PTY, создала APP-операцию `a18bbc479128f5d7658116abb7a9c78c`. Через отдельный запрос `/operations/inspect` подтверждено SUCCEEDED. В `/operations/migration-log` получены JOB_CREATED, JOB_STARTED и JOB_SUCCEEDED. Для этой установки Kubernetes ответил `no` на проверку права daemon читать `pods/log` в Namespace приложения. Структурированный результат прикладного процесса из stdout в этой операции отсутствовал.

Затем в новой PTY-сессии оператор открыл эту же запись из общей истории и увидел цель APP, ID приложения и SUCCEEDED. Для чтения результата повторное подтверждение миграции не потребовалось. В Kubernetes соответствующий Job имеет состояние Complete, у Deployment обе реплики готовы.

На другом приложении (`f381d0a5afb24e6ebb22c8183dde0b5d`) оператор выбрал в форме деплоя миграцию и увеличение числа реплик с одной до двух. В preview отображалась причина REQUESTED. ## Перезапуск daemon во время миграции

На ноде control-check установлен daemon `sha256:48c4d0d0bdf4780a28e9aa7812328d7b64f7ed45e5b5e8cacd8d279204c56731`. На тестовом приложении `f381d0a5afb24e6ebb22c8183dde0b5d` отдельная транзакция временно удерживала ACCESS EXCLUSIVE на таблице `paas_migrations.goose_db_version`. До перезапуска подтвердили три наблюдения: новая ручная операция `bc9cb3706abd640ec33073d4d2a8edf9` принята, PostgreSQL видит ожидающее блокировку соединение мигратора, в control DB сохранён UID созданного Job `4f8cf118-cfc5-41c4-92de-7ee7cd30d3b1`.

Тест удалил Pod daemon `416f15e0-b931-4fc7-a590-356d7f16272c`. После готовности сменившего его Pod `9a7f0c08-4a6b-4d76-9679-641cd1824bef` тест освободил блокировку. Через UDS исходная операция достигла SUCCEEDED. С момента начала проверки появился ровно один миграционный Job с прежним UID. В журнале сохранены JOB_CREATED, JOB_STARTED и JOB_SUCCEEDED. Повторный apply того же preview вернул HTTP 200 и прежний ID операции. В прикладной БД осталась одна применённая запись версии 1.

Совместимость со старым частично записанным журналом проверена отдельно на PostgreSQL 18.6. Тест `TestMigrationJobIntentPersists` сохранил VERSION_APPLIED до терминального события и передал пустой вывод при восстановлении. Ранее записанное событие сохранилось, журнал получил признак truncated и JOB_SUCCEEDED, повторное завершение сохранило этот результат. Этот тест и `TestMigrationRecoveryPreservesReservation` прошли под `-race`.

## Job создан, контейнер ещё ждёт образ

На control-check до исправления worker записывал JOB_STARTED сразу после регистрации UID Job. Теперь daemon `sha256:e2fe448e2f0921e6f65c2db90edd8f6f95b1907b8f0457d30a15847567a0e010` проверяет running или terminated у контейнера migrator в Pod, принадлежащем этому Job. При отказе до запуска возможен терминальный JOB_FAILED без события JOB_STARTED. Восстановление старого журнала и отказ до запуска проверены на PostgreSQL 18.6 под race.

Для проверки приложению `f381d0a5afb24e6ebb22c8183dde0b5d` временно задали новый digest того же проверенного мигратора. В OCI изменили только аннотацию манифеста; образ заранее не импортировали. Операция `8db259b8fc93fa82ef60d2d3258cd51c` создала Job с UID `679c0087-80e3-4a51-9ffc-ad2aca859068`. При ImagePullBackOff публичный журнал содержал только JOB_CREATED.

| Время UTC 8 ноября | seq | Публичное событие |
| --- | --- | --- |
| 11:57:47.519202 | 1 | JOB_CREATED |
| 11:59:08.530539 | 2 | JOB_STARTED |
| 11:59:10.530297 | 3 | JOB_SUCCEEDED |

После локального импорта OCI kubelet повторил загрузку, и прежний Job завершился. Через `/operations/inspect` подтверждены цель APP и состояние SUCCEEDED. В `/operations/migration-log` каждый из трёх кодов был записан ровно один раз. Доступ к stdout через pods/log на этой установке ещё не выдан.

После проверки GET настроек приложения подтвердил восстановление исходного образа `localhost/paas/example-migrate@sha256:257d8dd053a80f56a37a0f4dcfe9448171e5a9f41b7cbe36a176cd7553d72473`.

Отдельная проверка через client-go и локальный HTTP-сервер Kubernetes подтвердила обработку структурированных событий завершённого migrator. Произвольный текст отфильтрован. Для работающего контейнера daemon не запрашивал журнал. При смене UID Pod после чтения daemon отбросил полученные события. Исполнение этого пути на k3s с разрешённым чтением stdout остаётся частью 5.2. [Тест транспорта](../../../paas-daemon/internal/deployment/migration_events_transport_test.go) и [предложение по правам](../../openspec/changes/define-k3s-paas-foundation/design.md#чтение-событий-завершённой-миграции-предложение-для-52).

## События stdout на v5-fresh, 8 ноября

На выделенной v5-fresh со схемой v11 создано приложение `b0d520266031432db5880638c2869bb8` старым профилем подготовки. Повторный prepare новым профилем сохранил UID Namespace `5e42a64c-6443-4caa-9f40-d9a22eaab7c1` и Role `bb7ac70e-c451-4bba-b80f-13afd7932c0b`; resourceVersion Role изменился с `5733` на `5765`. Следующий повтор сохранил UID и resourceVersion. Второй Namespace для нового профиля подготовлен с app ID `805779e689b74827ac836ff53bdee197` и UID `6e59ccab-6fae-4754-bf4d-42d035e569e2`.

Проверка `kubectl auth can-i` с явным `--subresource=log` от сервисного аккаунта daemon показала `get: yes`, `list/watch: no` в обоих Namespace. В неподготовленном `kube-system` все три ответа `no`; общий `get secrets` также запрещён. Это право технически позволяет daemon читать журнал любого Pod подготовленного приложения; выбор мигратора и проверка UID выполняются в коде daemon.

Начальный deploy создал операцию `3157413b6a965000df40a1f313201b62`, завершившуюся SUCCEEDED с `VERSION_APPLIED`. Повторная ручная миграция, подтверждённая в PTY, создала `dd712f94181d4a798cd50e087fdad97f`, также SUCCEEDED, с `NO_PENDING_MIGRATIONS`. Оба события проверены через UDS `/operations/migration-log` и открыты в TUI. Исполнявшийся [сценарий](../../../paas-ctl/scripts/testdata/tui-migration-events-live.py) привязан к указанному одноразовому приложению и запускается один раз; для повторения нужен новый собственный fixture и согласованное изменение его ID и request ID в сценарии.

Локально прошли `python3 scripts/testdata/test-prepare-app.py` в `paas-ctl` и `GOWORK=off go test ./internal/deployment -run '^TestMigrationEvents' -count=1` в `paas-daemon`. Последний тест использует локальный HTTP listener и отдельно проверяет отсечение произвольного текста, предел чтения и подмену UID Pod; первоначальный запуск внутри sandbox не смог открыть listener, повтор с разрешённым loopback прошёл. Эти проверки не являются физической подменой Pod на k3s.
