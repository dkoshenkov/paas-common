# База приложения и получение credentials, 4.1–4.4

**Этап 4.1–4.4 одобрен пользователем.** На узле уже есть общий PostgreSQL 18, служебная БД, реестр Namespace и снимок образа мигратора в Goose v4. Семь маршрутов settings обслуживают регистрацию и настройки. В этом предложении подготовка прикладной БД начинается при первом принятом деплое с выбранным мигратором. Регистрация, сохранение образа и preview остаются без этих побочных эффектов. [Требования к БД](../../openspec/changes/define-k3s-paas-foundation/specs/application-database-access/spec.md) и [матрица доступа к Secrets](../../openspec/changes/define-k3s-paas-foundation/specs/application-secrets/spec.md).

## Одна команда оператора

Предлагаем добавить отдельный Flux service `database` с одним маршрутом. App-scoped preview/apply миграции уже описаны отдельно. Подготовка БД является внутренним этапом принятого деплоя. Отдельная команда создания БД оператору не нужна. [Контракт миграций](app-migration-contract-proposal.md).

| Запрос | Успешный ответ | Ошибки |
| --- | --- | --- |
| `POST /apps/database/credentials` с `{app_id,purpose}`, где purpose ровно `APPLICATION` или `MIGRATOR` | 200 с `{app_id,purpose,host,port,database,username,password}`. Port — целое 5432. Актуальное значение берётся из одного существующего Secret. | 400 INVALID_REQUEST для неизвестных полей, ID или purpose; 404 NOT_FOUND для отсутствующего/удалённого приложения или никогда не подготовленной БД; 409 DATABASE_NOT_READY для начатой незавершённой подготовки; 413 BODY_TOO_LARGE при превышении 1 MiB исходного тела; 503 DEPENDENCY_UNAVAILABLE при сбое зависимости. Несогласованная идентичность уже готового объекта — безопасный 500. |

Все ответы этого пути получают `Cache-Control: no-store`. Списки, настройки и операции сохраняют прежние несекретные DTO. Файл `migration.yaml` и произвольные запросы SQL не подключаются. Учётная запись оператора для v1 остаётся одной. Авторизация происходит при доступе через SSH и защищённый UDS; непривилегированные субъекты не могут открыть соединение. Kubernetes RBAC-ошибка у уже допущенного daemon означает неисправную зависимость. TUI открывает отдельное явное действие показа выбранного назначения, стирает значение из модели при закрытии; журнал, история, argv, environment дочерней команды и clipboard его не получают. Получение уже созданных credentials работает и после удаления образа мигратора из настроек.

## Однозначные имена и роли

Предлагаем вывести PostgreSQL-имена из выданного сервером постоянного app_id. Для ID из 32 lowercase hex имя БД и LOGIN приложения — `app_<id>`, LOGIN мигратора — `app_<id>_migrator`, владелец БД — `app_<id>_owner` NOLOGIN. Для прежнего допустимого непрозрачного ID используем первые 32 lowercase hex SHA-256 от байтов `legacy\0<app_id>`, с проверкой на коллизию до выдачи. Каталог хранит **точные выданные** имена, app_id и purpose. Такое уточнение к примеру orders/orders_migrator в спецификации нужно согласовать: отображаемые имена сейчас произвольны, могут совпасть, содержать Unicode и превышать ограничение PostgreSQL. Rename не переименовывает существующие роли и БД. При занятом имени с другим владельцем подготовка останавливается до DDL. Администратор сопоставляет pg_stat_activity.datname/usename с каталогом. Пользовательский application_name не определяет владельца.

| Principal | Права |
| --- | --- |
| Прикладной LOGIN | CONNECT только к своей прикладной БД, USAGE схемы `app`, SELECT/INSERT/UPDATE/DELETE таблиц, USAGE sequences. Без TRUNCATE, TEMP, CREATE, ownership, membership или административных атрибутов. |
| LOGIN мигратора приложения | CONNECT к своей БД и CREATE/USAGE в `app`. Владеет созданными там объектами, выполняет DDL и DML. Для служебной истории Goose отдельная схема `paas_migrations`, не доступная прикладному LOGIN. |
| Служебный reader/settings writer | Существующие служебные роли не получают кластерных CREATE DATABASE/ROLE или прав прикладных LOGIN. В Kubernetes у daemon выделенный ServiceAccount с GET на два фиксированных имени Secret в каждом доверенно подготовленном Namespace. Без list/watch Secrets всех пространств, RBAC/имперсонации и доступа к postgres-admin или GHCR. |
| Доверенная подготовка на узле | Предлагаем фиксированный root-owned systemd service с таймером, читающий только журнал намерений принятого деплоя и выполняющий заданный алгоритм; старт/рестарт устанавливает ctl. Служебный пользователь не может подставлять SQL, Secret, Namespace, пути или произвольные команды. Существующая PostgreSQL admin identity остаётся доступна только доверенному исполнителю. |

У роли приложения и мигратора запрещены SUPERUSER, CREATEDB, CREATEROLE, REPLICATION, BYPASSRLS и наследуемое членство. REVOKE CONNECT/TEMP от PUBLIC делается при создании каждой прикладной БД до открытия LOGIN. Существующую paas_control проверяем отдельно. Прикладным ролям также закрываем служебные postgres/template1 через управляемый профиль доступа PostgreSQL; перед изменением привилегий сверяем нужный доступ служебных identities. REVOKE CREATE/USAGE от PUBLIC для пользовательских схем и EXECUTE от PUBLIC на будущие пользовательские routines выполняется также для default privileges роли-создателя. Права на существующие и будущие таблицы и sequences в app задаются отдельно; migration history и функции с правами владельца отсутствуют в этих grants. Тестируем serial/identity INSERT и отказ прикладному LOGIN в setval. Указываем schema-qualified history Goose, управляющую схему исключаем из пользовательских grants.

## Порядок и восстановление

1. При durable acceptance writer под общим замком реестра, в одной транзакции с операцией и резервом БД приложения, сохраняет намерение подготовки. Предлагаем одну дополнительную Goose-миграцию поверх фактической актуальной схемы: журнал с operation_id, app_id, ожидаемыми Namespace name/UID, revision/digest мигратора, именами трёх ролей и БД, UID двух Secrets, идентификатором установки и состоянием. Открытые поля паролей, DSN и Secret data в служебной БД отсутствуют. DB reservation защищает приложение от второй одновременной подготовки и последующей несовместимой смены мигратора. Для старых приложений без подтверждённого Namespace UID сначала нужен доверенный факт подготовки; генерация из display name запрещена.
2. Исполнитель кратко получает запись журнала и сверяет владельца, Namespace UID, системный идентификатор PostgreSQL и связанный **принятый** снимок операции с мигратором. Для согласованного намерения создаёт в Namespace приложения два immutable Secrets, `paas-app-db` и `paas-migrator-db`. Каждый содержит `host, port, database, username, password`, значения — строки; пароли независимы, по 32 байта из системного CSPRNG. Метки/аннотации привязаны к установке, app_id и сохранённому идентификатору подготовки. После создания каждого записывает его UID. Повтор после потери ответа читает точно тот же объект, проверяет метки, UID, immutable, форму и несекретные поля. При пропаже уже записанного UID или расхождении — остановка для восстановления, без замены пароля.
3. С теми же значениями в транзакции PostgreSQL создаёт три роли; LOGIN app и migrator временно отключены. Отмечает владельца установки и намерения, исключает членство и посторонние права. `CREATE DATABASE ... OWNER ... ALLOW_CONNECTIONS false` выполняется отдельно от SQL-транзакции. Неотмеченную закрытую БД после обрыва можно продолжить только при совпадении уникального помеченного NOLOGIN-владельца и предварительно сохранённой фазы. Чужие объекты не присваиваются. До открытия подключений транзакционно закрывает PUBLIC и выдаёт точный CONNECT. Затем создаёт схемы, grants и default privileges, проверяет их и только потом включает два LOGIN. Никакие уже установленные пароли при повторе не меняются.
4. Исполнитель выполняет реальные TCP-аутентификации обеих ролей, сверяет PostgreSQL OID БД и ролей, Namespace UID, оба Secret UID, права и mapping. Только после этого отдельной транзакцией фиксирует READY; до READY reveal и выдача workload блокируются. В каждый внешний вызов проще входить одним исполнителем: локальный flock, транзакционный замок журнала для коротких записей, после рестарта сверка фактического объекта и UID перед продолжением. Сетевой вызов не удерживает транзакцию служебной БД. Ошибка владения требует RECOVERY_REQUIRED; временный обрыв возвращает к проверке текущей фазы. Повтор подготовки не запускает новый Job миграции.
5. После READY deployment worker может начать защищённый Job с отдельным migrator Secret и выбранным digest. Приложение запускается лишь после успеха обязательной первой миграции. При ошибке Job нет скрытого рестарта. Прикладной Secret разрешается только точным DB-grant к контейнеру/типу init с валидированными ключами либо целым Secret. Допуск по сети задаётся платформой с обеих сторон для нужных Pod и PostgreSQL TCP/5432 плюс DNS; Pod без права на Secret не получает значение. Удаление настройки мигратора/приложения не удаляет данные и пароли автоматически.

В v1 предлагается явная зависимость от durable acceptance и резерва БД из 3.3/3.5. До их появления 4.1/4.2 можно проверить на fixture с реально сохранённым намерением, а сквозную автоматическую подготовку следует оставить открытой. Выбранная система хранения разрешает повторную проверку подготовки после рестарта, но не обещает exactly-once для внешнего DDL. Для исключения раннего доступа при новой установке нужны уже согласованное шифрование Secrets at rest и RBAC в приложении, а для первого деплоя — исполняющий профиль workload/NetworkPolicy.

## Приёмка на одной ноде

- Два приложения с одинаковым display name и разными ID получают отдельные базы и логины. Третье без мигратора, preview и сохранение образа не создают ролей, Secret или БД. Зафиксировать mapping и проверить атрибуцию двумя живыми соединениями.
- PostgreSQL 18.6: микротесты реального CONNECT, DML, DDL, sequences, EXECUTE, TRUNCATE, temp, membership, чужих баз, служебной БД и history. Изменение таблиц и создание новой последовательности после миграции должно сохранять точную матрицу. Проверить объект с чужим именем, OID/owner и повтор после изменения display name.
- Последовательно убить исполнителя после каждого CREATE Secret/ROLE/DB, после двух LOGIN и перед READY. Перезапустить службу и узел. При успехе сохраняются OID, verifiers, UID и исходные значения. При подмене Secret с тем же именем, Namespace UID или владельца БД операция останавливается. Отозванный или подменённый scope не получает паролей.
- Проверить настоящий generated SDK через SSH/UDS. Оператор явно получает отдельно APPLICATION и MIGRATOR. После удаления настройки значения прежние. Проверить кэш-заголовки и canaries во всех обычных ответах, renderer состояния, журналах, событиях Kubernetes и аргументах процессов. Из обычного Pod соединение с UDS и API чтения Secret запрещено.
- В k3s проверить первый принятый деплой и restart между подготовкой и запуском Job; два параллельных деплоя не расходуют одну reservation дважды. Проверить фактические ссылки контейнеров, 1-й Job, сеть и отсутствие старта компонента при failure. Без этого 4.1–4.4 и исполнение деплоя не отмечаются завершёнными.

**Решение для старта** — один reveal API и действие TUI, стабильные физические имена по ID, две схемы и два отдельных Secrets, доверенный узловой исполнитель с журналом принятых операций, предложенные права и порядок восстановления. Смена пароля, удаление БД и выдача произвольных пользовательских Secrets требуют отдельных контрактов.
