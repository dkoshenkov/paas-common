# Установка GHCR и Traefik на одной ноде

8 ноября владелец одобрил реализацию 3.4 (приватный GHCR) и 3.5 (Traefik с тестовой CA и проверкой восстановления) на выделенном стенде. На control-check 8 ноября обнаружены Helm chart `traefik-41.6.101+up41.6.1`, образ `rancher/mirrored-library-traefik:3.7.15`, одна реплика, стратегия RollingUpdate. Аргументов ACME resolver в работающем процессе нет. В рабочем DeploymentTarget отсутствуют значения класса Ingress, HTTPS entrypoint и resolver. Условия установки и внешней приёмки различаются.

## GHCR на узле

Существующий административный SSH-шаг устанавливает один root-owned helper и четыре точных sudo-вызова для пользователя paas: `set-ghcr`, `apply-registry`, `restore-registry`, `status`. Контракт фиксирует файл k3s, владельца root:root, режим 0600, одну защищённую предыдущую версию и отдельный явный перезапуск k3s. Ввод имени и токена идёт из ctl по stdin в проверенном SSH-соединении. Для терминала нужен скрытый ввод токена. Для автоматической приёмки допустим синтетический токен через stdin. Результат показывает состояние конфигурации и готовность службы, без содержимого файла и credentials.

Для записи предлагается маленький узловой helper на Go, собираемый для архитектуры узла и устанавливаемый отдельно от daemon. Разбор YAML использует существующую библиотеку; тесты проверяют отказ при неоднозначном или повреждённом входном YAML, сохранение чужих mirrors/configs/TLS и обновление только auth ghcr.io. Сериализация охватывает все четыре операции; временные файлы и копия остаются в root-owned каталоге. После сбоя повтор сверяет конфигурацию и состояние предыдущей версии. Приёмка включает два одновременных вызова, повтор, отказ при symlink и небезопасных правах, сохранение предыдущего состояния при сбое, restore и явный apply. Проверить доступ к файлу от имени paas и daemon.

Для проверки реального приватного pull владелец вводит токен в своём терминале на выделенном стенде. Нужны тестовый приватный digest без локального cache, отказ до настройки и успешный pull после применения. Значение токена для отчёта и передачи в чат не требуется.

### Исходный образ для проверки GHCR

8 ноября для контроля указан `ghcr.io/dkoshenkov/kaizen/kaizen:sha-523f10c`. На запрос без Authorization реестр вернул 401 с Bearer challenge. Стандартный обмен без имени и пароля выдал анонимный токен (HTTP 200). С ним GHCR вернул индекс (HTTP 200) с digest `sha256:5faa7061163cefc0f7a25c0d1dc03ab880ca670cc1443fea10ad406b355c735f`. В индексе есть `linux/amd64` и запись с платформой `unknown/unknown`; варианта `linux/arm64` в нём нет. Проверка читала manifest. Запуска контейнера и загрузки слоёв не проводилось. Этот образ подходит для проверки анонимного чтения manifest. Для закрытия 3.4 нужен отдельный приватный digest с подходящей платформой и успешный pull на ноде после ввода credentials оператором.

По просьбе владельца создан отдельный приватный [репозиторий стендового образа](https://github.com/dkoshenkov/paas-ghcr-pull-fixture). Локальная сборка OCI содержит исполняемый файл для Linux amd64 и arm64 и использует непривилегированного пользователя 65532. Начальный коммит `2dacc4398dcea52376dc1c271dc8e02457de26fb` опубликован в main тестового репозитория. [Сборка GitHub Actions](https://github.com/dkoshenkov/paas-ghcr-pull-fixture/actions/runs/42502827422) отправила в GHCR индекс с digest `sha256:d0f5b3381bab1803b4ff78c3cb9a4e475135716e9a9ea61b7bdae68839568642`. Независимый анонимный запрос pull scope получил 401. В первоначальном workflow проверка после push завершилась ошибкой `cannot overwrite digest`; этим запуском авторизованное скачивание обеих платформ не подтверждено. После исправления workflow (коммит `9937f05a6b44dd4b0f0c05b270999f56a55f47b7`) выполнен [один ручной запуск проверки](https://github.com/dkoshenkov/paas-ghcr-pull-fixture/actions/runs/42505485626) по прежнему digest. Результат — success. Шаги сборки и публикации пропущены. Со временным токеном runner скачал индекс, оба манифеста, конфигурации и слои и сверил их SHA-256. Манифест amd64 — `sha256:453b052da9c649c5bfe1d40c74c720f2da5d4b3037f819af4860d2829d5ac2ed`, arm64 — `sha256:a08c21b86b6d7580d67cb77ffcb476ac8543769d80dcbf14e94c3d4fb4fb79fe`. Независимый анонимный запрос получил отказ. На ghcr-check для первоначальной отрицательной проверки временно закрепили адрес ghcr.io из-за сбоя DNS, после чего на пустом кеше наблюдался отказ авторизации. Положительный pull с ноды через настроенный узловой helper остаётся частью 3.4.

Синтетический TUI-прогон 8 ноября прошёл set, restore и явный apply, но тогда runner сохранял только `registries.yaml`. Он перезаписал helper-копию `registries.yaml.paas-previous` синтетическим baseline (207 байт, SHA-256 `e63d74d1a0c19f7cc6d555333ecce52ff09f71dcbe96e49f425da2f2d83d3b34`); исходного файла до прогона нет, восстановить его прежнее содержимое нельзя. Runner исправлен: теперь он заранее сохраняет и восстанавливает `registries.yaml`, `registries.yaml.paas-previous`, `registry-applied` (включая отсутствие, владельца, права и время изменения), отказывается работать с symlink и проверяет восстановленный helper status. Положительный pull ещё не запускался; статус helper и готовность k3s сами по себе pull не подтверждают.

## HTTPS и постоянное состояние Traefik

Предлагается единый доверенный профиль `traefik/web/websecure/letsencrypt`. Его настраивает административный установщик через конфигурацию штатного packaged chart k3s. Только после проверки фактического Traefik и сохранности state установщик передаёт профиль в конфигурацию Pod daemon. Runtime применяет этот профиль при построении Ingress, пользовательский YAML не задаёт другую конфигурацию. При отсутствии профиля preview Ingress должен сообщать ошибку. Deployment и Service без Ingress доступны независимо от ACME.

Один приватный PVC local-path хранит отдельные закрытые файлы для staging и production. При обновлении Recreate останавливает прежний writer до запуска нового. Признак первоначальной инициализации хранится отдельно от PVC на узле; потеря прежнего тома останавливает настройку до восстановления. Для первой версии предлагается резервная копия на выбранном оператором защищённом внешнем носителе с ограниченным доступом. Копирование и восстановление делаются при остановленном writer; сравниваются права и отпечаток восстановленного сертификата. Ключи ACME и резервная копия недоступны daemon и прикладным Pod.

Приёмка на изолированном стенде использует тестовую CA, проверяет HTTP-01, приоритет solver, redirect, restart, потерю state, backup/restore и отсутствие двух одновременно работающих writers. Отдельный probe в ctl проверяет DNS, ожидаемый адрес, SNI/SAN, цепочку и сроки из точки оператора. Результат TLS получает собственные время проверки и состояние. Для испытания публичного staging понадобятся тестовый FQDN, направленные на узел A/AAAA, доступные извне порты 80/443 и контактный email. Обращение к публичной CA и использование production-профиля требуют отдельного выбора оператора.

Основание — [контракт registry](../../openspec/changes/define-k3s-paas-foundation/specs/application-secrets/spec.md#requirement-credentials-приватных-образов-ghcr-настраиваются-через-cli) и [условия HTTP-01 и ACME](../../openspec/changes/define-k3s-paas-foundation/specs/shared-infrastructure/spec.md#requirement-traefik-обеспечивает-внешний-https-и-автоматическое-продление-сертификатов).

### Испытание с тестовой CA на tls-check

В конфигурации Pod daemon проверенный профиль передаётся через
`PAAS_INGRESS_PROFILE`. Допустимы значения `traefik/web/websecure/letsencrypt/staging`
и `traefik/web/websecure/letsencrypt/production`. Стенд с Pebble использует
`staging`. При отсутствии параметра или неизвестном значении preview Ingress
должен вернуть `INGRESS_PROFILE_UNAVAILABLE`; Deployment и Service остаются
доступными. Принадлежность к production-профилю и внешний результат TLS
проверяются отдельно. С PostgreSQL 18.6 и тестовым клиентом Kubernetes смена staging на production после сохранённого preview дала HTTP 409 PLAN_CHANGED при apply. Операция и резервы не появились. Приёмка доставки параметра на ноде ещё открыта. [Тест preview/apply](../../../paas-daemon/internal/daemon/deployments_test.go).

На выделенной ноде k3s v1.37.2+k3s1 с packaged chart traefik-41.6.101+up41.6.1 сервер Pebble v2.10.1 подтвердил три HTTP-01 запроса через порт 80. Для обычного HTTP-запроса Traefik вернул 308, а HTTPS с проверкой цепочки тестовой CA вернул ответ приложения. После остановки writer и ручного восстановления копии вернулся исходный отпечаток сертификата. В отдельном тесте принудительно сократили время до планового продления через настройку certificatesDuration: выпущен сертификат с новым отпечатком. Публичная CA в испытании не участвовала.

Перезапуск выявил изменение прав файла ACME с 0600 на 0660 под действием fsGroup. Traefik перестал использовать resolver и отдавал default certificate при готовом Pod. В эксперименте init-контейнер восстановил 0600. Для закрытия 3.5 требуется повтор через штатный установщик, с проверкой UID тома и identity ACME перед каждым запуском, штатными backup/restore и отображением проверенного профиля в TUI.

### Связь Traefik с backend управляемого приложения

На network-app-check до публикации Ingress Service B1 отвечал `v1` на HTTP
из собственного Pod по адресу `10.43.182.119:8080`. Из сетевого пространства
работающего `kube-system/traefik-68df944ff7-48h2t` подключение к тому же
адресу получило отказ. В схеме v13 базовая ingress-политика обычного компонента
разрешает связь внутри своего приложения. Эксперимент с тестовым Namespace
без этой политики не доказывает доступность приложения через Traefik. Для
финальной проверки нужен Ingress, принятый через PaaS, и ответ управляемого
backend через внешний HTTPS.

### Отображение CA-профиля в TUI

При чтении доменов приложения `GET /apps/domains` может вернуть необязательное
поле `tls_profile` со значением `staging` или `production`. Источник — профиль
работающего daemon, переданный узловым установщиком. Если профиль неизвестен,
поле отсутствует. TUI показывает выбранный профиль рядом со временем и
результатом проверки домена. Само чтение доменов не устанавливает готовность.

Для production операторский probe проверяет каждый ожидаемый адрес, доверенную
цепочку системы и имя в сертификате. Для staging оператор может передать
публичный корень тестовой CA из локального PEM-файла только для этой проверки.
При успешном handshake такой результат явно помечается staging. Ошибка или
отсутствие доверия сохраняет ERROR. Для старого daemon без поля TUI показывает
наблюдение TLS с неизвестным профилем. Старый клиент может пропустить новое
поле при чтении ответа. Владелец одобрил дополнение API и проверку TLS 8 ноября.

SDK и OpenAPI сгенерированы Flux v0.7.0. В HTTP-тесте с PostgreSQL 18.6
работающий daemon вернул оба допустимых значения в соответствующих
конфигурациях, а при неизвестном значении опустил поле. Старый клиент,
сгенерированный до добавления поля, прочитал ответ с `tls_profile`.
Сквозная проверка выбора PEM и отображения результата в TUI остаётся открытой.

### Проверка UID перед стартом Traefik

Владелец выбрал прямое чтение Kubernetes API и одобрил минимальную Role.
Штатный установщик создаёт в `kube-system` Role для core-ресурса
`persistentvolumeclaims` с `verbs: ["get"]` и `resourceNames: ["traefik"]`.
RoleBinding указывает только ServiceAccount `kube-system/traefik`.
Init-контейнер и основной процесс используют одну учётную запись и получают
одинаковое право на метаданные этого PVC. Узловой прокси для проверки UID исключён.

На control-check до установки Role команда `kubectl auth can-i get` от имени
фактического ServiceAccount с его стандартными группами вернула `no` для PVC
`traefik` и контрольного имени `unrelated-guard-control` в `kube-system`.
На выделенной tls-check исходный запрос `auth can-i get pvc/traefik` также
вернул `no`. После создания Role и RoleBinding `paas-traefik-guard-pvc` реальный
GET с impersonation SA и его системных групп вернул UID
`4042b318-327e-4986-98ee-ee1968dc25b4` и фазу Bound. GET контрольного имени
получил Forbidden. Для list PVC и patch, update, delete именованного PVC
проверка полномочий вернула `no`. На tls-check ресурсы RBAC созданы вручную. На чистой tls-app-check команда
`paas-ctl node traefik install` создала Role с UID
`6c33072a-1352-40a9-b488-8d53d3697afb` и RoleBinding с UID
`eb5afd94-19f9-4d9f-b9ed-81d186ba1faa`. Независимое чтение из API подтвердило
точный rules и единственного получателя. При первой попытке установщик ошибочно
счёл код выхода 1 у ожидаемого ответа `kubectl auth can-i: no` сбоем и
остановился до создания HelmChartConfig. После исправления обычный повтор создал HelmChartConfig и PVC. Chart применил стратегию Recreate и init-контейнер `paas-traefik-guard`. PVC `5749b805-9059-47ee-88cb-910e91226e9e` связался с PV `911cbd3c-3b45-4245-944f-b139f6dcb67e`. На этой ноде провижионер использует `spec.local.path` и создаёт новый каталог root:root 0777 под закрытым родителем. Штатная инициализация должна проверить принадлежность этого каталога перед изменением прав. При старте guard читает UID связанного PVC, проверяет
отсутствие удаления и сверяет UID с маркером узла и идентичностью смонтированного
тома. При недоступном API или несовпадении guard блокирует старт writer.

### Восстановление на заменённый PVC

После замены тома guard обнаруживает расхождение UID и останавливает запуск.
Для явного восстановления оператор подтверждает старый и новый
UID. Администратор останавливает writer. Установщик сверяет защищённую копию
с сохранённым маркером узла, переносит state на выбранный том и проверяет ACME
аккаунт и сертификаты. Только после проверки он привязывает маркер к новому UID
и разрешает запуск. В приёмке внешний TLS-клиент должен увидеть исходный сертификат.
Владелец одобрил эту процедуру 8 ноября. Приёмка на заменённом PVC остаётся открытой.

В рабочей копии административная команда `paas-traefik-recovery` принимает
`backup`, `restore` и `restore-replacement`. Последняя операция требует путь
к защищённой копии и оба UID. Локальный тест проверил восстановление на новый
том, обновление профиля установки и повтор команды при потере ответа на
изменение HelmChartConfig. При чужом UID исходного PVC команда отказала.
В этих тестах ответы Kubernetes задавались в процессе теста. Для приёмки на
k3s предстоит наблюдать остановку прежнего writer, смену UID и сертификат
через внешний TLS-клиент. [Проверка команды](../../../paas-ctl/internal/traefikguard/operator_test.go).

Linux-команда сохраняет копию в закрытом каталоге на отдельной файловой системе.
Для публикации файлов она использует `O_TMPFILE`: создаёт безымянный файл,
записывает данные, выполняет `fsync` и только затем присваивает окончательное
имя без перезаписи существующего файла. Носитель копии должен поддерживать эту
операцию и Unix-права. В отдельном контейнере Linux/arm64 проверены прерывание
перед присвоением имени, повторная запись и отказ при подмене файла на FIFO.
Поведение на файловой системе выбранного резервного носителя проверяется при
стендовой приёмке. [Тесты публикации файлов](../../../paas-ctl/internal/traefikguard/durable_test.go).

Для штатной приёмки подготовлена отдельная `tls-app-check`. Бинарник
k3s arm64 совпал с SHA-256 профиля. На свежей ноде штатный chart
`41.6.101+up41.6.1` запустил одну готовую реплику Traefik. До установки
PaaS отсутствовали HelmChartConfig и PVC с именем `traefik`, ServiceAccount
не имел права читать этот PVC. Локальный ACME directory Pebble ответил с
проверкой цепочки. На ноду передан публичный корень соединения с Pebble в
ConfigMap `tls-check-ca`. Для копии подключён отдельный виртуальный ext4-диск
`/dev/vdb1`: каталог `/mnt/lima-tls-acme-backup/backup` принадлежит root:root
и имеет режим 0700. На этом диске прошли проверки прерывания до публикации,
повтора без перезаписи существующего файла и отказа на FIFO. Возврат прежнего
сертификата после замены PVC на этой установке ещё предстоит проверить.

Ошибка копирования не должна оставлять работающий HTTPS выключенным. Перед
остановкой Traefik команда проверяет возможность записи на носитель. При
исчерпании места во время backup она повторно сверяет исходные UID и ACME state,
возвращает прежнюю конфигурацию и ожидает одну готовую реплику с успешно
завершившимся guard. Оператор получает ошибку копирования. После сбоя самого
возврата повтор использует журнал на ноде, даже если носитель уже отключён.
При ошибке restore содержимое тома может быть изменено, поэтому writer остаётся
остановленным. Эти ветки прошли тесты с подменой Kubernetes и дисковой ошибки.
