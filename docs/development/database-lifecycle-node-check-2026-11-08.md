# Приёмка отзыва SQL-доступа и удаления БД на v5-fresh

Для проверки созданы два приложения через обычный деплой с начальной миграцией. Область удаления ограничена первым приложением. Второе служит для проверки изоляции.

| Назначение | app_id | Первая операция деплоя | Результат |
| --- | --- | --- | --- |
| Одноразовая БД для отзыва и удаления | `203db593713d4491b0e71a5e3003ec33` | `e7787200edfeff55047226c18668ac0a` | SUCCEEDED |
| Соседнее приложение | `b38b35b34f8548c9922215a39e3a6807` | `1baabaa02cc38d0284ffdfbe471bf01a` | SUCCEEDED |

До обновления схемы с v10 на v11 выполнены четыре подключения psql, по одному под APPLICATION и MIGRATOR каждого приложения. На ноде сохранены OID обеих БД и их ролей, UID Secrets, Namespace, Deployment и Jobs, контрольные значения для сравнения паролей и содержимое прикладной схемы и таблиц миграций. Файл сравнения доступен только root. Скрипт воспроизведения — `paas-ctl/scripts/testdata/lifecycle-fresh-baseline.py`.

## Переход с v10 на v11

После установки совместимого daemon отдельный Goose Job v11 завершился успешно. Исходные данные совпали, все четыре SQL-входа снова прошли. Через UDS оператор получил для целевого приложения HTTP 200, состояние READY и ACTIVE для обеих ролей. Повтор установки выявил две устаревшие проверки номера схемы в установщиках daemon и Namespace. После исправления штатный `install-daemon` подтвердил Ready для образа `sha256:50c0f3b8f16d11eea3748e64db65d0d7a19375655b5d5379df853956990d7391`.

На отдельном PostgreSQL проверен повтор каждого из 11 внешних шагов. Тест прерывал исполнение после изменения ресурса, до чтения результата и подтверждения шага. При повторе использовался сохранённый журнал. Тест проверил сохранность данных соседней БД и остановку при зависимости роли за пределами целевой БД. Kubernetes в этой проверке моделировался. Скрипт воспроизведения — `paas-ctl/scripts/testdata/app-db-lifecycle-real.py`.

## Отзыв APPLICATION через TUI

Операция `7f3ff50cc9fa911919f599992f39be88` завершилась SUCCEEDED. Работающая psql-сессия APPLICATION завершилась, новый вход со старым паролем был отклонён, а запрос credentials вернул HTTP 409 ACCESS_REVOKED. Сессия MIGRATOR целевой БД и обе сессии соседней БД продолжили работу. Состояние соседнего приложения совпало с исходным снимком. Повтор запроса с исходным request_id вернул тот же operation_id. Запрос с новым request_id и прежней revision получил HTTP 409. Скрипт воспроизведения — `paas-ctl/scripts/testdata/lifecycle-fresh-revoke.py`.

Для обратного случая на отдельном PostgreSQL отозван MIGRATOR при активном APPLICATION. Текущая сессия мигратора завершилась, новый вход был отклонён. Прикладная роль сохранила действующую сессию, смогла открыть новую и прочитать контрольные данные. Там же проверены отказы при несовпадении OID базы и реальной подмене роли одноимённой ролью с другим OID. Для Secret проверялась подмена UID в модели Kubernetes.

## Удаление через TUI

После ввода неверного имени и на экране до окончательного подтверждения состояние БД сохранялось. Операция `079ea114976e2780ba08de83731fea48` завершилась SUCCEEDED. Проверка PostgreSQL показала отсутствие целевой БД и трёх выделенных ролей. Сессия MIGRATOR завершилась. API Kubernetes вернул NotFound для двух прикладных Secrets. Запись приложения и его первый деплой сохранились. Обе сессии соседнего приложения продолжили работать, а его данные, пароли и идентификаторы совпали с исходным снимком.

Повтор принятого удаления вернул исходный operation_id. Новый запрос удаления получил HTTP 409. Из TUI повторно отправили валидный манифест компонента с запросом миграции. Preview сообщил об удалённой БД. После этого проверены терминальное состояние, отсутствие целевой БД и обоих Secrets, а также сохранность соседнего приложения. Скрипты воспроизведения — `paas-ctl/scripts/testdata/lifecycle-fresh-delete.py` и `paas-ctl/scripts/testdata/lifecycle-fresh-terminal.py`.

Оператор открыл в TUI обе карточки APP, для отзыва и удаления показан SUCCEEDED. Старый запрос истории исключил эти записи, прежний inspect вернул для каждой 404. На отдельном PostgreSQL 18.6 при действующей резервации RUNNING-миграции хранилище отклонило и revoke, и delete как ResourceBusy. Ревизия не изменилась, дополнительная операция и запись действия не появились.
