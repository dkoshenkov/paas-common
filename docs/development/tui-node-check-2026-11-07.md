# Приёмка операторского TUI на одной ноде

Этап 6.2 проверен на Debian 13 arm64, однонодовом k3s v1.37.2+k3s1 и PostgreSQL 18.6.
Для аварийных проверок использовалась вторая независимая ВМ с собственным ядром.
Демонстрационный сервер оставался доступен. На каждом стенде работала одна нода.

| Действие | Наблюдение |
| --- | --- |
| Установка из Bubble Tea | В настоящем PTY оператор выбирает профиль и два digest, подтверждает установку клавишей y. Через SSH прошли четыре шага. Пустые списки отобразились после подключения к daemon. |
| Каталог после наполнения | На 11 приложениях и 11 операциях проверены следующая и предыдущая страницы, компонент выбранного приложения, карточка, фильтр ACCEPTED и выход. Тестовые записи вносил администратор SQL. |
| Ошибки доступа | При чужом SSH-ключе TUI показал ошибку подключения. Пользователь paas прочитал /health через UDS. Независимый пользователь nobody не смог открыть сокет. |
| Недоступность PostgreSQL | StatefulSet масштабирован до нуля. Через тот же сокет /health вернул 200, /ready — 503. В TUI отобразилась неготовность control plane. После возвращения PostgreSQL тот же Pod daemon с тем же счётчиком рестартов вернул 200. |
| Повтор и обновление | Повтор install-daemon сохранил UID Pod. Обновление образа с 66492982 на 6123abdd сменило UID Pod и сохранило UID Deployment. В новом процессе каталог и страницы операций читались через SSH. |
| Холодная загрузка | Выключение и запуск ВМ изменили boot_id с 16b523fe-ef5c-4719-b4fa-8c5d55146adc на 97b5004d-1be9-4d7a-97b5-d44cf7bc5368. В /run повторно появился сокет 0660 с UID/GID 61001. После запуска тестового loopback sshd прежний ключ открыл каталог; команда status подтвердила готовность БД. |

Сценарий терминала находится в [test-tui-node.py](../../../paas-ctl/scripts/test-tui-node.py).
Он запускает собранный ctl с controlling PTY и проверяет итоговый экран с помощью pyte.
Для заполненного сценария применяется [tui.sql](../../../paas-ctl/scripts/testdata/tui.sql),
который проверяет, что тестовый каталог пуст. Команды управления описаны в

## Дополнительная приёмка на control-check 8 ноября

- Карточка ручной APP-операции получает подробный статус через inspect. Клавиша `l` открывает её структурированный журнал. В отдельной PTY-сессии проверен просмотр завершившейся операции и событий Job.
- На экране приложения `s` открывает настройки мигратора. На тестовом Acceptance-plain просмотр, подтверждение образа и снятие настройки выполнены через PTY. Запрос к БД подтвердил возврат к исходному NULL. Проверка конфликта ревизии выполнена в тесте TUI.
- Клавиша `h` открывает домены приложения. В PTY зарегистрирован `tui-check-20261108.invalid`, затем оператор подтвердил отзыв. API вернул исходный список доменов.
- Для оператора на тестовой ВМ подготовлена сборка ctl с SHA-256 `2b1c6a8ef45495bd25e4d9aad3e56b8bb34b17c4def680890cac98c329a8ed30`. В терминале проверен запуск профиля control-check, переход Enter к непустому каталогу через SSH и выход клавишей q с кодом 0.

## 7.1. Два приложения после перезапуска daemon

[Сценарий 7.1](../../../paas-ctl/scripts/testdata/tui-two-apps-restart.py) принимает пути к ctl, fixture SSH, терминальному helper и рабочему манифесту, а также ID обоих подготовленных приложений. Он использует PTY, SSH/UDS, реальный PostgreSQL и Kubernetes API. При повторе число реплик второго приложения переключается между одной и двумя.

В итоговом прогоне ручная APP-миграция `afacfc13dbc7b0c29dc838ff398034ca` создала один завершившийся Job. Независимый COMPONENT-деплой `89e17d9c1cbc6a03817f6fc7f316d509` второго приложения уменьшил число реплик с двух до одной и прошёл rollout без нового Job. UID Deployment сохранились, соседнее приложение не изменилось. После смены UID Pod daemon сценарий заново открыл обе записи в TUI и увидел SUCCEEDED. Отдельный контрольный запрос inspect подтвердил оба ID, типы целей и терминальные состояния.

До и после сверены UID и пароли двух Secrets каждого приложения, OID и права БД и ролей, схемы и таблицы, строки notes и история Goose. Попытки TCP-входа прикладной ролью в чужую БД дали отказ в CONNECT в обе стороны до и после сценария. Пароли и данные сверялись в памяти. Два предварительных прогона создали дополнительные успешные операции и сменили Pod, но проверка формата карточки COMPONENT в скрипте завершилась ошибкой. После исправления сценарий полностью прошёл одним запуском.

## Импорт и отзыв публичных Ed25519

В меню ключей действие `g` загружает публичные ключи аккаунта. Оператор отмечает совместимые ключи пробелом, проверяет сервер и список SHA-256 отпечатков и подтверждает установку. При частичном успехе показан результат каждого ключа. Повтор предлагает только неудавшиеся записи и требует нового подтверждения. Возврат к экрану ключей и действие `x` загружают список импортированных ключей с самого узла. После подтверждения TUI сообщает об удалении записи. Проверка нового входа с другого рабочего места требует доступа к соответствующему приватному ключу.

В [интеграционной проверке модели TUI](../../../paas-ctl/internal/tui/github_acceptance_test.go) локальная HTTPS-фикстура вернула две страницы с разными ключами. Модель выбрала второй отпечаток и вызвала настоящий SSH helper. Новая аутентификация выбранным ключом прошла, другой ключ доступа не получил. После отзыва новая попытка входа перестала проходить, исходный операторский ключ продолжил работать. Фикстура подменяла транспорт только в тестовом процессе.

[Отдельная проверка sshd](../../../paas-ctl/scripts/testdata/ssh-key-import-live.sh) дополнительно подтвердила повторную установку без дубликата, конкретный SSH-отказ publickey после отзыва и побайтовое совпадение итогового authorized_keys с исходным. Перегенерация `make sdk` закреплённым Flux оставила идентичными все 81 файл проверенных каталогов Go SDK и OpenAPI/protobuf. Изначально запрос к публичному api.github.com завершился таймаутом, затем HTTP 504. Позднее production `githubkeys.List` с хоста успешно прочитал публичный API по TLS и вернул 3 допустимых Ed25519-ключа; значения ключей не выводились. Ни один внешний ключ в приёмке не устанавливался.

Команда запуска демонстрационного control-check обновлена на ctl с SHA-256 `faa2b70b52e633af256774a98459b455883721801a8bef8cbb9aecfc9b31105c`. В PTY проверены переход к ключам и открытие формы GitHub. Из ВМ отдельный HEAD-запрос к GitHub вернул 200, а полноценный запрос списка через TUI завершился сообщением об ошибке до выбора и записи ключей. Проверку реальной многостраничной выдачи публичного API оставили открытой.

## Обновление v5 → v8 через мастер

На отдельной остановленной ВМ v5-fresh перед испытанием подтвердили её имя и включили именно эту ноду. После загрузки k3s показал один Ready-узел, PostgreSQL и daemon готовы, PVC в Bound, прежний Job v5 в Complete. Версии Goose 0–5 применены. На ноде отсутствовали прикладные workloads.

В реальном PTY профиль `d` выполнил обновление с v5 до v8 и после этого прошёл повторно. На ноде подтверждены применённые версии Goose 0–8 и завершение Jobs v5 и v8. Сохранились UID прежнего Job, Deployment daemon, StatefulSet PostgreSQL и PVC. При повторной установке сохранился и UID Job v8. Через каталог и историю в TUI прочитаны пустые страницы. В конце ВМ вернули в исходное состояние stopped. Эта проверка охватывает путь v5 → v8 с пустым каталогом. Для остальных предлагаемых мастером версий и для сохранности непустых данных нужны соответствующие исходные состояния.

## Образы контейнеров и имена полей прикладного Secret

На control-check со схемой v8 проверены новые GET через SSH/UDS и через [терминальный сценарий](../../../paas-ctl/scripts/testdata/tui-metadata.py). В окончательной сборке daemon `sha256:5079fdf6464f3b3cb404f1f9c50549e02ed1fa6e9fb67086ef96caa7d949a30a` карточка компонента `672130f4fd34e6a7a04ee1eebb66bbb4` показала Deployment `orders-backend`, обычный контейнер и digest фактического образа. В PTY сверили его начальную часть, через API — полное имя образа с Kubernetes. Регистрация без Deployment дала пустой список, ссылка на компонент другого приложения — 404, отсутствие app_id в запросе — 400.

Клавиша `b` у приложения `b816c1ef8f8847a89f20392b02823b66` показала `paas-app-db` и имена database, host, password, port и username. Через API проверен полный набор полей ответа: app_id, secret_name и keys. Отдельный POST выдачи credentials не вызывался. Для приложения без настроенной БД и для отсутствующего app_id GET дал 404. Esc вернул оператора к списку компонентов.

На PostgreSQL с UDS и тестовым Kubernetes client проверены состояние PENDING (409), подменённый UID Namespace или Deployment (503) и исключение добавленного контроллером sidecar из выдачи. Перегенерация SDK закреплённым Flux дала те же хеши всех 86 файлов проверенных деревьев. В демонстрационной команде используется ctl `3f7eb1ea24bfcba0d2d4715ca4ff1f32e1aee0b07a2b7a3bb6cf492e41c2a664`.
