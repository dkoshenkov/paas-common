# Исполнение подтверждённого плана на одной ноде

**Реализация одобрена пользователем 8 ноября.** Этап связывает хранилище 3.3, подготовку БД 4.x и сценарии
5.1–5.4 с реальным исполнителем и экраном 6.3. Подготовка отдельного Namespace
уже выполняется доверенной SSH-командой. Предлагается расширить её фиксированный
профиль перед включением worker. [Требования к деплоям](../../openspec/changes/define-k3s-paas-foundation/specs/independent-deployments/spec.md).

## План и полномочия

Для объектов приложений использовать официальный Kubernetes Go SDK ветки 1.37,
строго декодировать четыре разрешённых вида API, сохранять ошибки с координатами
исходных документов. Применять согласованные правила защищённых полей, привязок
Secret, доменов, маршрутов и сервисов. UID Namespace из подтверждённой подготовки,
текущие UID и resourceVersion управляемых объектов, состояние готовности БД,
ревизии политик, идентичности Deployment и выводимые изменения включать во
внутренний план. В ответ оператору отдавать публичный план и безопасные diagnostics.
Перед принятием повторно построить план; перед записью проверить предусловия
Kubernetes. Никаких внешних записей в preview. Отдельный разрешённый профиль
доступа к API должен быть включён до запуска workers.

Namespace-local RoleBinding выдаёт исполнителю доступ к четырём типам ресурсов,
наблюдению своих Pods, ReplicaSets и EndpointSlices, управлению NetworkPolicy и
защищённым Job мигратора. Выдача RBAC, Namespace, workload SA и чтение/создание
прикладных Secrets остаются отдельными доверенными действиями с их узкими
разрешениями. Определение полномочий включает фактическую проверку Kubernetes
admission и сети на установленной ноде.

## Исполнение и восстановление

После атомарного принятия фоновый worker в daemon получает операцию из PostgreSQL.
В пределах одной ноды предложен один цикл планирования с исполнением до четырёх
операций на разных свободных целях. Перед каждым внешним действием фиксируются
его вид, объект и ожидаемое состояние; результат подтверждается через API.
После рестарта worker сверяет намерение и живой объект. Создание использует
стабильное имя и сверку owner/UID, обновление — UID и resourceVersion. Изменять
только управляемые пути, сохранять поля других контроллеров. Новый ресурс с тем
же именем требует проверки принадлежности. Неопределённый исход сохраняет
RECOVERY_REQUIRED с резервами, известный частичный результат — безопасную
диагностику. Терминальный переход и освобождение снимка/резервов атомарны.

NetworkPolicy, SA и привязки устанавливаются до запуска пользовательских Pods.
При первом деплое с мигратором worker ждёт достоверной готовности БД и успешного
Job. Остальные деплои запускают Job только по явному выбору. Одна операция
меняет выбранный компонент и его объекты. Готовность определяется по поколению
Deployment, количеству updated/ready/available Pods и EndpointSlices своих
Service. Срок rollout — 10 минут, отдельного migration Job — 30 минут.

## Действия в TUI и проверка

На экране приложения оператор выбирает компонент и файл либо каталог. TUI
передаёт исходные YAML, показывает WARN/ERROR и план, после подтверждения
отправляет apply, показывает operation_id и открывает карточку. Прерванное
ожидание можно продолжить из истории. Регистрация приложения и компонента,
настройки мигратора и независимое обновление образа используют действующие
контракты. Credentials раскрываются только по явному выбору назначения.

Приёмка включает реальный первый деплой, два независимых компонента, отказ
чужому Namespace/UID/Secret, конкуренцию apply, потерю ответа между намерением
и записью, рестарт daemon на каждой границе, истечение rollout и новое
обращение к истории. Затем пройти полный сценарий 7.1 на одной ноде. Отдельно
подтвердить совместимость профилей с уже установленной схемой v4.
