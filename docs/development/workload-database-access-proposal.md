# Доступ Deployment к прикладной БД на одной ноде

**Одобрено владельцем 8 ноября 2026 года.** Для v1 предлагается закреплять разрешение на Secret за экземпляром Deployment в PostgreSQL и открывать TCP/5432 по уже защищённой метке Pod. Первое применение может включать начальную миграцию и запуск приложения за одну операцию.

## Действующий контракт и пробел реализации

Оператор сохраняет `database_grants` в политике компонента с `expected_revision`. Каждый grant задаёт Deployment, тип и имя контейнера, список ключей либо `whole_secret`. YAML явно ссылается на `paas-app-db`. Secret мигратора зарезервирован для платформенного Job. Разрешение до первого деплоя и запрет наследования при пересоздании уже описаны в [согласованной политике](manifest-policy-proposal-2026-11-07.md).

Сегодня `DeploymentTarget` выводит instance ID из ownership или вычисляет его для нового Deployment с учётом удалённых экземпляров, но не заполняет `Profile.Bindings`. Проверка `secretReferences` поэтому отклоняет даже явно разрешённую ссылку. Она уже разбирает env, envFrom, Secret-тома и projected-тома для каждого потребителя. Только после успешной проверки шаблон Pod получает метку `paas.dkoshenkov.io/app-database=true`. В admission резерв БД пока зависит от наличия миграции. У postgres уже есть ingress `paas-workload-<app_id>`, а в Namespace приложения с default-deny специальный egress к БД и DNS есть только у мигратора.

## Привязка и первый apply

1. **Запись политики.** Для каждой новой комбинации (app, component, Deployment, container_kind, container_name) создать внутреннюю запись в той же транзакции. Она хранит UID Namespace и фазу. Ключи и whole_secret по-прежнему определяет политика. Для будущего Deployment фаза — «ожидает». Для существующего собственного — сохранить instance ID и UID из подтверждённого ownership. Чужое владение блокирует выдачу. При обновлении несвязанного поля политики существующая привязка сохраняется. Для старых grant без записи отказать и потребовать явного снятия и повторной выдачи.
2. **Preview.** Показать ожидающую привязку только как часть плана этого Deployment. Проверить точного потребителя, свободное имя для CREATE либо учтённые instance и UID для UPDATE, UID Namespace и ревизии политики и БД. План сохраняет эти доказательства. Если БД предстоит создать, план указывает начальную подготовку и миграцию. В иных случаях нужны READY, ACTIVE для APPLICATION и подтверждённый UID Secret.
3. **Admission.** Под теми же блокировками, что и policy write и lifecycle, повторно проверить план. Для фактического потребления взять резерв БД даже без миграции, а для первого CREATE — эксклюзивный резерв (UID Namespace, Deployment, имя) между компонентами. В транзакции приёма записать instance ID и operation ID в ожидающую привязку. Операция одновременно с миграцией занимает один резерв БД. Повтор apply возвращает исходную операцию.
4. **Перед запуском Pod.** В том числе после начальной миграции сверить фактические READY, ACTIVE, identity БД, UID Secret и Namespace, сетевые правила и резерв. Для UPDATE проверить live UID и resourceVersion. Для CREATE использовать создание с отказом при занятом имени. Сверенный UID нового объекта записать вместе с подтверждением action и ownership. При потере ответа сверить сохранённый intent и доказательство авторства. Если авторство установить нельзя, сохранить резерв и RECOVERY_REQUIRED. Присваивать себе найденный по имени объект запрещено.
5. **Удаление и повтор.** При подтверждённом удалении закрыть привязку вместе с записью ownership. Совпадение имени, меток или номера ревизии политики не открывает её снова. Оператор повторно выдаёт grant явным удалением записи из политики и новым добавлением. Потеря объекта с живой записью ownership или подмена UID требуют сверки. При доказанном отсутствии внешнего эффекта после отказа до CREATE разрешается вернуть впервые зарезервированную привязку в ожидание.

## Сеть и границы прав

Предлагается добавить в `prepare-app.py` одну платформенную egress NetworkPolicy на Namespace. Она выбирает те же Pod, что существующий workload ingress PostgreSQL (точный app, защищённая DB-метка, component и instance), разрешает TCP/5432 только postgres Pod в `paas-postgres` и UDP/TCP 53 только kube-dns в `kube-system`. Подготовка проверяет spec и владельца обеих сторон при новом и повторном запуске, в том числе для ранее подготовленного Namespace. Неизвестная разрешающая политика останавливает подготовку. Обычный манифест не может выставить платформенную метку. Допуск TCP распространяется на весь Pod, а Secret доступен только указанным потребителям. В модели v1 административная запись Pod, Deployment и NetworkPolicy в управляемых Namespace доверена платформе.

После проверки обеих политик доверенный prepare сохраняет их UID вместе с UID Namespace в существующей записи подготовки приложения. Обе колонки заполняются вместе. Daemon сверяет локальный egress по UID и spec. Для ingress в Namespace PostgreSQL используется подтверждение доверенного установщика; при повторном prepare он заново проверяет объект. При отсутствии подтверждения apply с DB Secret отклоняется.

Goose создаёт таблицу привязок. `paas_settings_writer` нужны чтение identity/состояния потребления и запись ожидающей или явно повторно выданной привязки в транзакции политики. `paas_operation_writer` нужны чтение привязки и обновление полей приёма, UID и закрытия в транзакциях admission/ownership. Разграничить SQL-права по таблицам и колонкам, проверить их фактическими ролями после обновления. Узловой provisioner сохраняет владение инфраструктурными NetworkPolicy. Для runtime достаточно существующих именованных GET Secret и наблюдения Deployment/ReplicaSet/Pod в Namespace приложения. В plan, журнал и диагностику попадают только имена, идентификаторы и ревизии.

## Снятие доступа и проверка

Обычное сужение ключей или снятие grant отклоняется с 409, пока затронутую ссылку использует принятая операция, управляемый Deployment или его прежние Pod. Оператор сначала применяет пакет без ссылки и ждёт завершения замены старых Pod. Если остаются другие разрешённые потребители в Pod, его сетевой допуск сохраняется. Экстренный отзыв APPLICATION действует сразу по [lifecycle-контракту](database-lifecycle-contract.md): NOLOGIN, завершение SQL-сессий, отказ в новых привязках и в применении старого preview. Сокет к порту и старое значение в памяти ещё не доказывают возможность SQL-входа.

Для приёмки нужны одноразовые приложения. Проверить PostgreSQL-транзакции и рестарт на границах приёма, CREATE и подтверждения UID. Одновременно подать два CREATE разных компонентов на одно имя и столкнуть apply с изменением политики, revoke и delete. На k3s проверить первый деплой с разрешением до создания БД, SQL-запрос под APPLICATION, отказ MIGRATOR Secret, запрещённый ключ/sidecar, доступность DNS и TCP только для выбранных Pod, неподдельность метки, отказ соседнему приложению и отказ одноимённому новому Deployment. Отдельно проверить сужение grant во время rollout, повтор после потери ответа и обновление существующей ноды с прежней политикой. Сохранить исходные UID, operation ID и результаты без значений Secret.

## Проверка установки схемы v12 — 8 ноября 2026

На выделенной одноразовой VM `v5-fresh` проверено штатное обновление v11→v12. До миграции совместимый reader `sha256:7d3a6164613685fda3b4d0d6297db2e5723a779a36da286e29a71ac432e8dce1` ответил `/ready` со статусом `ok` на v11. Затем установлен заранее импортированный goose `sha256:eee24be90822bcc2269a5a60e9f11ba49716d5e64a5eb3feb8833201f9f7a2da`; checksum исходника `00012_workload_database_bindings.sql` совпал с зафиксированным для образа (`b344189649f1421e7c3553beaa5878783ed23e76d01f7227c7c0a33f2d695711`). Миграция завершилась, `/ready` на v12 вернул `ok`; исходные строки БД и подготовки приложений совпали с сохранённым снимком при исключении двух новых колонок. UID всех прежних Job сохранились.

Для двух разрешённых одноразовых приложений повторная подготовка записала UID обеих workload NetworkPolicy. UID совпали с Kubernetes и сохранились при следующем повторе подготовки. Первоначальный повтор `install-postgres` выявил несовместимость старой проверки разрешений с v12; после исправления v12-профиля штатный повтор завершился успешно, UID успешного `control-migrate-v12` не изменился. Проверка PostgreSQL подтвердила отсутствие у `paas_runtime` табличного и поколоночного SELECT на `paas_workload_database_bindings`; `/ready` оставался `ok`.

Отдельно проверен **fresh SQL fixture**, а не новая установка k3s: в одноразовом контейнере PostgreSQL 18.6 выполнены свежие SQL-профили установщика и `migrate` из того же проверенного goose-образа. До и после миграции, а также после повторного применения профилей, `paas_runtime` не имел SELECT на bindings; доступ к публичному каталогу сохранился. Это не является подтверждением полной fresh-установки ноды, Kubernetes Job или сетевой приёмки. Проверки реального сетевого доступа workload и сценариев образов выполняются отдельно.
