# Хранение регистрации и настроек в однодовом PaaS

**Одобрено пользователем 7 ноября 2026 года.** SDK уже задаёт семь маршрутов и семь наборов ответов. Этот
этап добавляет им постоянное хранилище в `paas_control` и реализацию в daemon.
Применение сетевых правил, выдача Secret контейнеру, подготовка БД приложения
и запуск мигратора проверяются отдельно при исполнении деплоя.
[Контракт settings](../api/paas/settings.yaml) и
[профиль применения настроек](manifest-policy-proposal-2026-11-07.md).

## Регистрация и факт подготовки Namespace

Для `POST /apps/create` нужны и выданный сервером ID, и подтверждение доверенной
подготовки Namespace. В запросе есть только `request_id` и имя. Предлагается
перед вызовом API выполнять из ctl отдельную фиксированную SSH-операцию
подготовки приложения. Её профиль, sudoers и исходные права Namespace входят
в согласование этого этапа. Вход содержит те же два проверяемых поля.

1. Привилегированная операция на узле резервирует случайный ID приложения,
   имя Namespace и точное исходное имя приложения по ключу запроса в служебной БД.
   После короткой транзакции подготавливает Namespace и начальные ограничения
   по фиксированному профилю. Штатная повторная попытка использует прежний ID
   и проверяет владельца существующих ресурсов.
2. Закончив проверки, операция записывает Kubernetes UID Namespace в ту же
   запись резерва. При чужом объекте или смене UID оставляет конфликт оператору.
   Журнал резерва переживает сбой между созданием Namespace и записью UID.
3. Daemon внутри транзакции читает готовый резерв, проверяет scope, исходное имя,
   выданный ID и сохранённую принадлежность. Только тогда создаёт запись в каталоге.
   Пока подтверждение отсутствует, возвращает 503 с безопасным объяснением.
   Повтор после потери ответа может прочесть прежний результат прямо из каталога.
   Обращения к Kubernetes не удерживают SQL-транзакцию.

Узловой `prepare-app` принимает на stdin один JSON-объект с полями
`request_id` и `name`. Он создаёт Namespace `paas-app-<app_id>` с
Pod Security Admission `restricted` версии `v1.37`, NetworkPolicy
`default-deny` для входящего и исходящего трафика всех Pod и ServiceAccount
`paas-workload` с выключенным монтированием токена. Операция не создаёт
RoleBinding. Семь маршрутов настроек работают через SQL. Полномочия
планировщика для размещения приложений требуют отдельного согласования.

Резерв может изменять только доверенная подготовка. Daemon получает SELECT на
эти данные. Имя, метка из присланного YAML и знание `request_id` не позволяют
подделать готовый резерв. Для компонентов Namespace уже определён приложением.

## Предлагаемая схема Goose v4

Существующие строки, tombstones и историю операций сохраняет одна новая
up-миграция. Схема следует принятой проверке инвариантов в Go. Колонки данных
nullable, индексы обычные, без PK/UNIQUE/FK и триггеров.

| Где | Поля и назначение |
| --- | --- |
| `paas_app_preparations` | `request_id, initial_name, app_id, namespace_name, namespace_uid, deleted_at`. До окончания подготовки UID отсутствует. Индексы по `request_id` и `app_id`. |
| `paas_apps` | Добавить `create_request_id, initial_name, migrator_revision, migrator_image`. Обычный индекс по `create_request_id`. Допускается сохранённая revision без настроенного образа. |
| `paas_components` | Добавить `create_request_id, initial_name, policy_revision, policy_snapshot BYTEA`. Индекс по `(app_id, create_request_id)`. Снимок содержит JSON полного `ComponentPolicy` из SDK. |

Идентификатор приложения выдаёт серверная подготовка, идентификатор компонента —
daemon. Подходит 128 случайных бит в нижнем hex; под блокировкой проверяются
коллизии, включая удалённые строки. Выданный ID не используется повторно.
В старых строках без ключа регистрации чтение каталога работает как прежде.
Для старой живой строки с пустыми полями настроек GET возвращает детерминированную
начальную revision, вычисленную по виду настройки и её ID с однозначным
кодированием полей. Первое изменение создаёт случайную новую revision.
Так две операции чтения до первой записи получают одинаковый ответ.

Начальная политика — `database_grants=[]`, `external={mode:"none",domains:[]}`,
`service_grants=[]`. Отсутствие конфигурации мигратора кодируется отсутствием
поля `migrator`. Частично заполненная пара полей компонента, повреждённый JSON,
чужой родитель или неоднозначная строка проверяются до выдачи ответа. Невалидная
хранимая запись даёт безопасный 500 и остаётся доступной для расследования.

## Семь обработчиков

| Маршрут | Поведение хранилища |
| --- | --- |
| `POST /apps/create` | Область ключа — регистрация приложения. Первая подтверждённая запись даёт 201, идентичный повтор — 200 с исходным ID и именем, другой payload — 409 `REQUEST_ID_CONFLICT`. |
| `POST /components/create` | Область — регистрация компонента внутри `app_id`. Для нового ключа требуется живое приложение; иначе 404. Успех и конфликт ключа такие же, как у приложения. |
| `GET /apps/migrator` | Снимок живого приложения, включая revision и опциональный образ. Неизвестное или удалённое приложение даёт 404. |
| `POST /apps/set-migrator` | После проверки `expected_revision` сохраняются digest-ссылка и новая revision. Несовпадение — 409 `POLICY_CHANGED`. |
| `POST /apps/remove-migrator` | Та же проверка версии. Удаляется настройка образа; БД, роли, Secret и данные приложения сохраняются. |
| `GET /components/policy` | Проверяются живые приложение и компонент именно этого приложения. Возвращается полный снимок. Чужая принадлежность и отсутствие цели дают 404. |
| `POST /components/set-policy` | Та же проверка принадлежности и атомарное сравнение revision. Невалидный DTO даёт 400, корректный `allowlist` — 409 `EGRESS_ALLOWLIST_UNAVAILABLE`. Предыдущий снимок и revision сохраняются. |

Семантику DTO проверяют существующие функции `paas-common/pkg/http/paas/validation`.
GET использует прежний read-only snapshot PostgreSQL. В записи полный DTO и
ссылки на целевые живые приложения и компоненты проверяются до COMMIT. Внешние
Service и будущие имена собственных Deployment проверяются по учёту ресурсов
при apply. До первого деплоя привязка остаётся намерением. После принятия
она относится к конкретному instance Deployment; удаление и повторное создание
под тем же именем не восстанавливают выданное разрешение. Будущий apply и writer
политик должны разделять проверку занятости и владения.

Предлагаем для одинакового значения с актуальной revision возвращать текущий
снимок без смены revision. Старая revision всегда даёт 409, в том числе после
потери ответа на успешную запись. Для регистрации предлагается сохранять ключ,
исходный payload и результат вместе с tombstone. Валидный повтор возвращает
исторический результат 200, не восстанавливая запись. Это правило действует
после ранее разрешённого доступа, включая повтор регистрации компонента при
удалённом родителе; свежая регистрация под удалённым родителем получает 404.
Оба пограничных правила подтверждены вместе с этапом.

## Конкуренция, права и сбои

Все writers этого профиля начинают короткую транзакцию PostgreSQL
`READ COMMITTED` и первым отдельным SQL-вызовом берут один фиксированный
`pg_advisory_xact_lock` регистрации/настроек. Следующий SQL-вызов получает
свежий снимок уже после блокировки. Под ней проверяются scope ключа, исходный
запрос, родитель, единственность ID и revision; проверка и запись коммитятся
вместе. Так защищён и первый INSERT при отсутствии строки. Тот же замок обязаны
использовать доверенный writer резерва и будущие writers удаления/владения.
Для одной ноды это предсказуемый предел пропускной способности. Таймаут
ожидания и отказ БД дают 503. При неизвестном результате COMMIT клиент повторяет
тот же ключ регистрации либо перечитывает настройку; новый ID по факту
потери ответа не создаётся.

Роль `paas_runtime` и её DSN сохраняют read-only права. Предлагается добавить
отдельную identity daemon для записи настроек, вторую DSN и малый pgxpool. Выдать
ей точечные SELECT/INSERT/UPDATE по нужным колонкам каталога и SELECT резервов;
DDL, DELETE, запись операций и изменение факта подготовки остаются запрещены.
Доверенная подготовка узла получает отдельную identity с правом записи резервов.
Её Secret доступен только административному исполнителю фиксированной операции.
Пароли отделены от journal и аргументов процессов. Выдача или отзыв бизнесовых
прав приложения не следует из наличия служебной writer identity.

Существующий `pgxtx.ReadSnapshot` подходит для чтения. Для записи требуется
явный COMMIT с сохранением причины ошибки и различением неизвестного исхода.
Перед реализацией сверить опубликованный `packages-go` с этими требованиями.
Универсальный transaction runner стоит выносить отдельно лишь при проверенном
общем контракте; отраслевые проверки, замок регистрации и отображение HTTP-ошибок
принадлежат PaaS.

## Переход с действующей однодовой установки

1. Подготовить совместимый reader, способный читать каталог и историю на v3 и
   v4. В v3 он не выдаёт готовность новых writers. Рабочий daemon обновляется
   отдельным pinned digest через Recreate; UID Namespace, каталог, старый
   migration Job и PVC сохраняются.
2. Доверенный установщик дополняет существующую БД и Secrets writer-ролями,
   проверяя прежние installation ID, UID тома и PostgreSQL system identifier.
   Отдельный `control-migrate-v4` получает новый предварительно импортированный
   digest и существующую DSN мигратора. Завершённый `control-migrate-v3`
   сохраняет прежний digest, UID и результат.
3. После проверки схемы и grants явно обновить Pod на v4-профиль с новой
   read-write DSN. Разрешить в установщике именно переход от известной
   прежней Pod template к согласованной новой, по UID и resourceVersion.
   В журнале сохранить исходный и целевой отпечатки для сверки после потери
   ответа. Автоматическое понижение схемы и попытки повторной инициализации
   PostgreSQL исключены. При неуспехе migration Job предыдущий reader
   продолжает работать на поддерживаемой схеме, включение writers откладывается.

## Приёмка

- Реальный PostgreSQL v3 → v4 с живыми и удалёнными строками и прежней историей.
  Повторный запуск миграции и installer сохраняет UID, данные и пароли.
  Проверить GET старых записей, одну устойчивую initial revision и отсутствие
  побочных эффектов чтения.
- Через generated client и UDS воспроизвести все семь маршрутов, типизированные
  статусы, чужую принадлежность, корректный отказ `allowlist`, повреждённые
  записи и восстановление доступа к БД после 503. Оператор не получает пароль
  в ответе или обычном журнале.
- Конкурентно запустить одинаковые регистрации, различные payload одного ключа
  и две записи по одной revision. Проверить единственный ID и фиксированный
  итог, один победивший CAS и снимок проигравшей стороны. Перезапустить daemon
  между COMMIT и доставкой ответа; повтор не создаёт другую сущность.
- На одной ноде проверить подготовку Namespace, отказ при чужом UID, сбой после
  создания Namespace, перезапуск миграционного Job, отдельное обновление образа
  daemon и сохранность старого каталога. От имени reader запретить запись,
  от имени settings writer — DDL и изменение чужих служебных таблиц, от имени
  daemon — изменение реестра доверенной подготовки.

### Одобрено 7 ноября 2026 — предел запроса настроек

Каждое из пяти тел POST settings ограничено в контракте одним MiB
(1 048 576 байт исходного JSON). При превышении daemon возвращает типизированный
HTTP 413 до декодирования и записи. Проверяется фактически прочитанное тело,
включая запросы без Content-Length. При сохранении и чтении политики действует
тот же предел для её JSON-представления. Приёмка охватывает границу, превышение
на байт, безопасный отказ и сохранение прежней ревизии.

### Проверка узлового helper

В изолированном PostgreSQL 18.6 четыре параллельных вызова подготовки с одним
ключом получили один ID. Повтор увидел сохранённый UID Namespace. Попытки
изменить имя или подставить другой UID завершились отказом. Проверка подключается
к PostgreSQL под `paas_namespace_preparer` с правами из установочного SQL.
Её запускает `sh scripts/testdata/postgres-control-sql.sh` из `paas-ctl`.

Тест `scripts/testdata/test-prepare-app.py` воспроизводит потерю ответа после
создания Namespace на имитации Kubernetes API и настоящем файловом журнале.
После повтора UID сохранился. При подмене Namespace, появлении посторонней
NetworkPolicy или RoleBinding подтверждение остановилось. На этом стенде
не проверяются применение Pod Security Admission и фильтрация сетевого трафика
ядром ноды. Обновление v3 → v4 и применение ограничений также проверены на работающей ноде. [Приёмка на k3s](settings-node-upgrade-2026-11-08.md).
