# Ручной Goose up и деплой с выбранной миграцией

**Контракт одобрен пользователем 7 ноября 2026 года.** Для задач 1.1, 2.3.3 и 5.1–5.3 предлагаются две команды оператора: запустить мигратор приложения и обновить компонент после явно выбранной миграции. На сегодня SDK умеет описать только автоматическую первую миграцию в плане компонента. Постоянная настройка `migrator.image` и revision уже описаны отдельным сервисом settings. Этот документ задаёт следующий контракт, исполнение которого ещё предстоит реализовать и проверить. [Деплои и миграции](../../openspec/changes/define-k3s-paas-foundation/specs/independent-deployments/spec.md) · [текущие DTO](../api/paas/types.yaml) · [профиль настроек](settings-storage-proposal.md).

## Действия оператора

| Действие | Цель и результат |
| --- | --- |
| Обычный деплой | Существующие `POST /deployments/preview` и `POST /deployments/apply`. Пакет относится к одному компоненту. В первоначальном деплое с мигратором план содержит INITIAL_MIGRATION, и компонент ждёт успеха Job. Последующий обычный деплой не запускает Job. |
| Миграция приложения | Оператор на экране приложения выбирает отдельный запуск Goose up, видит имя/ID приложения и закреплённый образ. После подтверждения создаётся операция приложения. Deployment, Service, ConfigMap и Ingress компонентов остаются прежними. |
| Деплой с миграцией | Оператор выбирает компонент, новый пакет и действие «Выполнить миграцию перед обновлением». Один preview и одно подтверждение связывают digest мигратора, действия над схемой и план компонента. Ошибка миграции останавливает обновление до публикации нового Deployment. |

Предлагается разрешать выбор установленного в settings образа по полному именованному digest SHA-256. Запрос содержит ожидаемую revision настройки; в preview daemon возвращает точный digest. Чтобы использовать другую версию, оператор отдельно меняет настройку с её собственной проверкой revision и повторяет preview. Это решение исключает скрытую смену образа по tag и незапланированное предоставление SQL-полномочий образу из Deployment YAML. Возможность разового выбора другого digest без изменения общей настройки требует отдельного решения владельца.

Предлагается допускать ручной запуск **после** подтверждённой первоначальной подготовки схемы приложения. До неё оператор проходит первоначальный деплой с обязательной миграцией. У приложения с уже подготовленной БД и удалённой настройкой мигратора данные и доступ сохраняются, запуск нового Job недоступен. Вариант с выбранной миграцией при первом деплое выполняет ровно один INITIAL_MIGRATION.

## Точный контракт HTTP

Все маршруты статические. JSON-команды принимают один объект, отклоняют неизвестные поля и `null` вместо optional-отсутствия. Для компактных команд предлагается предел 1 MiB на реально прочитанное тело; для пакета YAML остаётся согласованный предел 8 MiB на проводе и прежние ограничения парсера.

| Метод и путь | Запрос | Успех |
| --- | --- | --- |
| POST /migrations/preview | `{app_id, expected_migrator_revision}` | 200 MigrationPreview, только для отдельного запуска по приложению |
| POST /migrations/apply | `{preview_id}` | 202 OperationRecord при новом принятии, 200 прежний OperationRecord для повтора |
| POST /deployments/preview-with-migration | `{app_id, component_id, files[], expected_migrator_revision}` | 200 MigratingDeployPreview для атомарного принятия всего плана; files имеет исходную форму ManifestFile |
| POST /deployments/apply-with-migration | `{preview_id}` | 202 либо 200 OperationRecord с целью COMPONENT |
| GET /operations/inspect | Query `operation_id` | 200 OperationRecord для любой сохранённой цели |
| GET /operations/history | Query `state?, limit?, cursor?` | 200 `{items: OperationRecord[], next_cursor?}` для обеих целей |
| GET /operations/migration-log | Query `operation_id, after?, limit?` | 200 `{operation_id, items: MigrationLogEvent[], next_after?, truncated}` для операции, в плане которой есть миграция |

Успешный MigrationPreview содержит `preview_id`, `expires_at`, `diagnostics:[]` и `migration:{app_id, image, revision, reason:"MANUAL"}`. MigratingDeployPreview включает те же поля и `plan:{resources:ResourceChange[],additional_actions:AdditionalAction[]}`. В `migration.reason` стоит INITIAL либо REQUESTED; в `additional_actions` ровно один соответствующий `{app_id,kind:"INITIAL_MIGRATION"|"REQUESTED_MIGRATION"}`. В этих **новых** DTO одноимённое поле `additional_actions` получает собственный тип, поддерживающий оба значения; валидатор существующего PreviewResponse сохраняет свой закрытый набор. Миграция в плане всегда относится к тому же приложению. При ошибке в манифесте требуется только `diagnostics` с ERROR, без plan, migration, ID и срока. Для ручной команды ошибка JSON/ID/формата revision — 400, состояние приложения — отдельная ошибка ниже.

Пример запроса и ответа на отдельный preview. Хэш приведён как пример формата.

```json
{"app_id":"orders","expected_migrator_revision":"m4"}
```

```json
{"preview_id":"p17","expires_at":"2026-11-07T16:30:00Z","diagnostics":[],"migration":{"app_id":"orders","image":"ghcr.io/example/orders-db@sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","revision":"m4","reason":"MANUAL"}}
```

Общие ошибки передаются действующим ErrorResponse с non-null diagnostics. Неправильная форма даёт 400 INVALID_REQUEST, превышение полного тела — 413 BODY_TOO_LARGE, неизвестная цель или preview — 404 NOT_FOUND. Для зарегистрированного приложения без мигратора предлагаем 409 MIGRATOR_NOT_CONFIGURED, до первоначальной подготовки — 409 INITIAL_DEPLOYMENT_REQUIRED, несовпадение ожидаемой ревизии при создании preview — 409 POLICY_CHANGED. Истёкший сохранённый неиспользованный preview даёт 410 PREVIEW_EXPIRED, удалённый — 404. Недоступность обязательной зависимости даёт 503 DEPENDENCY_UNAVAILABLE. Квоты дают 503 PREVIEW_CAPACITY_EXCEEDED или ACTIVE_CAPACITY_EXCEEDED. Для нового apply к изменившемуся допустимому плану — 409 PLAN_CHANGED, для ставшего недопустимым — 409 RECHECK_FAILED. Ошибка после достоверного принятия возвращается через state/diagnostics операции.

Каждый preview получает сохранённый вид команды: обычный деплой, отдельная миграция или деплой с выбором миграции. Apply сначала ищет этот preview/его сохранённую связь **в области своего вида**. Попытка применить его другим из трёх маршрутов даёт 409 PREVIEW_KIND_MISMATCH, без новой операции и без исполнения. Поэтому старый клиент не может случайно запустить выбранную миграцию через обычный apply. Для правильного вида поиск уже принятой связи предшествует TTL и квотам. Переименование приложения не меняет его ID; содержимое снимка нельзя менять под тем же preview_id.

## OperationRecord и совместимость истории

OperationRecord сохраняет `operation_id, app_id, state, diagnostics[], created_at, updated_at` и условные `stage?, finished_at?`. Обязательный `target_type` имеет два значения: APP и COMPONENT. Для COMPONENT обязательно непустое `component_id`; для APP ключ `component_id` отсутствует. Для новых операций, действительно включающих миграцию, предлагается optional `migration:{image,revision,reason}` с подтверждённым digest и причиной MANUAL, INITIAL либо REQUESTED. Это служебная идентичность образа, координаты пользователя/БД/Secret и SQL в неё не входят. Остальные инварианты пяти state, timestamps и безопасных Diagnostic сохраняются. Пример записи ручной миграции:

```json
{"operation_id":"o17","target_type":"APP","app_id":"orders","state":"RUNNING","stage":"MIGRATE_DATABASE","diagnostics":[],"created_at":"2026-11-07T16:01:00Z","updated_at":"2026-11-07T16:01:02Z","migration":{"image":"ghcr.io/example/orders-db@sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","revision":"m4","reason":"MANUAL"}}
```

1. Добавить в новом Goose up признак цели. Существующая строка без признака читается как COMPONENT при валидном старом снимке. Сохраняются прежние ID, времена, диагностика и tombstones. История не зависит от живого каталога. Некорректный старый снимок даёт безопасный 500; пропуск строки исказил бы страницу.
2. Сначала развернуть reader, совместимый с текущей и новой схемами. Новые producers включаются только после миграции, проверки grants и наличия совместимого reader. Включение обычного мигратора бизнесовой БД не обновляет схему самого control plane.
3. Старые `GET /operations/get` и `/operations/list` продолжают выдавать прежний Operation для целей COMPONENT. В старом списке APP не занимает позицию или lookahead; lookup APP по старому endpoint возвращает 404. У новых компонентных записей старый клиент получает проекцию с прежними обязательными полями. Если старый клиент встречает ID блокирующей APP-операции, он может показать ID; её карточка доступна в новом inspect. Это ограничение совместимости требуется явно утвердить.
4. Новый history объединяет обе цели в одном порядке по прежнему opaque operation_id, с прежними правилами tombstones, фильтров и keyset pagination. У нового маршрута свой scope cursor; токен от старого списка на новом и наоборот — 400 INVALID_CURSOR. Limits 1–100, default 50, JSON страницы до 8 MiB, новая запись до 64 KiB с escaping. Одобрено исключение для старой валидной Operation до 65 536 байт: добавление обязательного target_type=COMPONENT расширяет её до 65 562 байт без потери данных. Только store знает происхождение снимка; потребитель валидирует старую проекцию и прежний предел. Размер и связи полей проверяются до начала отправки ответа.
5. Сохранённый Job даёт статус по UID/условиям и коду завершения. Для журнала предлагаем до 128 безопасных событий на операцию и 32 KiB совокупно, отсортированных по `seq` с 1. `MigrationLogEvent={seq,at,code,version?}`; `at` — UTC сервера, `version` — целое неотрицательное. Разрешённые коды первой версии — JOB_CREATED, JOB_STARTED, VERSION_APPLIED, NO_PENDING_MIGRATIONS, JOB_SUCCEEDED, JOB_FAILED, LOG_TRUNCATED. Сообщения о version/no-op принимаются только в ограниченной структурированной форме. При переполнении сохраняется терминальное событие и признак `truncated=true`. Клиент получает до 50 записей, default 20, `after` — последний виденный seq (0, если не передан). Для операции с миграцией до появления событий вернётся пустой массив, для операции без миграции — 404. События удаляются вместе с историей. Неизвестный stdout/stderr, SQL, DSN и произвольные тексты образа в API и обычные логи не попадают. Успех не определяется выводом программы.

## Исполнение, блокировки и права

Подтверждение атомарно занимает ёмкость узла, целевую бизнесовую БД и при комбинированном деплое компонент/маршруты. В одной транзакции PostgreSQL сохраняются связь с preview, неизменяемый input/internal plan, digest, версия настройки, целевая БД, намерение для Job и стабильное имя. Проверяются также ожидаемая исходная схема/факт первоначального запуска, владение, разрешения и все условия сравнения обычного плана. Только после COMMIT допустимы вызовы Kubernetes. При занятой БД любой из трёх способов запуска миграции получает 409 DATABASE_BUSY с реальным `conflicting_operation_id`; для занятого компонента — действующий COMPONENT_BUSY. Очереди нет. Первоначальный деплой другого компонента того же приложения не может обойти обязательную подготовку схемы. При неполном выводе результата COMMIT клиент повторяет **тот же apply с тем же preview_id**, а не создаёт новый preview. Сохраняются 503 ACCEPTANCE_UNKNOWN и единый ID операции.

| Вид | Этапы | Критерий успеха |
| --- | --- | --- |
| Ручной up | MIGRATE_DATABASE после фиксации намерения и прав | Достоверно подтверждён успешный исход исходного Job. Применение нуля новых миграций тоже считается успехом. Компоненты не переключаются. |
| Первый деплой | PREPARE_RESOURCES → INITIAL_MIGRATION → APPLY_RESOURCES → WAIT_READY | Job подтвердил подготовку схемы до запуска компонентов; Deployment/EndpointSlice достигли принятого профиля готовности. |
| Последующий деплой с миграцией | PREPARE_RESOURCES → MIGRATE_DATABASE → APPLY_RESOURCES → WAIT_READY | Выполняются обе части одного подтверждённого плана. Успех SQL и провал rollout фиксируются как частичный результат. Для последующего обычного деплоя этап миграции отсутствует. |

Для бизнесового Job предлагаем `restartPolicy: Never`, `backoffLimit: 0` и `activeDeadlineSeconds: 1800`. Это предложенный, ещё не измеренный предел 30 минут только для конкретного запуска мигратора. Согласованные 10 минут ожидания rollout начинаются отдельно. Таймаут HTTP или закрытие TUI не убивает принятый Job. При рестарте daemon проверяет имя, owner и UID, сверяет фактическое выполнение и результат. Если ответ create потерян, допустимо найти тот же Job по намерению; существующий завершившийся Job не заменяется новым. При несовпадении UID, неизвестном исходе SQL либо возможности продолжающейся транзакции остаются RECOVERY_REQUIRED и необходимые резервы. FAILED допустим при известном безопасном завершении, OUTCOME_KNOWN_PARTIAL фиксирует известные изменения; один лишь exit code не доказывает отсутствие выполненного SQL. Оператор проверяет причину и явно создаёт новую попытку. Автоматические down, redo и повтор up после ошибки не входят в согласованный сценарий.

Блокировка control plane привязывает занятую БД к операции. Внутри Job нужен независимый session lock Goose на выделенной бизнесовой БД на всё применение up. Исполнителя нельзя выпускать до реальной проверки на двух процессах и потере соединения: занятая БД отказывается принимать вторую миграцию, а неоднозначное завершение сохраняет резерв исполнения. Шаблон использует закреплённый Goose как библиотеку и SQL из образа.

У администратора TUI одна доверенная роль через SSH/UDS. Job получает только собственную роль мигратора и Secret своего приложения, в подготовленном Namespace, с отдельным ServiceAccount, без API-токена и метки instance пользовательского Deployment. NetworkPolicy допускает только кластерный DNS и целевой PostgreSQL. Обычный Pod не может запустить такой Job или смонтировать его Secret. Профиль считывания GHCR на ноде не выдаёт токен мигратору. Для записи операций потребуются отдельные минимальные grants в control plane: существующие reader и settings writer не получают DDL, права выдачи Namespace или доступа к бизнесовым credentials.

Предварительные снимки используют общие TTL 30 минут и квоту 64 записи / 256 MiB. Активные ACCEPTED/RUNNING/RECOVERY_REQUIRED обоих видов входят в единый предел четырёх операций / 256 MiB исходных снимков, с принятым резервом публичного состояния. Повтор уже принятого apply при заполненной квоте возвращает прежнюю запись. Терминальная история живёт 30 дней от finished_at; ownership, факт первоначальной подготовки, действующие маршруты и SQL-история Goose живут независимо. TLS продолжает иметь собственную внешнюю проверку.

## Приёмка решения

- Старый сгенерированный клиент читает прежнюю и новую компонентные записи, продолжает страницу по старому cursor и получает предсказуемый 404 при lookup APP. Новый клиент видит обе цели без пустого component_id. Проверить переход со старой схемы с tombstones и сохранёнными диагностическими именами до 512 байт.
- Запустить отдельный up, начальный деплой и комбинированный деплой конкурентно по одной БД. Проверить единственного владельца резерва, один Job на один принятый preview и пригодный ID в каждом ответе 409. Независимая БД на другой цели может использовать свободный слот.
- Потерять ответ после COMMIT, перезапустить daemon после отправки create Job и повторить apply. Проверить прежние ID, UID, digest, число запусков up и фактические изменения схемы. Подменить Job одноимённым чужим объектом: сверка не должна принять его за своё исполнение.
- Между preview и apply сменить revision/digest, отозвать необходимый доступ и занять целевые маршруты. Убедиться, что новый незапланированный Job/Deployment не создан. Проверить неправильный вид apply, 1 MiB / 8 MiB, TTL и квоту, включая незавершённый RECOVERY_REQUIRED.
- На реальной PostgreSQL и k3s проверить no-op up, успешную новую миграцию, сбой SQL до и после частичных изменений и зависший Job. При неуспешной первоначальной миграции новый workload не запускался; при неудаче после успешного up сохранены факт применения SQL и наблюдаемая версия Deployment, включая частичное обновление. Secret/SQL-canary отсутствуют в API и доступном журнале.
- Обновить компонент обычным путём без миграции и с явным выбором миграции. Подтвердить, что второй сценарий запускает Job перед rollout и не меняет версии соседних компонентов, а ручной up не создаёт новый ReplicaSet.

**Владелец одобрил** два новых вида preview с отдельными apply; ограничение ручного запуска подготовленной схемой и выбранным в settings digest; OperationRecord с двумя совместимыми представлениями истории; ограниченный журнал и 30-минутный deadline. Эта форма включена в активную delta OpenSpec и служит основанием для SDK. Действующая схема v4 хранилища настроек, API деплоя, Kubernetes-права и исполняющий worker этим предложением не изменяются.
