# Сеть обычного компонента в однодовой v1, этап 5.5

**Реализация одобрена владельцем 8 ноября для выделенного стенда.** Оператор уже может сохранить `service_grants` и `external.mode` через GET `/components/policy` и POST `/components/set-policy`. Ревизия ответа подтверждает сохранение желаемой политики. Этап 5.5 связывает её с фактическими Pod и трафиком. Требования заданы в [дельте shared-infrastructure](../../openspec/changes/define-k3s-paas-foundation/specs/shared-infrastructure/spec.md#requirement-сетевые-связи-приложений-разрешаются-явно) и [согласованном профиле манифестов](manifest-policy-proposal-2026-11-07.md#сеть-до-реализации-paas-012).

## Какие правила нужны

| Поток | Кто разрешает | Область допуска |
| --- | --- | --- |
| Обычный Pod → обычный Pod того же приложения | Платформа при подготовке Namespace | Оба направления между Pod своего Namespace с защищёнными идентификаторами обычного workload. Тот же класс Pod получает DNS к назначенному кластерному resolver по UDP/TCP 53. Default-deny остаётся основой. |
| Компонент A → обычный Service B другого приложения | Оператор A выдаёт grant в политике **компонента** A | Две NetworkPolicy. У источника egress, у назначения ingress. С обеих сторон проверены Namespace UID. Источник ограничен точными app/component и действующим instance. Назначение ограничено экземпляром workload за Service и подтверждёнными протоколами и targetPort. Ответ проходит, обратный вызов требует отдельного grant. |
| Приложение → общий Service | Владелец общего Service по уже согласованному 5.4 | Исключительное полномочие владельца. На объявленный shared Service обычный grant не создаёт пару политик. Проверять также совпадение конечных Pod и портов у другого Service: алиас с тем же назначением может обойти запрет. Перед регистрацией shared сверить уже действующие обычные grants и блокировать регистрацию при пересечении до их снятия. Последующие изменения selector/портов проходят ту же проверку. |
| Компонент → интернет | Его `external.mode` | В `none` разрешены только согласованные исключения. В `all` добавляется внешний egress только этого компонента. В `allowlist` действует согласованный 409 с сохранением прежней ревизии и режима. |

Для workload с правом APPLICATION доступ к БД определяется отдельной защищённой меткой. Для Job мигратора сохраняются DNS и целевой PostgreSQL. Штатный вход Traefik проверяется отдельно. Сетевые правила выбирают Pod целиком. Для L3/L4 два Service, ведущие на те же Pod и тот же порт, дают один и тот же достижимый endpoint, включая обращение по Pod IP.

## Как применять и восстанавливать

1. Для явной связи использовать сохранённую политику, ownership источника и цели и запись подготовки Namespace. Сегодня `checkServiceTargets` проверяет приложения и компоненты. Дополнительно закрепить Service UID и целевой instance при выдаче grant на существующий управляемый Service. Чужой или отсутствующий Service отклонить. Пересоздание цели под тем же именем требует явного снятия и повторной выдачи. До первого запуска источника grant остаётся желаемым. При rollout сверять фактический instance источника и исключать устаревшие селекторы.
2. Использовать уже работающие проверки `SharedPolicies` для Service, EndpointSlice, Pod UID, именованного targetPort и протокола. Переиспользовать запись intent перед созданием, пустую исходную NetworkPolicy, защищённый маркер, UID/resourceVersion, новый маркер ревизии при отзыве и сверку после записи. Передавать в построение пары точный selector источника: `SharedConsumerSelector` выбирает **все** обычные компоненты приложения и подходит только для полномочия 5.4. Подробности восстановления уже согласованы в [проекте 5.4](network-recovery-proposal.md).
3. Settings writer меняет только желаемое состояние. Исполнитель сериализует сверку и публикацию ревизии в control DB, использует действующие права наблюдения ресурсов и записи политик в подготовленных Namespace. Узловой installer проверяет RBAC, default-deny, защищённые метки и принадлежность всех разрешающих правил. Для работы daemon не выдаются hostNetwork, права администратора узла или cluster-wide запись. Разделить запись SQL желаемой политики, фактических UID и результата сверки между действующими ролями settings и operations.
4. На потерю Namespace/Service UID, подмену EndpointSlice, конфликт порта, неизвестную разрешающую политику или смену ревизии реагировать повторной сверкой. Снять ранее открытые правила на каждой доступной своей стороне по подтверждённому UID. Не усыновлять и не исправлять чужие объекты. При неясном результате сохранять intent и состояние BLOCKED, включая рестарт. Пустая собственная политика не перекрывает чужую разрешающую политику. Изменения Service, публикация shared и изменение ordinary grant требуют общего порядка блокировок и установки ограничений **до** расширения доступности endpoint. Периодическая сверка обнаруживает внешнее расхождение с задержкой. Гарантия опирается на единственного доверенного писателя в управляемые ресурсы.
5. Изменения settings распространяются и на работающие Pod без нового deploy. Перед первым запуском установить и проверить базовую изоляцию и требуемые правила источника. Отдельный endpoint для сетевых операций не требуется. Предлагается добавить в ответ существующего GET политики необязательный блок с желаемой и подтверждённой ревизиями, состоянием PENDING/APPLIED/BLOCKED и безопасной причиной. Он нужен, чтобы после рестарта и при частичном отзыве TUI не показывал сохранённый режим как действующий. APPLIED означает сверку ресурсов на поддерживаемом проверенном профиле узла. Внешний тестовый сервер не требуется при каждом изменении настроек.

## Когда узел допускает all

Installer должен определить сетевой профиль из фактической конфигурации k3s: CNI и исполнитель NetworkPolicy, IP-семейства, Pod/Service CIDR, адреса интерфейсов, локальных сетей, API, узловых сервисов и шлюзов. Для внешнего egress из диапазона каждого поддерживаемого семейства исключить внутренние и специальные сети, включая link-local/metadata, частные диапазоны, ULA, loopback, multicast, все реальные внутренние маршруты, публичные адреса узла и инфраструктуры. Специальные маршруты к DNS, БД и Service добавлять только по своим полномочиям. Если ingress платформы опубликован через внешний адрес, включить его в проверку обхода. Поддерживаемые служебные входы со стороны Traefik не дают исходящего допуска к нему.

Обычная NetworkPolicy не гарантирует блокировку соединений с собственным узлом. Порядок DNAT и применения IP-фильтра зависит от dataplane. Для выдачи `all` узел должен уже иметь проверенное ограничение на границе Pod/host, сохраняющееся после перезагрузки. Его наличие и конфигурацию сверяет доверенный installer. Пока гарантия не установлена, не открывать `all`; согласовать причину отказа с оператором. Новые host firewall rules или замена CNI потребуют отдельного архитектурного решения. При смене сетевого профиля инвалидировать подтверждение, снять собственные расширяющие правила и заблокировать новые запуски до повторной проверки. При недоступности Kubernetes показывать непроверенное состояние. [Семантика NetworkPolicy и ограничения Kubernetes](https://kubernetes.io/docs/concepts/services-networking/network-policies/)

## Приёмка на одноразовых целях

| Проверка на фактическом k3s | Что зафиксировать |
| --- | --- |
| Два приложения, по два обычных компонента, мигратор и общий Service | До grant связь внутри приложения работает, между приложениями закрыта. После grant A1 → B1 проходит запрос и ответ через ClusterIP и разрешённый Pod IP/порт. Новые соединения A2 → B1, B1 → A1, A1 → другой порт и к непредоставленному shared endpoint отклоняются. Проверить alias Service, именованный targetPort, UDP и TCP. |
| Работающий workload, режимы none → all → none | Из source Pod проверить управляемые внешние слушатели по имени и по IP, включая TCP 25/443 и UDP. Положительный контроль из разрешённого источника подтверждает доступность каждого слушателя. В all сохранить отказ доступа к API через Service IP/DNS и адрес узла, к kubelet, NodePort, платформенным Pod и Service, link-local/metadata и внутренним маршрутам. Проверить все включённые IP-семейства. Для IPv6 без маршрута записать этот факт. Проверить DNS обычного workload и мигратора и запрет мигратору всех остальных целей, кроме целевой БД. Отдельно повторить вход через Traefik. |
| Отзыв, drift, рестарт после первого из двух write | Записать policy revision, UID объектов и результаты свежих подключений до и после отзыва. Долгоживущий TCP проверить отдельно. После подмены Service и Namespace старая запись не открывает новый объект. Повтор после рестарта восстанавливает собственные intent. Посторонняя additive policy даёт BLOCKED до устранения. После перезагрузки узла заново проверить ограничения Pod/host. |

**Одобрены** закрепление цели по UID и отказ пересекающимся обычным/shared путям, дополнение существующего GET наблюдаемым статусом и условие активации `all` на проверенном узле. Проверки 5.4 на v5-fresh подтверждают работу общей пары политик для разрешённого приложения. Режимы обычных компонентов и способность этого узла изолировать host в `all` требуют собственной приёмки.
