# Приёмка установки k3s через paas-ctl, 7 ноября 2026

На свежей Debian 13 arm64 с собственным ядром (Apple Virtualization.framework)
контрольный запуск `paas-ctl node prepare` установил профиль через независимого
SSH-администратора. Затем `node install` под пользователем `paas` установил
k3s `v1.37.2+k3s1`. Локальный API ответил `ok`, нода стала Ready, проверка
шифрования Secrets вернула Enabled. Тестовый кластер и ключи были выделены
для этой приёмки. Во время подготовки использованы утилиты из Debian 13.

| Сценарий | Наблюдение |
| --- | --- |
| Целостность загрузки | Профиль с заведомо другим SHA-256 дал `download checksum mismatch`. Бинарник и unit отсутствовали. После явного исправления тестового профиля скачан бинарник с закреплённой суммой. |
| Чужая установка | Посторонний файл на месте бинарника и остаточный каталог не были заменены. Остановленная существующая служба осталась остановленной после вызова ctl. |
| Полномочия | Запуск произвольного sudo и передача дополнительного аргумента к разрешённому helper отклонены. У `paas` отсутствует доступ на запись к helper и профилю, а также доступ на чтение к административному kubeconfig. |
| Повтор и принятие существующей ноды | UID ноды, UID контрольного ConfigMap, SHA-256 серверного CA и systemd InvocationID совпали после повтора и после проверки уже работающего кластера без маркера установщика. |
| Мультинод | Вторая Debian VM зарегистрировала настоящий kubelet. Оба узла с разными boot ID были Ready. Команда `node install` вернула код 1 и `expected exactly one node`. Оба UID, оба состояния и InvocationID сервера сохранились. После отказа worker обновил настоящий NodeLease. Временный worker и его туннели удалены, единственная нода снова проходит проверку. |
| Привязка к серверу | В приватном mount namespace подмена machine-id при одной Ready-ноде воспроизвела ошибочный успех старой проверки. Новый helper сверяет `status.nodeInfo.machineID` с локальным `/etc/machine-id` в том же снимке списка. Отказ и обычный успешный вход проверены на VM, включая зашифрованный SSH-ключ. |
| Частичная установка | Debian-фикстура проверяет отказ при чужом drop-in, конфигурации или изменяемом бинарнике, защиту существующего sudoers и повтор после неизвестного результата запуска. Отсутствие `/dev/kmsg` сначала воспроизведено на OrbStack с аварией kubelet, затем перенесено в проверку до изменения новой ноды. |
| CLI и качество | Команды на Cobra 1.10.2 используют flagx из существующего packages-go. Проверены справка и прежние способы задания флагов `status`. Для ctl прошли build, test, race, vet, tidy-diff, fmt, lint и linux/amd64 build. На VM исполнялся linux/arm64 бинарник. ShellCheck проверил предупреждения и ошибки сценариев. |

Вариант запуска из каталога `paas-ctl` описан в разделе «Установка k3s на одну ноду» файла `paas-ctl/README.md`.
Нужны одноразовая VM, Linux-бинарник и каталог `scripts/`. Команда
`sudo sh scripts/test-k3s-node.sh --disposable-vm /путь/к/paas-ctl` запускает
полный однонодовый сценарий. Она добавляет также тестовый объект Node для
проверки отказа. Отдельный прогон с двумя настоящими kubelet приведён в таблице.

Этап 3.1 закрывает установку и повторную проверку k3s. Установка общего
PostgreSQL, размещение Pod daemon и проверка приложений учитываются отдельно.
