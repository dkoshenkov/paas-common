# Приёмка регистрации общего Service на схеме v9

Выделенный однодовый стенд v5-fresh начал проверку на схеме v8. PostgreSQL был готов, прежний Job v8 завершён, прикладных workloads до теста не было. В `k8s.io` containerd импортированы отдельный миграционный образ (`sha256:e2fe448e2f0921e6f65c2db90edd8f6f95b1907b8f0457d30a15847567a0e010`) и совместимый daemon для чтения (`sha256:9d3f4ffec11563eab8a434d0f604c8538e9cfed6a1c7688a3308e0674a6b6970`). Первоначальный импорт в namespace containerd по умолчанию не сделал образ доступным Kubernetes. Мастер остановился до миграции. После импорта в k8s.io обе полные ссылки проверены через CRI.

В мастере ctl профиль `k` обновил ноду с v8 до v9. Job `control-migrate-v9` с UID `c6898d49-fa21-48bc-aa62-58b0aac69dbb` завершился, Job v8 сохранился. Повтор того же профиля сохранил UID Job v9 и Pod daemon `427b6dcb-23cc-4eb4-bd0c-2e4de70b0beb`. Счётчик рестартов daemon оставался равен нулю, UDS `/ready` ответил 200.

[Скрипт проверки API](../../../paas-ctl/scripts/testdata/shared-api-smoke.py) подготовил два приложения, зарегистрировал компонент и развернул в нём Deployment и ClusterIP Service штатными preview и apply. Операция дошла до SUCCEEDED. Получены UID Namespace `65cb237d-d41e-4772-854c-e422a5487223`, Service `7b7d8f8f-677d-404d-b7f8-25fffc90aa60` и Deployment `d7dd862e-36e5-47f3-bc29-dccce0c287e5`. В EndpointSlice `020109ba-2d9f-45c2-9d81-2aa8bdd8e8ed` endpoint готов.

| Действие оператора | Результат |
| --- | --- |
| Регистрация отсутствующего Service | HTTP 404 |
| Регистрация существующего Service | HTTP 201 и начальная revision |
| Повтор исходного request_id | HTTP 200 и та же регистрация |
| Новый request_id для уже зарегистрированного имени и UID | HTTP 409 |
| Запрос допуска с текущей revision | Сохранено desired allow с новой revision; в списке потребителя адрес отсутствовал |
| Изменение со старой revision | HTTP 409, в том числе после отзыва |
| Отзыв с текущей revision | Сохранено desired deny; список потребителя по-прежнему пуст |

SQL-проверки выполнены в том числе под ограниченной ролью записи; для двух таблиц v9 установщик выдаёт SELECT и ограниченные колоночные INSERT/UPDATE. Проверены отказ DELETE, DDL и запрещённых изменений идентичности. Отдельная проверка PostgreSQL устанавливает права v9, отзывает нужное разрешение и проверяет, что readiness перестаёт подтверждать готовность. На v8 эта проверка прав v9 не требуется.

Для завершения 5.4 требуются исполнение и проверка ingress/egress NetworkPolicy, реальные соединения двух разрешённых потребителей и отказ третьему, отзыв и независимое обновление сервиса. Подтверждённый адрес в ходе этой проверки не создавался. При пересоздании Service под тем же именем текущая v9 обнаруживает смену UID; новая регистрация и снятие старых разрешений описаны в [предложении по восстановлению](network-recovery-proposal.md#повторная-регистрация-после-замены-service).

## Старт daemon при выключенном PostgreSQL

При первоначальном включении ноды прежний daemon трижды завершился до готовности БД. До исправления процесс обращался к очереди операций PostgreSQL прежде, чем начинал слушать Unix-сокет. После исправления временная недоступность хранилища отражается в readiness; worker продолжает опрашивать БД.

[Контрольный сценарий](../../../paas-ctl/scripts/testdata/daemon-cold-start-smoke.py) сохранил исходное число реплик PostgreSQL (одна), остановил его и заменил Pod daemon. Новый Pod `20c5e53d-df00-43a5-813c-057b14a262a7` при выключенной БД вернул через UDS health 200 и ready 503. После восстановления PostgreSQL до одной реплики тот же Pod дал ready 200, счётчик рестартов сохранился равным нулю. Списки приложений, операций и общих сервисов совпали со снимками до остановки.

## Первые проверки сетевого допуска на v10

На выделенной ноде мастер выполнил переход с v9 на v10. Для отдельного компонента развернули HTTP-сервис, который отвечает строкой версии, и создали три потребителя в разных Namespace. Владелец проверил ответ v1 на loopback. После явного допуска первых двух потребителей статус обеих пар дошёл до APPLIED. Каждый открыл новые HTTP-соединения к ClusterIP и по выданному имени Service через числовой порт 8080 → 8081 и порт 8082 с именованным targetPort http. Ответ в каждом случае — v1. Третий потребитель без допуска получил отказ при попытках установить соединения к обоим портам ClusterIP.

В ходе проверки также обнаружен отказ preview при обновлении ранее развёрнутого Deployment: Kubernetes добавил protocol TCP в описание containerPort, а алгоритм трёхстороннего слияния расценил его как стороннее изменение при замене порта. Этот случай проверяется отдельно от допуска к новому сервису.

У нового владельца `3bd1076179f941829a37a81f9dc6a105` и компонента `a622ad8f42dc30d291bc60bd38d1a621` тестовый Service имел UID `f564285a-25c3-4e67-9b16-59d568ad7488`. После смены версии приложения владельца потребители прочитали v2. UID Deployment потребителей сохранились. После отзыва ранее разрешённый потребитель больше не мог установить новое соединение. До проверки обратного направления процесс в Pod потребителя ответил v1 на loopback; попытка владельца инициировать соединение с этим Pod была отклонена.

Во время ещё одного запроса allow статус был PENDING с новой desired revision и предыдущим подтверждённым deny. До завершения тест сменил Pod daemon, новый экземпляр довёл ту же ревизию до APPLIED. Запрос потребителя получил v2. Повтор административной подготовки Namespace владельца и потребителя с исходным request_id сохранил их UID. Третий потребитель по-прежнему не имел доступа. [Сценарий реальных соединений](../../../paas-ctl/scripts/testdata/shared-network-live.py).

Для ранее зарегистрированного владельца отдельный preview/apply одного Deployment после исправления обработки стандартного TCP прошёл до SUCCEEDED. Прежний UID Service сохранился. На схеме v11 preview полного пакета показал UPDATE Service и NO_CHANGE Deployment; apply завершился SUCCEEDED. UID обоих объектов и ClusterIP Service сохранились при изменении портов. На финальном reader v11 отдельный одноразовый Service зарегистрировали и допустили потребителя: статус APPLIED, новый TCP-запрос вернул v1. После пересоздания Service его UID изменился с `dcb4c4ef-cf74-4347-a1a3-31c799801469` на `12390477-6ade-4632-a308-0783a5796127`, ClusterIP сохранился. Статус пары перешёл в BLOCKED с причиной `IDENTITY_MISMATCH`; пять новых TCP-подключений потребителя были отклонены, локальная проверка владельца вернула v1. Повторная регистрация после подмены ownership проверена отдельно на PostgreSQL. Отдельно на reader с исправлением обработки потери Namespace создали одноразового владельца и потребителя. После APPLIED потребитель получил v1 по TCP; затем удалили только его Namespace с UID `e3c972c8-c306-456d-a608-da3d595d0b06`. Статус пары стал BLOCKED (`UNPROVEN_POLICY`), ingress NetworkPolicy владельца сохранила UID `677bd8b9-c9db-45c3-b2d4-33ff865078ab` и получила пустой список разрешений; локальная проверка владельца вернула v1. Подмена UID и исчезновение каждой стороны также проверены на fake Kubernetes client и PostgreSQL. Для grant новой пары revision прочитали SELECT из control DB: общий список вернул 503 из-за ранее намеренно заменённого Service; текущая реализация проверяет идентичность каждого объекта в запрошенной странице списка.

На той же ноде разрешённый потребитель `bf2a63cd57694384881df57502ff5897` получил `connection refused` при новой попытке TCP к ClusterIP PostgreSQL на порту 5432; `pg_isready` внутри Pod PostgreSQL одновременно подтвердил готовность. На независимой одноразовой паре TCP-соединение установили до отзыва и после APPLIED deny отправили повторный HTTP-запрос по тому же сокету: он вернул v1. Новая попытка TCP была отклонена с `connection refused`. Это наблюдение данного стенда, а не гарантия сохранения установленных соединений. На повторно запущенной ноде read-only [PTY-сценарий](../../../paas-ctl/scripts/testdata/shared-tui-readonly.py) открыл приложение, затем через g → s показал сохранённые пары APPLIED и BLOCKED. Запрошенные и подтверждённые ревизии совпали с прямым API; для BLOCKED отображалась текущая причина `UNPROVEN_POLICY`. При первой проверке строка списка обрезалась при ширине 140 и DNS не был виден. После исправления экран выводит ID, владельца, компонент, revision и DNS отдельными строками. Повторный read-only PTY на ширине 100 показал полный DNS и revision для допущенного потребителя, а также оба статуса и их ревизии. Общий List API при этом возвращал 503 для страницы с намеренно заменённым Service UID.
