# Backlog PaaS

## PAAS-019 — Автоматическое восстановление узла и гибкое делегирование операций

- Статус: варианты будущего улучшения; вне первого объёма по решению пользователя.
- Первый профиль: фиксированные привилегированные операции PaaS, без произвольного
  shell/административного kubectl; восстановление registry-файла и применение
  выполняются двумя явными действиями без автоматического рестарта/отката.
- Кандидаты: автоматизация восстановления после подтверждённых сбоев и более
  гибкое делегирование ограниченных административных операций.
- Работа: отдельно согласовать необходимость, допустимые причины/границы
  восстановления, ограничение повторов, журналирование и права. Сверить с
  будущими ролями PAAS-013, без второго независимого механизма полномочий.
- Приёмка выбранного расширения: невозможно выполнить произвольную команду
  или расширить права daemon; автоматические действия ограничены, наблюдаемы
  и не образуют бесконечный цикл рестартов/откатов.
- Архитектура и реализация согласовываются отдельно; универсальный root executor
  и recovery framework заранее не создаются.

## PAAS-018 — Расширенные операции и политики запуска миграций

- Статус: варианты будущего улучшения по запросу пользователя; вне первого объёма.
- Первый профиль: только up; при занятой БД новый запуск отклоняется со ссылкой
  на текущую операцию; после ошибки повтор выполняет оператор явно.
- Кандидаты для отдельного согласования: управляемые обратные миграции и операции
  down/redo/reset с разными уровнями риска; очередь запусков для одной БД;
  ограниченные политики повторов после подтверждённо безопасных сбоев.
- Работа: определить необходимость каждого кандидата, права/подтверждения,
  совместимость схемы с приложением, отмену очереди и защиту от выполнения
  устаревшего образа, допустимые причины/лимиты повторов и частично применённый SQL.
- Приёмка выбранного расширения: нет параллельного изменения схемы; повтор
  не дублирует небезопасные побочные эффекты; отмена и состояние операций видны;
  разрушительное действие не маскируется под обычный up.
- Эти кандидаты не разрешают автоматический откат данных и не заменяют backup.
  Не создавать очередь, общий scheduler или retry framework заранее.
- Архитектура и реализация каждого выбранного улучшения согласовываются отдельно;
  наличие в backlog не делает все кандидаты обязательными.

## PAAS-017 — Сбор метрик и дашборды как код

- Статус: будущее развитие по запросу пользователя; вне текущего первого объёма.
- Цель: пользователь описывает сбор метрик и собирает дашборды кодом;
  определения версионируются в Git и воспроизводимо применяются через PaaS.
- Работа: согласовать формат описаний источников/правил сбора, запросов, панелей
  и компоновки дашборда, проверку перед применением и поведение обновлений.
  Значения credentials не помещать в код, использовать ссылки на разрешённые секреты.
- Выбор системы сбора/хранения/отображения метрик, языка или DSL и способа применения
  требует отдельного согласования; конкретный стек сейчас не выбран.
- Приёмка: из сохранённого описания воспроизводятся сбор метрик и дашборд;
  повторное применение не создаёт дубликатов, изменение кода обновляет нужные
  панели/настройки, некорректное описание получает диагностику до применения.
- Связь с PAAS-002: использовать согласованные источники и атрибуцию приложений,
  не создавать второй независимый стек мониторинга ради описания как код.
- Архитектура и реализация требуют отдельного согласования; новые зависимости,
  формат конфигурации и универсальный конструктор заранее не создаются.

## PAAS-016 — Пользовательские секреты и отображение необходимых перезапусков

- Статус: отложено пользователем ради минимального первого объёма разработки.
- Цель: вводить через CLI/TUI произвольные секреты приложения, например SMTP-пароль
  или токен внешнего API, хранить значения вне Git и выдавать выбранным контейнерам.
- При изменении секрета показывать затронутые компоненты и необходимость перезапуска;
  перезапуск выполняется явным действием оператора, без автоматического запуска.
- Для отображения использовать выбранный Bubble Tea и при необходимости Bubbles/
  Lip Gloss; отдельную библиотеку визуализации заранее не добавлять.
- Работа: согласовать операции создания/обновления/удаления, ссылки и зависимости
  потребителей. Не смешивать с ротацией паролей PostgreSQL или заменой GHCR-токена.
- Приёмка: значение не попадает в Git/обычные логи, выдаётся только выбранным
  контейнерам; после изменения видны затронутые компоненты и требуемый перезапуск;
  обновление секрета само по себе не перезапускает приложение.
- Пока задача отложена, универсальный API/экраны пользовательских секретов и
  отслеживание их обновлений не входят в текущий этап. Архитектура и реализация
  требуют отдельного согласования.

## PAAS-011 — Усиление хранения registry credentials и обработки в памяти

- Статус: обязательное будущее усиление по решению пользователя; вне первой версии.
- Первая версия хранит registry credentials в root-only конфигурации узла без
  прикладного шифрования файла. Это не заявляется защитой от root или чтения диска.
- Цель: согласовать и реализовать более безопасное хранение credentials, включая
  шифрование сохранённых данных и резервных копий, жизненный цикл ключей,
  восстановление после перезагрузки и минимизацию открытых копий в памяти.
- Работа: выбрать механизм по модели угроз, определить доступ доверенного runtime
  к credentials, ротацию/отзыв, резервное копирование и поведение при потере ключа.
  Шифрование с ключом в том же доступном месте не считать достаточной защитой.
- Учесть `runtime/secret` для временной обработки на поддерживаемых Linux-целях:
  пакет экспериментальный, требует GOEXPERIMENT=runtimesecret и не шифрует хранение.
  Проверить доступность и ограничения выбранного Go toolchain; на неподдерживаемых
  платформах не заявлять его защиту. Исключить утечки через логи и временные файлы.
- Приёмка: сохранённые credentials и их резервные копии защищены выбранным механизмом;
  проверены восстановление, ротация и потеря ключа; токен не раскрывается daemon;
  ограничения защиты памяти и доверие root документированы и проверяемы.
- Связь с PAAS-010: перед реализацией сверить объём. Если её итоговый механизм
  уже выполняет все критерии PAAS-011, закрыть эту задачу по тем же подтверждённым
  результатам без второго механизма. Сам переход на imagePullSecrets не закрывает
  шифрование хранения автоматически.
- Архитектура и реализация требуют отдельного согласования; криптографические
  компоненты первой версии ради этой задачи заранее не создаются.

## PAAS-010 — Независимая выдача GHCR credentials через imagePullSecrets

- Статус: обязательное будущее развитие по решению пользователя; вне первой версии.
- Первая версия использует registry credentials на уровне узла для container runtime,
  без Kubernetes imagePullSecret с GHCR-токеном.
- Цель: перейти на imagePullSecrets с отдельным доверенным получателем credentials,
  сохранив недоступность открытого GHCR-токена для daemon, включая косвенное
  извлечение через создаваемый им workload.
- Работа: согласовать конечного получателя и его аутентификацию, сквозное шифрование
  из CLI, хранение/ротацию/восстановление ключей, независимые ограничения Kubernetes
  на чтение, изменение и монтирование registry Secrets. Daemon не должен иметь
  возможности отключить эти ограничения или получить токен через другой канал.
- Разрешения на скачивание и привязки registry credentials к workloads учитывать
  отдельно от доступа контейнеров к credentials БД.
- Защиту хранения и обработки в памяти сверить с PAAS-011; общие работы не дублировать.
- Переход: описать перенос с конфигурации узла, замену и отзыв старого токена,
  восстановление после сбоя и проверку отсутствия обхода через старую конфигурацию.
- Приёмка: разрешённый workload скачивает приватный образ GHCR; токен не появляется
  в daemon, его логах и состоянии; попытки прямого чтения и косвенного получения
  через env/volumes/изменение workloads отклоняются независимыми ограничениями.
- Зависимость: `define-k3s-paas-foundation`, `application-secrets`.
- Архитектура и реализация требуют отдельного согласования; заранее создавать
  универсальный интерфейс или второй механизм в коде первой версии не требуется.

## PAAS-001 — Окружения приложения

Статус: отложено пользователем; вне первой версии.

Цель: поддержать независимые окружения одного приложения, например `dev` и `prod`.

Предложение для будущего OpenSpec change:

- Деплой относится к паре «приложение + окружение».
- Каждое окружение получает отдельную базу PostgreSQL, пользователя приложения,
  пользователя мигратора и Kubernetes Secrets.
- Например: база `orders_dev`, роли `orders_dev` и `orders_dev_migrator`;
  база `orders_prod`, роли `orders_prod` и `orders_prod_migrator`.
- Данные и credentials одного окружения не дают доступа к другому.

Критерий готовности: два окружения одного приложения разворачиваются и обновляются
независимо; роли одного окружения не могут подключиться к базе другого.

Граница первой версии: приложение с мигратором в конфигурации получает одну базу
и две роли — пользователя приложения и мигратора. Новое приложение без мигратора
не получает БД и её credentials. Выбор окружения и связанные параметры не реализуются.

Архитектура окружений требует отдельного согласования перед реализацией.

## PAAS-006 — Автоматическое версионирование всех репозиториев

- Статус: требование пользователя; реализация отдельным согласованным change.
- Цель для `0.x.x`: во всех трёх репозиториях minor по умолчанию, patch по `fix:`,
  minor по `!`/`BREAKING CHANGE:`. Переход на `1.0.0` согласуется отдельно после
  готовности мультинода. Начиная с `1.0.0`, API проектировать с обратной
  совместимостью; bump-политика `0.x.x` на `1.x.x` не переносится.
  При нескольких изменениях выбирается максимальный bump в пределах согласованной политики.
- Проверено по локальным файлам, без запуска GitHub Actions:
  - `paas-common`: `.github/workflows/release.yml` запускает Release Please на push в main;
    `configs/release-please-config.json` содержит только `release-type: go`,
    manifest указывает `0.3.2`; явного правила minor по умолчанию нет.
  - `paas-ctl`: только `release-reusable.yml` с `workflow_call`; caller `release.yml`
    и release-конфиги отсутствуют. `scripts/init-workflows.sh` может их создать,
    но его шаблон также не задаёт minor по умолчанию.
  - `paas-daemon`: то же состояние, что у ctl.
- Источник поведения стандартной стратегии: [Release Please default strategy](https://github.com/googleapis/release-please/blob/main/src/versioning-strategies/default.ts).
- Работа: реализовать согласованную политику `0.x.x`; подключить недостающие
  callers/configs без ненужной генерации остальных workflows. В `1.x.x` проектировать
  API с обратной совместимостью.
- Приёмка: проверены обычный commit → minor, fix → patch, breaking → minor,
  смешанный набор, отсутствие рекурсивных release-коммитов и запрет автоматического
  перехода на `1.0.0`.
- Нужна отдельная проверка существования выбранной версии action, настройки
  `RELEASE_PLEASE_TOKEN` и реального CI; наличие YAML не подтверждает успешную автоматизацию.

## PAAS-008 — Права БД по компонентам приложения

- Статус: будущее развитие; на первом этапе компоненты, которым нужен доступ к БД,
  используют общую БД и пользователя приложения. БД выделяется только при наличии
  мигратора в конфигурации приложения.
- Цель: выдавать каждому компоненту отдельную роль с минимальными правами только на
  таблицы, необходимые этому компоненту.
- Работа: описать таблицы и операции, сопоставить их ролям компонентов, добавлять
  права безопасно при миграциях и отзывать ненужные grants.
- Приёмка: компонент не может читать или изменять таблицы вне своей явно заданной
  области; начальная модель общей роли продолжает работать до отдельного перехода.

## PAAS-007 — Мультинод для 1.0.0

- Статус: обязательная возможность будущего продукта `1.0.0`/`1.x.x`.
- До этого продукт `0.x.x` работает только на одной ноде.
- Работа: отдельно согласовать управление несколькими нодами, размещение компонентов,
  хранение данных и поведение при недоступности узла.
- Не приравнивать мультинод к HA без отдельного контракта отказоустойчивости.
- Приёмка: несколько нод поддерживаются и проверены до выпуска `1.0.0`;
  конкретные сценарии определяются в отдельном OpenSpec change.
